### Problem
No app icon badge with unread MPs (operator, 2026-11-17).

### Trace (dev-swift `1df2121a`)
- Launch: `RootNavigationView.swift:40` loads the forum list whatever the start tab, through `PrivateMessageCountingSource` (`RootModel.swift:159-166`, `PrivateMessageCount.swift:58-60`), which records the home page's count (`ForumListParser.swift:39`). `RootModel.appIconBadge` (`RootModel+Notifications.swift:7-10`) then has it and `RootNavigationView.swift:60-63` sets the icon. **Messages never needs to be opened**: the new hosted test of the real root shows it.
- Background: `MPBackgroundCheck.swift:60` sets the badge after each check (default interval 30 min, `SettingKey.swift:81`).
- Setting: `mp_badge_enabled` default true (`SettingKey.swift:78`); off gives 0.
- Permission: asked at launch (`SwiftHFRApp.swift:105`, `MPNotificationCenter.swift:17-30`).

### Cause found in the code (first launch only)
The root sets the badge only when its count changes. At a build's first launch, the home page's count can arrive while iOS's permission prompt is on screen. Measured on the iOS 27.0 simulator: with authorization `notDetermined`, `badgeSetting` is `notSupported` and `setBadgeCount` **does not throw**, so the write is dropped silently (the « Badge not set » log never fires). Nothing sets the badge again until the count changes. Legacy sets it again each time the app is back on screen (`MainWindow.swift:2588-2593` @ 87fe0d1c, `syncAppIconBadge` at `:1564-1567`).

This does not explain a build that never asked for permission (the operator's comment of 22:00: SwiftHFR missing from iOS Notifications): that remains cause 1, the build.

### Change
- `MPNotificationDelivering.setBadge` returns whether iOS shows the badge (`@discardableResult`): `MPNotificationCenter` reads `badgeSetting == .enabled` and the write's success.
- `RootNavigationView` takes the delivery as a parameter (default `MPNotificationCenter()`), keeps a badge iOS did not show pending, and sets it again when its window becomes active. A shown badge is not set again on every foreground (unlike legacy): the app's count can be older than the one the background check just set (GAP-192). Limit: a pending badge may rewrite such a newer count once, when a background check set it after badges were turned on while the badge was pending; the next page load corrects it. A refused permission keeps the badge pending: one settings read and one write per foreground.
- Why no wider: the count path is right (test below); Réglages is untouched (scope 3 needs a wording decision).

Multi-window: `SharedPrivateMessageCounts` gives every root the same count per generation, so N windows only repeat the same write; a per-window `badgeIsPending` cannot set a count another window has moved past. Isolation: `View` is `@MainActor`, the `Task` writes `@State` there; compiles under strict concurrency. Lint by hand: no line over 140, no function over 50 lines, no nesting or discardable-let issue.

1. **Low** — `App/SwiftHFR/Root/RootNavigationView.swift:66-68`: the comment says "a newer count a background check set stays", which is not true for a *pending* badge. Scenario: iOS « Pastilles » off, count 3 pending; app in background, 2 more MPs arrive, the member turns « Pastilles » on, the background check writes 5; back to the app, the root rewrites its stale 3, and nothing reloads the count on foreground (`AppLifecycle.scenePhaseChanged` only rechecks sessions). Self-corrects at the next page load. Fix: state the limit in the comment (and PR body), or, when pending on `.active`, skip the write if the ledger's last recorded count is newer than the page that gave `appIconBadge` — the comment fix is enough for me.
2. **Detail** — same lines: a refused permission keeps `badgeIsPending` true for the life of the root, so every foreground costs one `notificationSettings()` + one `setBadgeCount`. Harmless, and it is what makes device check 4 work; the doc comment says "no permission yet" only — add "or refused".
3. **Detail** — `docs/lots/LOT-140-background-mp-check.md:70` ("the running app sets the icon badge from the Messages badge count") does not mention the re-set rule (#1060); one clause, same PR or the ledger note.
4. **Detail** — `theLaunchsHomePageGivesTheIconItsCountWithoutOpeningMessages` passes before and after, as the PR says: a characterization test of the count path, fine as such.

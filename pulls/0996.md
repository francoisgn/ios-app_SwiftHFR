## What and why

**Problem.** Since 2026-11-17 00:20 UTC, `ReaderPageEndWebTests` (`atRestTheHintSitsTheSharedGapUnderTheLastMessageAboveTheBar`, `aTallPageReportsItsEndOnlyWhenItIsScrolledThere`) and `ReaderInsetsWebTests` (`aRefreshReopensAtTheSameMessageWhenTheBarsChanged`, and `aRefreshAfterAPinchZoomReopensAtTheSameMessage` in job 133770412196) fail now and then on the iOS 27 simulator.

**Cause (one signal for all three).** The tests treat `ready` as "the scroll view shows the document". `ready` is posted by `reader.js` from the WebContent process; the UI process applies the document's first layer-tree commit (content size + WebKit's reset to the top, see `WebKitResetWatch`) later. Under load the gap is wide enough to be seen.

| Test | What it waited on | Why not deterministic | Evidence |
|---|---|---|---|
| `atRestTheHint…` | `ready`, then "offset within 2 of `contentSize + 50 − bounds`" | Before the commit `contentSize` is the blank page's (650 = 800 − 100 − 50): the "end" is −100, the offset already there, so the wait passes on its first poll and the hint is measured with the page at its top | jobs 133712438518, 133717388761, 133753519977, 133769701618, 133770412196: band `0.0...650.0` (offset −100), hint at 3070–3101, test over in 1–3 s |
| `aTallPage…` | same, then a way back to `last() − 20` | Same stale `last()` = −100: target −120, unreachable, 60 s timeout | job 133712438518: `offset (0.0, -100.0), target -120.0` |
| `aRefreshReopens…` / `aRefreshAfterAPinchZoom…` | the new page's `scrollY` = 1000 | Before WebKit's reset the scroll view still shows the old document at the same reading top (offset 900 under 100 = 1000): the new page's `scrollY` can read 1000 before the reset puts it back to 0 and the held restore runs. Likely cause, read from the code: the log shows `scrollY` 0 right after `settled`, while the later offset-900 and `readingTop` checks of the same 1 s test passed (so the app's restore did land) | jobs 133772120017, 133770412196 |

**#943.** Its stylesheet changes only CSS values (margins, font sizes, quote fill); nothing in it changes when `ready` is sent or when WebKit commits. It is not shown to be the trigger; runner load (`Timed out waiting for Launch Services database update`, WebContent launches over 1 s in the same windows) widens the existing gap.

**Change (tests only, no app code).**
- `showsDocument(_:)` (`ReaderWebTestSupport`): waits until the scroll view's content height (at zoom 1) is within 2 points of the page's `scrollHeight` (the agreement green end-of-page runs show; blank page 650 vs documents of 3000+). The new document's size only reaches the scroll view through a layer-tree commit after the navigation's commit, the same one that applies WebKit's reset. Only valid for a page taller than the viewport (stated in its comment; all callers are).
- Page-end tests: `showsDocument` after `ready`, before any scroll and before `last()` is computed.
- Insets tests: `showsDocument` before the first document's own scroll, in the three tests that scroll it (same class, no failure seen there yet). The refresh restore waits on `restored(_:token:in:timeout:)`: the reset watch committed the new document and has ended (the reset came, the restore was sent), **and** the page's `scrollY` and the scroll view's `readingTop` both equal the target. The post-load assertions (`scrollY after load`, offset 900, `readingTop`) are unchanged.

Why this wide: these are the only tests that scroll a freshly loaded page themselves or read a restore from the page side; the landing test (`ReaderWebControllerTests`) goes through the app's landing, which already waits for the reset.

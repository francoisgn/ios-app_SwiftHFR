The App job is red on `dev-swift` (job 130925974296): `ReaderInsetsWebTests.aRestoreWhileHiddenDoesNotKeepTheControllerAlive()` fails at 94 s; `VideoPlayerSheetTests.theWebViewSendsTheRefererOnTheWireForYouTubeOnly()` and `aPlayerThatAnswers401…` fail, or pass after 210–330 s; `StaticPageTests.theWebViewRunsNoPageScript()` passes in 300 s. ### Cause
The job logs give test names and durations, not Swift Testing failure messages.

| Evidence | Reading |
|---|---|
| `VideoPlayerSheetTests.theYouTubePlayerRequestIdentifiesTheApp()` (sync, no I/O) took **48 s**; most `@MainActor` model tests took 90–150 s | the main actor is starved during the parallel run |
| Green run 43060241312: the windowless player tests took **245–268 s** and the windowless static page 67 s; the reader tests, hosted in a window, took 5–25 s after the first one | web views in no window are the slow ones |
| `for _ in 0..<3000 { Task.sleep(10 ms) }` in the player tests | a budget in iterations, not in time: each turn waits for the starved main actor, so "30 s" became 300 s |
| `aRestoreWhileHidden` passed in 7 s when green and failed at 93.6 s (about its 90 s wait) | its second document loaded while the web view was out of its window, and WebKit did not always finish that hidden load |
| #810 (job 130808619061): after 21:55 no test finished for 6 h; 21 suites (web and non-web, all main-actor) never reported | a blocked main thread, or a wait that never ends, with nothing to stop it |

### Change
- `WebTestWaiting.swift` (new):
  - `TestEvent`: a one-shot event whose deadline runs on a detached task.
  - `answer(of:within:)`: a WebKit call that never answers becomes a `WaitTimeout` failure.
  - `WaitBudget`: a task-local deadline, so a WebKit call inside `until(async:)` gets only the time left.
  - `hostInWindow`: factored out of `makeController`.
- `VideoPlayerSheetTests`: the player is shown in a window. The tests wait for the server's first request, the failure callback and the end of the load (KVO on `isLoading`), each with a deadline, instead of 3000-iteration loops. The assertions are unchanged, plus a check that the request arrived before the deadline.
- `StaticPageTests`: the page is shown in a window. `LoadWaiter` also ends when the content process dies, and has a deadline. **Tightened**: the test now fails when the page did not load, instead of passing on an empty body.
- `ReaderInsetsWebTests.aRestoreWhileHidden…`: the page leaves its window once ready, and the test waits until `document.visibilityState` is `"hidden"`. Then it sends a two-frame probe and the restore a refresh sends (`scroll(toReadingTop:)`). It asserts the controller is freed (30 s, unchanged) and that the probe never answered. The test no longer asserts that a document loaded while hidden reaches ready (`recorder.ready == [1, 2]`). That load was what stalled on CI, and the refresh-to-restore path stays covered by `aRefreshReopensAtTheSameMessageWhenTheBarsChanged` (#368, Fable round 3 nit 4). Seeing this test red under the #662 mutation needs a Mac: #845.
- `ReaderWebTestSupport.evaluate` goes through `answer(of:)` and `WaitBudget`, so `until(async:)` and `settled` cannot hang on a JavaScript call that never returns.
- `.github/workflows/ci.yml`:
  - `timeout-minutes: 45` on "Build and test on the simulator": a green run takes about 16 min there, and a failing one adds up to 10 min of `simctl diagnose` (LESSONS 54).
  - `timeout-minutes: 75` on the app job, which also covers the simulator setup and the 5-minute Release build.
  - Without these limits, a hang holds a runner for the 6 h default, as on #810.

Why this wide and no wider: other polling loops and unbounded continuations in the app tests (`AppThemeTests`, `ConnectionCounter`, model gates in `ReaderTestSupport` and `ModeratorAlertTestSupport`) are not in the failing set. No test is skipped, disabled or loosened (#368). This diff does not explain #810's own hang; the step timeout now turns such a hang into a fast red.

### Tests
The cloud cannot build the app, so this CI run is the first compile. Checked on Linux:
- `TestEvent`, `answer(of:)`, `WaitBudget` and `until(async:)` compile under Swift 6 with warnings as errors.
- They behave as expected: an event fires, a wait times out, 2000 zero-timeout waits all end, a call that never answers throws `WaitTimeout`, and a 300 ms `until(async:)` ends at 0.30 s.
- SwiftLint `--strict` is clean.

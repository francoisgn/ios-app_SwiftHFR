### Problem
#681 (beta feedback on legacy #372): on the iPhone Duo's cover screen, Catégories → scroll the list → tap a category froze the legacy app. The issue asked whether SwiftHFR has the same freeze, and whether it is the #979 layout loop fixed by #1048.

### Cause: not reproduced in SwiftHFR, and not the #979 loop
- **Legacy's cause** (`HFRswift/Swift/Common.swift:337-341` @ 87fe0d1c, `backlog.md:65` HFR-097): a collapsed **system** large title, then a push, loops in `UINavigationController` layout; legacy's fix is inline root titles on both Duo displays (`PhoneDisplayPolicy`). SwiftHFR has no system large title since #998 (2804fc93): `screenTitle` sets `.navigationBarTitleDisplayMode(.inline)` on every tab root, and the large title is a list row (`ScreenTitle.swift`). So legacy's precondition is gone on every iPhone, Duo included.
- **#979's cause** (`DensityHeaderMargin`, fixed by #1048): it needs a section header with `densityHeaderMargin()` in the list left under the push. `ForumListView` has none (rows only), so the Catégories push cannot hit it.
- **Measured** on the iPhone Duo simulator (iPhone19,4, iOS 27.2, boots folded): the window of the whole screen is **466 × 678 pt** (the device type's `capabilities.plist`, display `LCD`: 1398 × 2034 px @3x), safe area **right 84 pt, bottom 34 pt** (the vertical system strip on the right), horizontal size class compact. In it, the issue's steps pass:
  | Run | App code | Result |
  |---|---|---|
  | head (`1a8a1997` + this test) | current | 4/4 pass |
  | before #1048 | `ListDensity.swift` @ `1df2121a^` (#1048 touched no other app file) | 4/4 pass |
  | before #998 on Catégories | `.navigationTitle("Catégories")`, no large-title row (system large title, as at `2804fc93^`) | 4/4 pass, no hang |

  The third run means the legacy loop does not show in a hosted test on the simulator even with a system large title: the physical Duo stays the deciding check (below).

### Change, and why this wide
Tests only:
- New `CategoriesCoverScreenPushHostedTests/aCategoryOpensAfterAScroll(density:scrolled:)`: the Catégories tab as `RootTabsView` builds it (tab view with `.tabBarMinimizeBehavior(.onScrollDown)`, the app default; collapsed `NavigationSplitView`; Favoris beside it), 22 categories × 8 sub-forums, signed in (fakes), hosted in a window of the whole screen of the simulator it runs on. It scrolls the list to its end in quarter-screen steps (or not), selects the last (or first) category as a tap does (the list's `UICollectionView` delegate `didSelectItemAt` on the row that shows its label), waits for `topics:<n>:1`, gives 20 frames under the push, and checks `selectedSource` and the request. Regular and compact density. A 45 s main-actor watchdog ends the run with `fatalError` naming the last step (`[#681] HANG … after '<step>'`), as #979's test does.
- `HostedHangWatchdog.swift`: #979's private `StepLog` and accessibility helpers move to one shared file (tag per test); `FavorisHeaderTapHostedTests` uses it, unchanged otherwise. The accessibility switch is process-wide, so `beginAutomation()` / `endAutomation()` count their users (`AutomationUsers`) and turn it off only with the last one: a suite ending first can no longer pull the tree from one still looking up rows when suites run in parallel (review round 1).

No app change: nothing failed to fix.

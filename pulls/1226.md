### Problem
The app-lock switch read « Verrouiller l’app (Face ID / code) » on every device, promising Face ID on Touch ID iPads and passcode-only devices (HIG › Managing accounts: refer only to authentication methods available in the current context; also an App Review risk). The lock is new in SwiftHFR (LOT-173, GAP-168/169): no legacy counterpart.

### Cause
`SecuritySettingsSections` used a fixed string; nothing read `LAContext.biometryType`.

### Change
- `AppLockMethod` (`faceID`, `touchID`, `opticID`, `codeOnly`), built from `LABiometryType` (`init(biometry:)`), with `switchTitle`: « Verrouiller l’app (Face ID / code) », « … (Touch ID / code) », « … (Optic ID / code) », « Verrouiller l’app (code) » when the device reports no biometry.
- `DeviceOwnerAuthenticating.method` (the existing seam of the lock): `LocalAuthenticationAuthenticator` reads `biometryType` after `canEvaluatePolicy(.deviceOwnerAuthenticationWithBiometrics)` (which is what fills it, **whatever that call returns**: a Face ID iPhone with no face enrolled, or locked out, still reports `.faceID` and still shows « Face ID / code », which is right: the device offers that method; review round 1 corrected my first comment and Mac check on this point). Previews and the test double return `.faceID`.
- `AppLockModel.switchTitle` forwards it; `SecuritySettingsSections` uses it. The authentication policy itself (`deviceOwnerAuthentication`, biometrics then code) is unchanged.
- `docs/lots/LOT-173-keychain-sync-lock.md` no longer quotes the fixed title (review round 1).

### Tests
`AppLockMethodTests` (written first): the title for each `LABiometryType` (`faceID`, `touchID`, `opticID`, `none`); the model takes its title from the authenticator for each method; the code-only title mentions no biometry. The real `LAContext` read is one line over a system API: Mac check on #893 (Touch ID iPad simulator shows « Touch ID »; a Face ID device shows « Face ID » even with no face enrolled; « code » only on a device that reports no biometry, e.g. an iPad without Touch ID). Not run here (Linux); `compile-check` runs on the head.

If the device has the sensor but nothing is enrolled (or biometry is locked out), `canEvaluatePolicy(.deviceOwnerAuthenticationWithBiometrics)` returns false with `.biometryNotEnrolled` (or `.biometryLockout`), but `biometryType` still says `.faceID` or `.touchID`.
   - Failing scenario: a Face ID iPhone with no face enrolled shows « Verrouiller l'app (Face ID / code) ». The Mac check on #893 will fail against what the PR says it checks.
   - Fix, two options:
     - (a) Keep the behaviour, which is HIG-compliant because the device does offer Face ID. Correct the comment, the PR body and the check.
     - (b) If « code » is wanted when nothing is enrolled: when `canEvaluatePolicy` returns false with `.biometryNotEnrolled`, map to `.codeOnly`. Add a pure mapping `init(biometry:canUseBiometrics:)` with a test for each case.

That section also re-renders on account-sync changes. `canEvaluatePolicy` never shows UI and costs little, so this is acceptable. It also picks up an enrolment change on the next render.

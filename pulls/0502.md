Direct-PR: LOT-049 review leftovers from #485
Author model: Opus 5.5

**Problem.** Review leftovers of #485 (merged as 2cfa0a3): the spec's intentional difference 3 and the `QuoteComposer.prefill` doc comment said the reply is posted "with CRLF either way (`W14`'s body)" and that HFR "accepted `W14`'s bytes as served". The spec's formatter section did not say tags inside the quoted text are skipped, and did not name the test that checks it.

**Cause.** `W14`'s captured `content_form` has a bare LF after each `[/quotemsg]` (CRLF only inside the quoted text). The flow posts CRLF everywhere, as a browser does (LOT-048's `FormBody(newlines: .crlf)`), and `QuoteCaptureTests` compares with `PostingHarness.browserBody(of: "W14", …)`, which turns those LF into CRLF: so the posted bytes are not `W14`'s as served.

**Change (wording only, no behaviour change).**
- `docs/lots/LOT-049-quote-engine.md` intentional difference 3 and `QuoteComposer.swift:8-9`: the flow posts CRLF line breaks as a browser does (LOT-048); the posted body equals `W14`'s once its bare LF after each `[/quotemsg]` are turned into CRLF (`PostingHarness.browserBody`). The `\n` prefill design is unchanged.
- Behaviour → `QuoteSelectionFormatter`: the bolded occurrence is the first case-insensitive one outside any `[…]` tag of the text (`visibleRange`, regex `\[[^\[\]]*\]`).
- Tests list: names `innerTagsAreNotSearched`.
- Edge cases: a member's own bracketed text (e.g. `[1]`) matches that regex, so it is treated as a tag and a selection on it is never bolded (prefill unchanged).

The CodeRabbit suggestion declined on #485 (match a selection across formatting tags) is now #501 (M5, optional, at parity with legacy).

**Tests.** None needed (wording). `swift build` of `Packages/HFRKit` passes with the doc-comment change.

LOT-037 (complete; closes the lot: its row is set to done in this PR).

**Problem.** HFR answers HTTP 200 to every write, success or not. The write flows (LOT-048, 050, 051, 054) need one classifier that never reports a success HFR did not confirm.

**Cause.** Legacy treats "no refusal found" as success: the 99-byte plain-text reply to a bad `hash_check` (W17b) has no `.hop`, so the oracle says `success`.

**What changed.**
- `HopResponseParser.classify(html:context:requestURL:)` in HFRParsing (pure, typed throws), producing the LOT-012 `HopResponse`. `success` needs a refresh to an https forum URL **and** a `.hop` sentence without link/input; W17b is `rejected`; the W17c sentence is `loggedOut`; `alreadyAlerted` only in the `.alertPrepare` context (same shape as a refusal otherwise); everything else `unrecognized`.
- `SearchRedirectParser.target(inRefreshContent:)` loses `private` so the refresh meta is read by one function (no behaviour change).
- `HopResponse.Kind` doc comments match the rule.
- Spec `docs/lots/LOT-037-hop-response-classifier.md` (legacy sources, differences from legacy, pending capture), `docs/HFR-PROTOCOL.md` §6c `LOT-037`.
- No wider: no client flow, no form parsing (LOT-036), no HFRClient change.

**Tests** (`HopResponseParserTests`, 18 tests, 61 cases): differential on the 17 LOT-004 response oracles (kind, message, anchor); W17b asserts the legacy `success` and the corrected `rejected`; W17c `loggedOut`; GET writes W18/P03a/b/d; read pages R12/RA5, forms R44/R46 never success; structural edges (off-forum refresh, refresh without `.hop`, `.hop` without refresh, empty bodies, alert context). Shown to fail with the legacy rule restored (16 issues across 8 tests: W17b, refresh/hop requirements, off-forum refresh, empty bodies, R44, R46).

**Pending capture** (classified conservatively until captured): alert already sent, alert submit success, other logged-out write answers, poll vote answer.

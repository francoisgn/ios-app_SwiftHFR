### Problem
With iCloud on, the composer's upload history stays on each device (ADR 0013 rules 2 and 3: "upload histories do not leave the device"). The operator decided (2026-11-16, option A) that the 100 newest uploads follow the Apple ID, merged by id, also at activation.

### Cause
Not a bug: ADR 0013 kept the history device-only. Legacy has no iCloud at all (`git grep NSUbiquitousKeyValueStore 87fe0d1c` finds nothing; the history file is `HFRswift/Swift/ReplyService.swift:1936` @ `87fe0d1c`).

### Change
Engine only (HFRStorage). The app wiring of `SyncedListsStore` is #447 (blocked on the iCloud entitlement): it will pass `ImageUploadServices.liveHistory.store` as `rehostHistory:` (noted in the LOT-172 spec). Also for #447: the image picker loads the history once and does not observe `changes()`, so an open picker will not show uploads merged meanwhile.
- **`SyncedListsStore` gets a fifth slot, `rehosthistory`** (one global key, like the history): on every event (initial-sync rule / activation, server change, saved local change) `mergeRehostHistory()` merges the cloud's uploads into the device's history by `RehostedImage.id`, applies the removals of both sides, then pushes the 100 newest uploads and the removals when they differ from the cloud's (compared by ids, never by bytes; equal dates ordered by id so devices converge). Not last-writer-wins: adds made on two devices both survive. No push after a failed save, nor over a newer cloud `version`, nor over a cloud value that changed during the merge (its own event merges it).
- **Removals are tombstones**: `RehostUploadHistoryStore.remove(id:)` now records `{id, removedAt}` (newest 100 kept) in the device document, an optional field (`decodeIfPresent`, omitted when empty, so a history without removals is written byte-identical to before); the store gains `changes()`, `document()`, `merge(images:removals:)` and `replace(with:)`. Documented limit: a device that merges after more than 100 removals elsewhere can push the oldest of them back (ADR Amendment 4).
- **Cloud form** `RehostHistoryEnvelope` `{version:1, items:[RehostedImage], removals:[…]}`, dates in `JSONEncoder`'s default form like the device file (seconds since 1970 does not read a `Date` back equal, LOT-064).
- **Apple ID rules as for the lists** (Amendments 1–2): nothing while signed out (history kept); a different Apple ID quarantines the **whole** history (removals included) and empties the store, restored if that Apple ID returns. **For the orchestrator/operator:** the 90-day quarantine lifetime applies, as for the lists; unlike the lists, the part of the history beyond the 100 newest exists nowhere else, so an Apple ID that never returns loses it after 90 days. The issue asks for the list rules and the ADR states it.
- **ADR 0013 Amendment 4** + markers on rules 2/3, a §3 policy row, the appendix E row and the budget line; measured worst case now ≈ 341 KiB in 47 keys (history key ≈ 49 KiB), bound raised to < 360 KiB. LOT-064 and LOT-172 specs updated.
- **Older builds**: no released build wrote the key or the file field. A build before this PR ignores the key (`isListKey("rehosthistory")` is false at the base: no `.` and not `allowlist`) and reads the history file without `removals` (unknown key ignored by its synthesized decoder; dropped if it saves, which only lets a removed upload come back).

Why this wide: the issue's scope (merge, cap, activation, Apple ID rules, budget, ADR). No app code touched.

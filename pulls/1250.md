**Problem.** Some tests waited a fixed delay and then asserted a negative. On a loaded runner they could pass without running the interleaving they document (LESSONS 2; same pattern as #704, #772, #521):
- `BlocklistSyncTests` slept 50 ms "to let the edit queue".
- `ComposerPlacementTests` slept 100–400 ms before "nothing changed".
- `ArchivedDraftsTests` slept 120 ms to outwait a 50 ms autosave.

**Change.**
- **Engine (`HFRClient`):** a new internal `MPStorageSync.callsInFlight` counts the calls that entered `serialized` and have not returned. Tests read it through `@testable import HFRClient`, as `CapturedSessionCheckTests` already does.
  - `BlocklistSyncTests.aNoOpEditDuringASyncKeepsThatSyncsMerge` waits until the edit has entered the queue behind the held read, asserts it, then opens the gate.
  - The engine's `anEditWaitsForTheSyncInFlight` (200 `Task.yield()`s, same class of problem) now waits on the counter too.
- **`ComposerPlacementTests`:** the page records the `dockedComposer` it saw in each pass, and the stand-in bar reports its height.
  - The inset tests wait for the pass with the covering bar, then for the pass with `.full`. They also check `largest`: no inset handed to the page while covered reached the viewport.
  - The close, width-change and keyboard tests check their negatives after `RenderProbe.settled()` (three rendered updates). The keyboard test also checks at the source: the composer has no close reason and no close asked.
  - In the keyboard test, the window is key from the start, and the editor's focus is awaited and asserted before the keyboard goes.
  - The bar-top test waits for the layout where the inset reaches the bar.
  - `barTop` and `isInScrollView` moved to `ComposerPlacementTests+Touches.swift`.
- **`ArchivedDraftsTests`:** the test keeps the autosave scheduled before the set-aside (`ReplyComposerModel.pendingAutosave`, a test accessor). It checks that task was cancelled by `archiveAndClear` and awaits it.
- Nothing is loosened: every earlier assertion stays, and assertions were added.

**Proof.**
- **Engine, run on Linux:** green.
  - Mutation "`edit` skips the queue" (`MPStorageSync.swift:75` → `try await performEdit(now: now, change)`): `anEditWaitsForTheSyncInFlight` is red and the edit is lost.
  - Reviewer's mutation (`await previous?.value` dropped in `serialized`): red 10/10 and 25/25.
- **Owed on a Mac** (app-hosted, argued by reading, not run):
  - `ReaderUnderBars.insets` returns `measured` → `underAFullHeightComposerThePageKeepsItsInsets` and `aComposerOpenedAtFullHeightNeverHandsThePageTheViewport` go red (`largest`, `bottom`).
  - `MPStorageSyncModel.edit`'s "changed" flag kept as model state → `aNoOpEditDuringASyncKeepsThatSyncsMerge` goes red. Write it as a stored `Bool` set by `edit` inside its work closure, and have `run` read that property instead of the `merges` closure for every call (as the comment at `MPStorageSyncModel.swift:240` warns). `merges: { true }` is caught by `anEditThatChangesNothingStartsNoMerge` instead.
  - `archiveAndClear` without `settleAutosave()` → `aPendingAutosaveLeavesNoActiveDraftAfterASetAside` goes red (`pending.isCancelled`; the outcome alone stays the same, since a late autosave writes nothing on an empty text).
  - On the Mac run, also check that later suites do not depend on which window is key.

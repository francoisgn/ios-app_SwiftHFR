### Problem
Device pass of #1388 (operator's iPhone Duo, trace build, read-only): on every trip to the background the root's `usesSidebarRoot` flipped twice (iOS lays the app out in the other size class for its app-switcher snapshots), the swap rebuilt Favoris, and its appearance sent `GET /forum1f.php` **in the background**. Locked, that request froze and ended `URLError.timedOut` after 25.8 s and 56.3 s; the list kept « Le forum ne répond pas » on return. 3 trips in 3 minutes gave 3 background reloads, 2 timeouts (table on #1404).

### Cause
- `App/SwiftHFR/Root/RootNavigationView.swift:172` (`RootLayout.body`) computed `usesSidebarRoot` from the size classes whatever the scene phase, and `:179-187` builds one root or the other: a flip replaces `RootTabsView` by `RootSidebarView` and back, so the list views are rebuilt. The list models are not (they live in `RootModel`, `@State` of `RootNavigationView`), but:
- `App/SwiftHFR/Navigation/TopicListView.swift:129` runs `model.onAppear()` from `.task(id: model.wantedFilter)` on every appearance, and `TopicListModel.onAppear` (`TopicListModel.swift:278-293`) refreshes Favoris and flags on each one (`favorites.autoRefresh`); `MessageListView.swift:101` does the same for the MP list (`MessageListModel.onAppear` reloads the page on screen).
- Nothing stops or replays a load in flight when the scene leaves, so a request iOS freezes surfaces as `timedOut` (`ContentLoader.finish` keeps the error).

### Change
0. **When a window is away** (`SceneAwayTracking`, new, applied above the root in `RootNavigationView`; `\.sceneIsAway`): from a move to `.background` until the next `.active`. Only `.background` starts it: the snapshots are taken there, and an inactive window (notification prompt at first launch, Control Center) is on screen and its requests run. It follows the **moves**, not the phase alone: a view hosted outside a SwiftUI scene reads the default phase, `.background`, all along (measured: the first version keyed on the phase alone left every hosted test away, so Duo folds never swapped and lists never loaded); before the first move, a window counts as away when its phase and the app (`UIApplication.applicationState`) are both in the background, computed in `body` so the lists' first `task` already sees it (round 1, finding 2).
1. **No root swap while away** (`RootLayout`): the root last built stays; back on screen the size classes decide again, so a fold or unfold made while away swaps then (`rootSwapped()` runs as before). Real size changes while active (Duo fold/unfold, iPad multitasking, rotation) are unchanged.
2. **No list load while away** (`SceneAwareListLoad`, new, used by `TopicListView` and `MessageListView` in place of their `.task`): an appearance while away runs `onAppear` once the window is active again, not before.
3. **A load in flight when the window goes away is stopped and asked again on return** (`suspendLoad()` = `ContentLoader.suspend()`, then the model's `retry()` on return). The stopped load is remembered by the loader (`ContentLoader.wasSuspended`, cleared by the next load), so a list built again meanwhile (a fold made while away swaps the root on return) asks for it too (round 1, finding 3). On Messages, `suspendLoad()` also stops a « MP multiples » search as `chooseSegment` does (`loadCount` first), so its loop does not ask for the page again in the background; `retry()` resumes it (round 1, finding 1). Chosen over "retry once after a `timedOut`": the frozen request's result is dropped deterministically (superseded generation), whatever error iOS makes of it (`timedOut`, or `networkConnectionLost` which maps to `.other`), with no guess about which failures came from the suspension; rows and any previous error stay as they were meanwhile. Cost: a load that would have finished in the few background seconds iOS grants is sent again on return (one request).

Why this wide: the trace shows the reload comes only from the root rebuild (no session check, no home reload on return), so (1) removes the cause; (2) and (3) close the class for any other rebuild or load while away (a tab split collapsing on the snapshot traits, a pull just before locking). **Not covered**: the reader's page loads, the profile, the categories' forum list and the Plus lists that load on appearance (bookmarks, offline, quality alerts) are not stopped at a lock and can still end `timedOut` on return: follow-up #1422.

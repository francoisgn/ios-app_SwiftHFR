## What and why
Every lot that persists data (060, 061, 063, 064, 065, 090, 091, 119, 130, 067/158) was choosing its store alone. On 2026-10-28 the operator asked for one matrix deciding what belongs where, judged by transferability first:
- in MPStorage: it follows the HFR account and is shared with userscripts and the Android client;
- on the device;
- in iCloud: it follows the Apple ID.

**`docs/adr/0013-storage-tiers.md` (Accepted):**
- four tiers and their rules, with one master per item;
- conflict policy: LOT-062 merge for MPStorage, last-writer-wins for iCloud KVS, and the cloud wins on initial sync;
- offline behaviour;
- legacy import order: device first, then cloud;
- accounts are device-only, with the opt-in iCloud Keychain copy and the app lock (Q12);
- MPStorage sync is on when a storage thread exists, else asked at the first write (Q14);
- the simplification list;
- the needs: the iCloud KVS capability and entitlement, and no dependency;
- appendix: the matrix of every persisted item, with `origin/master` citations, sensitivity, size and churn, store and parity flags.

**Operator decisions of 2026-10-29** (from the Opus review rounds):
- theme parity: all 7 theme keys are kept and synced, and FEAT-010's single accent is out of scope;
- super-favourites and smiley favourites are per HFR account; the legacy global keys are imported into the account active at first import;
- the Keychain opt-out uses the full `enabledAt` timestamp, with fail-closed rules:
  - a tie switches off;
  - a push never lowers `enabledAt`;
  - bootstrap happens only from a full envelope later than every known `deletedAt`;
  - a bootstrapped item is provisional;
  - a switch-on over a full envelope adopts its `enabledAt` and merges the accounts;
  - accepted residual risks: clock skew and a late repair;
- the account key is frozen (LOT-172 `accountKey`), with no migration when LOT-072 lands;
- `embedded_videos` is dropped.

The PR does not change running storage code, and most ownership and migration rules are explicit. However, the credential-sync contract has inconsistent opt-out transitions that should be resolved before implementation.

**Retained concerns**
- **Medium · security · observed:** The accepted credential-sync contract does not consistently preserve opt-out tombstone dominance. Bootstrap imports any synchronizable item and enables sync, without distinguishing a credential envelope from a tombstone. Race repair also preserves deletedAt while expecting it to exceed the racing device's lastPushed; a stale write completed after deletion can make lastPushed later than deletedAt, so the stated switch-off condition no longer follows. The separate rule that only explicit switch-on may overwrite a tombstone is protective, but leaves these transitions contradictory rather than fully specified. Implementations could disagree about consent and opt-out enforcement across credential-bearing devices.

**Security Blast Radius**
- _observed_ — Credential replication operates on the whole account envelope across the user's iCloud Keychain devices. Imported cookies retain session authority without another login. Switching synchronization off preserves device-only credentials, so it is not a remote logout or session-revocation mechanism.

**Security Findings and Attack Paths**
- _inferred_ — The identified risk concerns already participating credential-sync devices and their recovery transitions, not an established unauthenticated entrypoint. An implementation following the ambiguous bootstrap or timestamp rules could fail to converge on the user's opt-out decision; runtime credential disclosure has not been demonstrated.

**Trust Boundaries and Controls**
- _observed_ — The design distinguishes HFR-account ownership from Apple-ID ownership. KVS account changes isolate old pending data; credential replication requires opt-in and uses encrypted iCloud Keychain transport. Ordinary credential changes are expressly forbidden from recreating an absent synchronizable item or overriding an opt-out tombstone.

**Resilience and Maintainability Implications**
- _observed_ — The credential contract explicitly anticipates delayed delivery, absent items and non-conditional Keychain writes. Read-compare-write and periodic tombstone repair are meaningful safeguards, but their bootstrap and ordering conditions need reconciliation to establish the promised opt-out convergence.

**Hardening Proposals**
- _proposed_ — Define tombstone-aware bootstrap and one consistent opt-out ordering rule independent of a racing push timestamp. Validate the contract against delayed delivery, stale writes after deletion, repeated repair and a genuinely later explicit re-enable action before implementing credential replication.

# NSUbiquitousKeyValueStore

An iCloud-based container of key-value pairs you share among instances of your app running on a person’s devices.
    
    `@interface NSUbiquitousKeyValueStore : `NSObject``

## Overview

Use the shared `NSUbiquitousKeyValueStore` object to store settings, configuration information, and app-specific data in a person’s iCloud account and share it among instances of your app running on all of the person’s devices. The object stores a dictionary of key-value pairs that you provide, and propagates that data to devices with the same Apple account. Sharing data among different devices gives you a way to coordinate your app’s behavior on those devices. For example, a textbook app might save the current page number on someone’s iPhone so that the person can continue reading from the same place on their other devices.

Important

Don’t store personal or sensitive information in the key-value store. The system stores the information on disk in an unencrypted format. Store personal or sensitive information in the person’s Keychain instead.

Each app has a single iCloud key-value store object, which you retrieve from the `defaultStore` class property. Use this same object throughout your app to read and write values. Don’t subclass `NSUbiquitousKeyValueStore`.

Note

To use this object, you must distribute your app through the App Store or Mac App Store, and you must request the iCloud key-value store entitlement in your Xcode project.

The keys in the iCloud key-value store identify the item and its purpose in your app, and the value is a data object you use to implement the corresponding behavior in your app. Values must be property list types such as `Int64`, `Float`, `Double`, `Bool`, `String`, `NSNumber`, `Date`, `Array`, or `Dictionary`. To include other types of objects in the key-value store, archive them to a `Data` object first and store that object instead. Prefer simple types over custom objects whenever possible.

When you write a new value, the iCloud key-value store saves it in memory initially and writes it to disk asynchronously later. If the device doesn’t have an active Apple account, the changes remain only on the current device. When the person signs into their account, the system forwards any changes to the iCloud server and reconciles the values there with the local ones. As you make more changes, the system keeps the local and server-based copies of the data synchronized, updating each one at appropriate times.

When a value changes on one device, iCloud forwards that change to the person’s other devices.

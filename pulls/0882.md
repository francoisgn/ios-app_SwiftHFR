Closes #587
Claim: mac/M1

**Problem.** After a pinch zoom, Actualiser reopens the topic several messages too far down. There is no shift without zoom.

**Cause.** The reading top was saved from the scroll view, whose points are CSS px × zoomScale (the bar's inset is not scaled). It was restored with `window.scrollTo`, which takes CSS px at any scale, so the zoom multiplied the offset.

**Change.**
- `ReaderScrollGeometry.layoutY(readingTop:zoomScale:)` divides by the zoom.
- `ReaderWebController.readingTop` now returns CSS px, so the saved value is the page's position and the restore path is unchanged.
- Nothing else is touched: no change to `TopicReaderView`, `ReaderWebView` or the bars.

**Tests.**
- `ReaderZoomRestoreTests` (pure): zoom 1.8 and 0.5, unzoomed identity, invalid scale.
- `ReaderInsetsWebTests.aRefreshAfterAPinchZoomReopensAtTheSameMessage` (real WKWebView): zoom 2 at content 1000, then a refresh with `keepsScrollPosition`.
  - `scrollY` lands within 1 of the CSS content under the bar (1150).
  - `zoomScale` is back to 1 once the new document is ready, verified by the test.
  - Seen failing with `readingTop` reverted to the old one-liner: restored 2300, expected 1150.

**Gate.** iPhone and iPad green (1479 tests).

**Not verified.** A real finger pinch on a device: the test zooms with `setZoomScale` on the simulator.

## What and why

### P1 — MPStorage thread identified by its subject alone (`7b5130e`, round 1 `9a5f38c`)
- **Problem**: any member can send an MP titled `a2bcc09b…`. The finder took the first such row and the list hid every one: a foreign row found first made `read` throw `editLinkMissing` (the sync stayed broken until the thread was deleted from a browser), and the member could not read, answer or delete that MP in the app.
- **Cause**: `MPStoragePageParser.findThread` returned the first matching row (legacy `MPStorage.m:713-723` @ 87fe0d1c does the same); `hidingStorageThread()` removed every matching row; `MPStorageSync.locate` re-searched only on `notAddressed`.
- **Change**:
  - Parser: `MPStorageThreadSearch` is now `candidates` (every storage-subject row, in list order) + `navigation`.
  - Transport: the walk reads each candidate's first page (`locate`, factored out of `read`) and takes the first whose first message carries the account's edit link. A candidate that is another member's thread, answered "destiné", or whose page title is not exactly the subject is skipped; any other failure still stops the search (so no duplicate gets created). Cost: one extra GET of `R60a` per candidate, during a search only.
  - Sync: a cached `post` that answers `editLinkMissing` is dropped and searched again, like `notAddressed`.
  - App: `LivePrivateMessageSource` hides a storage-subject row only when it is the thread the sync located (`MPStorageCopyStore` copy's `post`) or a one-to-one thread with the storage recipient (round 1: the account's rows name it, `R13u1`, `R13u1b`, `R333b`), via `hidingStorageThread(post:)`. Another member's MP stays visible.
- **Why no wider**: identification uses verified facts only: HFR prints no edit link on another member's post (`RU1`, `R44`, `R63a`/`R63e`, HFR-PROTOCOL §6b/§6c) and prints one on the viewer's own (`R60a`); the account's storage rows name the recipient as interlocutor. A thread another member started with this subject is **not captured**: the transport test derives it from `R60a` minus its two edit links (`MPStorageCapture.threadPageOfAnotherMember`, which checks it removed exactly those); #1203 asks for the real capture. `R333b`'s two storage rows are both the account's own and stay hidden.
- **Tests**: `MPStorageTransportReadTests.skipsForeignThreadWithStorageSubject` (red: `outcome.value → 3157083`, one request), `skipsCandidateWhosePageIsAnotherThread` / `aCandidatePageThatCannotBeReadStopsTheSearch`, `MPStorageListWalkTests.skipsCandidatesThatAreNotTheAccountsThread` / `onlyForeignCandidatesIsNotFound`, `MPStorageSyncTests.aCachedForeignThreadIsSearchedAgain`, `MPStorageThreadHidingTests.keepsForeignStorageSubjectRowVisible` / `dropsTheAccountsStorageRowsByRecipient` / `dropsTheStorageRowBeforeItIsLocated` / `dropsTheLocatedThreadWhateverItsInterlocutor`. Existing tests updated for the extra GET and the new search shape.

### P2 — flag writes lacked the login fence (`2bb610b`, merge `f4eb70c`)
- **Problem**: a logout or account switch landing between the session check and the write sent `addflag` without cookies or as another account; HFR answers that with the success bytes (`P03q` = `P03a`, #314).
- **Cause**: `TopicFlagFlow` ran `confirm(check)` then a plain `send`, with no `hashCheckSeed()`.
- **Change**: seed before the check, `seed.identity != nil` after it, then `PostingSession.send(since:)` (as `DeletePrivateMessageFlow`, `PollVoteFlow`). New `TopicFlagError.sessionChanged`; in the app it reuses #1056's `session(.unconfirmed(.sessionChanged))` text and is retryable (merge `f4eb70c`). `send(since:)` gains `requiringToken: false` for the token-less GETs; the list removal reads its token in the same actor turn.
- **Tests**: `FlagSessionGateTests.loginDuringTheCheckSendsNothing` (every action × other account / same account again / logout; red: write sent, `failure → nil`), `identityChangeDuringTheCheckSendsNothing`, `listRemovalSendsTheTokenHeldAfterTheCheck`; app `TopicRowActionsTests.everyFailureSaysWhetherAnythingLeft` and `aSessionThatChangedDuringTheCheckOffersARetry`.

### P3 — unreadable account-sync state overwritten (`d343e3a`)
- **Problem**: after a rollback, a state of a later version (or damaged bytes) read as "off, nothing known" and was saved over: switch, `honouredDeletedAt` and `hadLocalAccounts` lost, so an opted-out device could bootstrap again.
- **Change**: absent → off, nothing known (unchanged). Unreadable → `loadState` throws the new `AccountSyncError.unreadableState`; every operation loads before it saves, so nothing is written over it (ESSENTIEL persistence rule). The app shows « … vient d'une version plus récente de l'app ou est illisible. Mettez l'app à jour. » (it used to say "another device is changing the copy" for any `AccountSyncError`). LOT-173 spec updated.
- **Recovery** for damaged (not later-version) bytes: the operator chose option (b) on #1200, an explicit, confirmed user reset. It lands in the follow-up PR `fix/1200-p3-reset`.
- **Tests**: `AccountSyncUnreadableStateTests` — absent vs unreadable vs later version; `anUnreadableStateNeverBootstraps` was red exactly on the issue's scenario (`bootstrapped: true`, `user-a` imported, state overwritten); app `AccountsModelSyncTests.anUnreadableStateIsShownAndKept`.

### P4 — legacy accounts archive decoded without secure coding: reverted (`27f44e6`, reverted by `7b2ca13`)
- **Tried**: `requiresSecureCoding = true` and `decodeObject(of:)` limited to the classes legacy's writer puts in the archive (`MultisManager.m:49-80`).
- **Result**: the macOS run of the ready PR (run 44403024224, job 135150903639) failed `LegacyAccountArchiveTests` "decodes every field of the legacy archive" with `sourceUnreadable`. It was the only failure (567 tests, 1 issue): the replayed legacy archive does not decode under secure coding with that list, so this change would have broken the import of legacy accounts for every upgrading user.
- **Decision** (cloud/orch): revert. The three files are back to dev-swift byte for byte. P4 is not fixable here without breaking the legacy import, and the archive comes only from the app's own Keychain item. It can be revisited with LOT-067's Mac check M1 of the archived classes.

### P5 — `http` accepted on the forum host (`8f8f203`)
- **Change**: `HFREndpoint.absoluteURL(href:)` always returns `https` with no explicit port. `http` is upgraded, an explicit default port (80/443) dropped, any other port or user info refused (LESSONS 37). `SessionHostPolicy` is unchanged: it already refuses https→http redirects, and the endpoint layer is where the issue asked for the fix.
- **Effects**: the MPStorage walk follows an `http` next link over https (test updated: the "off the forum" case is now `:8080`). The new-topic composer takes the forum's `http` link over https (app test case swapped for `:8080` and a user-info link, plus `anHTTPLinkOnTheForumIsTheComposerOverHTTPS`).
- **Tests**: `HFREndpointReadTests.absoluteURLUpgradesHTTPOnTheForumHost` (red: `http://…` returned as is), `absoluteURLRefusesOtherPorts` (red: `:8080`, `:8443`, `https://…:80` accepted), `MPStorageListWalkTests.anHTTPNextLinkIsFollowedOverHTTPS`.

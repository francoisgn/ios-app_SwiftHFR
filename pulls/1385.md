### Cause
**Inferred by elimination, not observed** (Fable round 1, finding 3): on the trace branch `AccountsModel.swift` differs from the base only by trace lines, and only `adoptSyncReport` puts an existing `valid` account back to `.checking` and bumps `currentSessionChanges` with `expired=false`; the counts fit (12 check starts, 11 valid results, 11 session changes, no `accounts.restore` or `recheckSessions` line around them). The precondition (sync on, a copy whose `credentialsAt` stays ahead of the device clock) is not in the trace.

The repeated checks carry no `launch accounts.restore` / `active recheckSessions` trace line, and the check starts just before the session change: the only caller that does this is the account sync's take-over, `adoptSyncReport`'s `syncCheckTask` (`AccountsModel.swift:428-434` at `7e90d83b`: adopt, `currentSessionChanges += 1`, then `checkSessions`). The chain:
1. `checkSessions` `.valid` → `persistSession` (`AccountsModel.swift:218-220`).
2. HFR sends `md_user`/`md_passs` again with a new expiry on every logged-in answer (HFR-PROTOCOL §6c, `R74`; AGENTS learning LOT-043), so the stored account changes → `noteSyncChange(.refresh)` (`AccountsModel.swift:349`) → `AccountSync.localChange` → merge (`AccountSync.swift:94-121`, `293-331`).
3. If the iCloud copy is dated later than this device's clock (`AccountSyncMerge.newer`, a tie keeps the remote: `AccountSyncMerge.swift:67-71`), the remote copy wins and the account is reported `replaced` though it is the same login with other dates → `adoptSyncReport` → session change (`RootNavigationView.swift:44-47` → `RootModel.currentSessionChanged`, the #1231 reloads) and a new check → back to 1.

A list reload never starts a check: the loop goes through the check's own write-back. Why the copy was dated ahead on the operator's account (another device's clock, a copy written by another device) is not visible in the trace; the fix does not depend on it. `bf690808` (#1254) keys the prompt on `accounts.current?.id`, not on session changes, and `d5bba7e2` (#1202) adds no check or reload trigger at launch (its MPStorage walk does not run on an iPhone opening on Favoris, w1276b).

### Change
`AccountsModel` remembers, per account, the login a check or a login confirmed (`confirmedLogins`, set in `persistSession` and `logIn`). The sync take-over (`takeOver(_:from:)`, split out of `adoptSyncReport`) leaves alone an existing `valid` session whose replacement carries the same login cookies (`md_user`, `md_passs`, `md_id` values, dates aside: `loginIdentity(of:)`; `md_passs` stays the same across logins, `R72`): no adoption, no check, no session change. New credentials from another device are still adopted, checked once and signalled once (#1231). Nothing in HFRKit changes.

Round 1 (`40391f5e`):
- The login identity is the values of `md_user` and `md_passs` only. `md_id` is set by the login alone (+30 days, `W03`), so a jar drops it while a copy may still list it expired, and the two never matched. `md_passs` carries any real credential change (a password change); `md_id` is implied by `md_user`.
- **Bound**: a take-over reported by this device's own write-back push (`pushOwnRefresh`) never starts another check of a `valid` account, whatever the copy holds. So no replacement, matching or not, can make a check loop.
- `remove(_:)` clears `confirmedLogins`.
- Not fixed here: the engine-side echo (#1390) and a copy dated ahead freezing the stored expiries (Fable finding 4, posted on #1390 as issuecomment-7221677106).

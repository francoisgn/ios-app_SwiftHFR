### Problem
Operator feedback of 2026-11-18: refresh a list or a topic by pulling either end, with an icon that grows with the pull, a haptic, and a refresh that fires only when the icon is full; and no end-of-page hint in the reader (#1207 and its comment).

### What exists today
- **Lists**: `.refreshable` (system `UIRefreshControl`), top only.
- **Reader** (topic and MP, `WKWebView`): no top pull; a pull past the end, released beyond 72 pt, refreshed (`ReaderPullWatcher`, #820), with the hint « Tirer vers le haut pour actualiser » (#820, #932).
- **Legacy @ 87fe0d1c**: `.refreshable` at the top of the lists only (`MainWindow.swift:791`, `Favorites.swift:747`, `MPListView.swift:625`); the reader refreshes from a bottom button (`MessagesView.swift:5051-5058`), no pull, no hint.

### Change
- **`PullRefreshRule`** (pure): icon scale = pull / 72 pt clamped to 0…1 (`PullRefreshRule.threshold`, the reader's 72 pt); fires exactly once per touch, when the icon first reaches full size **with a finger down**, and is armed again only when the finger has left, also by the pan's end when no offset moves after the lift (round 2) (round 1: a refresh resets the reader's page to its top, WebKit #642, which is no rest while the finger is still down). `PullEdgesTracker` runs one rule per end and treats a scroll without a finger as no pull.
- **Reader**: the hint is removed. `ReaderPullWatcher` observes the scroll view's offset (KVO) for **both ends** (round 1: top pull added, `-(offsetY + adjustedContentInset.top)`), feeds `PullEdgesTracker`, reports both icons' scales (`events.pullProgress` → `TopicReaderModel.pullTop/pullBottom` → two `PullRefreshIcon`s in `ReaderStateOverlay`) and calls `pulled(edge)` at the full-size crossing: haptic then `ReaderRefresh.run` (reading position kept). `TopicReaderModel.pulledEdge` is set only around a refresh that a pull started, so only that icon turns: a first load, ‹ ›, a page jump or the toolbar « Actualiser » turn none (round 1).
- **Lists**: `pullToRefresh(isRefreshing:refresh:)` (`PullToRefresh.swift`) on `TopicListView`, `MessageListView` and, since round 1, `ForumListView` (Catégories) replaces `.refreshable`: top and bottom pulls through the pure `ListPull(ScrollGeometry)`, `onScrollPhaseChange` for the finger, `PullRefreshIcon` (turns only for the end that was pulled), `HapticFeedback.live.impact(.light)`, and an « Actualiser » accessibility action.
- **Not in this PR**: `BookmarksView`, `QualityAlertsView`, `OfflineTopicsView`, `UserProfileView` keep the system pull (not named by the issue; one line each if wanted).
- **Device check (#893)**: threshold feel, the icons' position (the bottom one `padding(.bottom, 96)` above the floating bar, the top one below the navigation bar; the overlays sit outside the pager strip and banners, so check overlap), haptic, light/dark, Reduce Motion. `host: mac-helps`.

If you delete the `addTarget` line, or change `panChanged` to ignore `.ended`, every test stays green (L01). On a device, the round-2 bug would then come back unnoticed: a lift with no momentum leaves the rule disarmed. Fix: make `panChanged` internal and drive it with a `UIPanGestureRecognizer` subclass whose `state` is set through `UIGestureRecognizerSubclass`. 2. **Detail: possible double fire at a lift, `ReaderPageEnd.swift:40`.** I don't think it can happen in practice. Our target is added after UIScrollView's own pan target, and UIKit calls targets in the order they were added. By the time `fingerLifted()` runs, the scroll view has already handled `.ended`: `isTracking` is false and dragging has ended. The bounce then moves the offset on later frames with no finger down, so a re-armed rule cannot fire again for the same touch. A second refresh would need an offset event with `isFingerDown` true after the lift, which UIScrollView does not send. In the worst case, the `!model.isLoading` guard would not catch it within the same run-loop turn, because the first refresh's `Task` has not started yet.
3. **Detail: `progress(0, 0)` at the lift does not hide a running refresh.** `PullRefreshIcon` stays full size and turning while `isRefreshing` is true (`pulledEdge`), in both `ReaderStatusViews.swift:14-18` and `PullToRefresh.swift:54-57`.

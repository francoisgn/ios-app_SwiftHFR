**Problem.** `drafts.json` is keyed by `DraftContext`'s synthesized `Codable`, so case and label names are on-disk keys, and no test held a literal file. A later rename would keep every round trip green, and on upgrade each member's `drafts.json` would fail to decode and be set aside: all drafts and archived replies gone. One bad entry already set the whole file aside (`DraftStore.loadedState`, `catch is DecodingError`).

**Change.**
- **Golden v1 file** (`DraftFileFormatTests`): one draft per `DraftContext` case, with both archived sources (`quote`, `quickReply`), captured from the writer at 1b6f98f0. It covers the nested `TopicID`, `CategoryID` (`"13"`, `"prive"`) and `ArchivedDraftSource` codings.
  - `readsTheVersion1FileOfEveryContext`: the file reads back to the expected drafts.
  - `writesTheVersion1File`: the writer still produces that file, compared as parsed JSON.
- **Entry by entry**: `DraftDocument` reads its drafts one by one and counts the entries it cannot read (a newer build's context, a malformed date) in `unreadableEntryCount`. When there are any, the store:
  - copies the file as it was aside, byte for byte (`drafts.json.corrupt`, same rotation as a quarantine, never deleted, and not copied again if `.corrupt` already holds these bytes);
  - writes the readable drafts back and loads them;
  - tells the member once (`didRecoverFromCorruptData`).
- **Safety**:
  - If the copy or the write fails, writes stay blocked, as for an I/O failure, so no save can drop an entry that was not set aside.
  - `DraftPersistence.backUpUnreadableData()` refuses by default. `FileDraftPersistence` copies, and `InMemoryDraftPersistence` is an explicit no-op.
- **Unchanged**: a file that is not a draft document at all, or a newer version, is still set aside whole, as before.
- **`page`**: it stays in `.reply` because it is in the key and in the v1 file. A comment says the app always writes 1.
- **Explicit `DraftContext` coding**: not done. The synthesized coding is the v1 format, and the golden test pins it. A comment says a format change needs a new `currentVersion` with a migration on read.
- **Docs**: LOT-063 §Format is updated. LOT-157 now says the drafts' `.corrupt` copies keep an erased account's texts, as every store's set-aside data does.

**Tests** (HFRKit, run on Linux):
- `anUnreadableEntryIsSetAsideNotTheFile` and `aBadDateIsOneUnreadableEntry` were red before the change (the file was set aside).
- `anEntryThatCannotBeSetAsideBlocksWrites`, `aPersistenceWithoutABackupBlocksWrites` and `aRetriedSetAsideKeepsOneCopy` each go red under their mutation (checked by the author and the reviewer).
- The two golden tests pass by design: they fail on any later format change.

- **Findings 1, 2 and 4.** Unreadable entries no longer live in the file. A file with unreadable entries is copied aside byte for byte (`drafts.json.corrupt`, the same place and rotation as a quarantine, never deleted). The readable drafts are then written back and loaded, and the member is told once (`didRecoverFromCorruptData`).

LOT-157 already documents that `.corrupt` copies keep their bytes ("the bytes stay in the `.corrupt` copy"), and the account deletion does not erase them. That is an existing property of every quarantine, not new here.
  - `DraftPersistence.backUpUnreadableData()` has a no-op default for in-memory stores and test doubles.

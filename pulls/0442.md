**Problem.** FEAT-013 asks for a preview of a draft "exactly as HFR will render it". The legacy app has no preview; the issue leaves the module (HFRParsing or app), the input/output, the fidelity rule and the security model to an ADR, to be merged before any code.

**Decision (ADR 0014).** A local, pure `BBCodeRenderer` in `HFRParsing` that follows **HFR's own rendering model**: the text is rewritten tag by tag into the HTML string HFR writes (one shape per tag, each proven by a captured pair; crossed tags come out crossed, as HFR writes them), and that string is parsed **on the reader's own path, twice as the reader does** (inside the thread page's markup, serialized back as `MessageBlockParser.contentHTML`, then `MessageContentNormalizer`, the sanitizer of record), so the preview gets the same tree-builder repairs, the same sanitizer and the same display stack as the posted message (`TopicHTMLBuilder`, `ReaderWebController`: `hfrreader:` scheme, CSP `script-src 'none'`, images through the cookie-less client and policy C). Everything no pair proves is text, as HFR does with `[color=]`, `[list]` and an unclosed tag. Fidelity is measured by differential tests against HFR's own rendering on five pairs: run 9's `/apercu.php` (`W61`/`R95d`, `W62`/`R95h`) and the quote prefills of the LOT-001 corpus against the thread page (`R41a`/`R42`/`R41b` → `R20`), which settle smileys, the toolbar's colour syntax `[#RRGGBB]`, crossed tags and one whitespace rule.

**Operator choice O-1** (in the ADR with what each option shows otherwise than HFR, recorded on #189): FEAT-013 says "exact" and no local renderer is exact by construction. (a) local renderer labelled as a preview (recommended now), (b) local renderer plus an on-demand "aperçu HFR" calling `/apercu.php` (a later `HFRClient` lot; recommended if users report differences), (c) `/apercu.php` only. **Decided 2026-11-02: (b)** (#189); the `/apercu.php` flow is LOT-184 (#449, M5), opened by this PR.

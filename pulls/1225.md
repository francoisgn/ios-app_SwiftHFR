### Problem
In the « Aller à la page » alert (topic and MP list pagers), an out-of-range or non-numeric entry was dropped silently: « Aller » closed the alert with no move and no message; the range lived only in the placeholder, which disappears on the first digit (HIG › Text fields; operator note on #1154, 2026-11-19: refuse any value out of range and keep the alert open). Legacy clamps and says « Choisir une page entre 1 et N » (`HFRswift/Swift/Common.swift:3104-3105, 3130` @ 87fe0d1c).

### Cause
`PagerPageMenuPill`'s alert button called `menu.page(fromEntry:)` and did nothing on nil; SwiftUI closes an alert for any button, so the refusal was invisible.

### Change
- `PagerPageMenu.canSubmit(entry:)` (same rule as `page(fromEntry:)`) disables « Aller » while the entry is not in `1...total` (any page ≥ 1 when `total` is only a lower bound): the alert cannot be submitted wrong, so it stays open.
- `PagerPageMenu.entryMessage` puts the range in the alert's message: « Choisir une page entre 1 et N » (legacy's wording), or « Choisir une page à partir de 1 (au moins N pages) » for a lower-bound total.
- No other behaviour changes: `page(fromEntry:)` is untouched.

### Tests
`PagerPageMenuTests` (written first, fail to compile without the change): `theGoButtonIsOnlyOnForAnEntryInRange` (8, 12, 1 on; 0, 13, 9999, « huit », empty, blank off) and `theAlertMessageStatesTheRange` (exact and lower-bound totals). The SwiftUI wiring (`.disabled`, `message:`) is two modifiers: device check on #893 (type 9999 on a 12-page list: « Aller » dimmed, message shown). Not run here (Linux); `compile-check` runs on the head.

1. **Low**, `App/SwiftHFR/Navigation/PagerPageMenu.swift:94`: the fix depends on SwiftUI updating `.disabled` on an alert button as the `TextField` binding changes, and it can't be checked on Linux. If iOS 27 reads the disabled state only once, when the alert opens, the result is wrong both ways. « Aller » stays dimmed after typing a valid page, because the entry starts empty. Or, if the button ignores it, typing 9999 on a 12-page list closes the alert with nothing done again. Legacy disables a toolbar button in a sheet (`Common.swift:3208` @ 87fe0d1c), not an alert action. Fix: none in code. The #893 check must go both ways: « Aller » dimmed on 9999, then enabled after typing 8; also the hardware-keyboard Return key on an invalid entry.
2. **Low**, `App/SwiftHFRTests/Navigation/PagerPageMenuTests.swift:57-63`: `canSubmit` only wraps `page(fromEntry:)`, whose refusals (0, above total, letters) the existing test already covers. The new test fails without the change only because it doesn't compile. Removing `.disabled` or `message:` from the view leaves every test green, so the regression in #1154 has no automated guard (L01). Fix: say so on the PR and rely on the #893 check, or add an app-hosted or UI test if one is cheap.
3. **Detail**, `PagerPageMenu.swift:36`: entries are trimmed with `.whitespaces`, while legacy uses `.whitespacesAndNewlines` (`Common.swift:3101`). So a pasted "8\n" is refused. It is refused visibly now, so this is not blocking. Fix: trim `.whitespacesAndNewlines`.

The rest is consistent with the operator note:
- An out-of-range entry is refused and the alert can't be submitted.
- When the total is only a lower bound, any page from 1 is accepted, as before, and the message says so.
- « Choisir une page entre 1 et N » matches legacy at `:3130`.
- Edge cases: "+8", "008" and " 8 " are accepted as 8. 20-digit overflow, "٨", "１２", "-0" and "8.0" are refused.
- The only caller is `PagerToolbar.swift:85`, which uses the same semantics.

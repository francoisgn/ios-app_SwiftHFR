### Problem
A one-to-one MP row whose correspondent was never read since the install shows initials even when the member has an avatar (operator device feedback, #714).

### Cause
The avatar cache is filled only from the pages read (`AvatarStore`, GAP-230), and legacy's MP rows only read that cache (`MPListView.swift:893-930` @ `87fe0d1c`): nothing asks HFR for a member who never appeared in a page read.

### Change
- **Engine** (`HFRNetwork`): `HFREndpoint.profileRedirect(pseudo:)` is the row's `profilebdd.php?config=hfr.inc&pseudo=<pseudo>` link, sent **without following** the redirect; `HFREndpoint.memberID(inProfileRedirect:)` reads the id only from a 3xx whose `Location` is `/hfr/profil-<digits>.htm` on `https://forum.hardware.fr` (`R716a`, `R716c`); an empty id (`R716d`, unknown pseudo) or anything else is nil, so an unknown member costs one request. `PageFetcher.memberID(pseudo:as:)`, **anonymous by default**.
- **No session cookie**: the captures prove the route does not need one (`R716c` without cookies answers as `R716a` logged in; the profile page is read logged out in `R56a`/`R56b`, and `LiveUserProfileSource` already reads profiles cookie-less and only at `/hfr/profil-<id>.htm`).
- **App**: `MemberAvatarPrefetcher` (one per session, in `AppEnvironment`, nil when logged out), reached by `MessageAvatarView` through an environment value. When the cache read misses for a one-to-one row, the row's `.task` asks it; it looks the member up (`LiveMemberAvatarLookup`: redirect, then `UserProfileParser` through `LiveUserProfileSource`) and hands the avatar URL to `AvatarStore.offer`, which keeps its rules (forum image host, no cookie, no redirect, 256 KiB, decodable image, 24 h). The store's write bumps the generation, so the row reads the new file.
  - **Only visible rows**: the request lives in the row's `.task`; a row that leaves the screen before its turn gives it away untried and is asked again when it shows.
  - **Never twice in a row**: one lookup at a time, at least 1 s apart (each lookup is two page GETs); each pseudo (case-insensitive) is tried at most once per session, whatever the outcome (no avatar, unknown member, failure).
  - Any cache entry (even stale) skips the lookup: the row shows it and page reads refresh it.
- **Fallback**: unchanged, the monogram when no avatar is found.
- `docs/HFR-PROTOCOL.md` §6c "#714": the client's use, and a non-ASCII pseudo as not captured.

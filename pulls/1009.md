## Problem
SwiftHFR kept the `2440d79` timeouts (30 / 60 / 15 / 5 s) as a **total** limit; legacy 4.0.x at `2fe43da3` uses 10 s as an **idle** limit (`ae196aa0`), so a stalled page gave up after 30 s instead of 10 s, and a slow page that keeps receiving would have been cut by a 10 s total limit.

## Cause
`HTTPRequest.timeout` was enforced by `URLSessionTransport.withDeadline` around the whole exchange (a total limit, on every platform); swift-corelibs ignores `timeoutInterval`.

## Change
Operator decision of 2026-11-16 on #683: as legacy.
- `HTTPRequest.timeout` is now an idle limit; new `HTTPRequest.totalTimeout` (default nil) caps the whole exchange. Presets: standard 10, topic search 10, global search 10 idle + `globalSearchTotal` 10, background 5 s (`Classes/Constants.h:70-72`, `Classes/ObjCForumSearchWorker.m:8,131-132` @ `2fe43da3`). Global search endpoint and flow set both.
- Apple platforms: `URLRequest.timeoutInterval` already is an idle limit; the total deadline only runs when `totalTimeout` is set. Linux (corelibs): a per-request session delegate sees each chunk (`countOfBytesReceived` stays 0 while a body streams, measured) and fails with `timedOut` after `idle` seconds without data; a watcher sleep as long as the limit counts as a stalled process, not an idle network. The owner session's delegate still decides followed redirects (LESSONS 30: `HFRSessionTests.redirectLeavingTheAllowedHostIsNotFollowed` caught the first version dropping it).
- App: `TopicReaderModel.waitLimit` was derived from `RequestTimeout.standard`; it covers the fetch **and** the web view (#750 operator decision, 30 s), so it is now its own 30 s value instead of silently becoming 10 s (test updated). Not changed: the reader's error state already says « timeout » with « Réessayer » (#750).
- Docs: LOT-040 and `docs/HFR-PROTOCOL.md` timeouts.
- Not changed: no new dependency; no device measurement was possible from the cloud (the presets are the operator's decision, not a measurement).

## Tests
Loopback server (real sockets). `swift test` on Linux: 2083 tests, 0 failures (the suite freezes ~55 s as on `dev-swift`, measured on its head).
- `slowButFlowingAnswerIsNotCutByTheIdleLimit`: red before the change (`timedOut` at 0.8 s while data flows), green after.
- `answerThatStallsAfterItsFirstBytesFailsAtTheIdleLimit`: shown to fail without the watcher (transport error when the server closes at 20 s).
- `totalTimeoutCutsAnAnswerThatKeepsFlowing`, `presetsAreLegacyAt2fe43da3`, `HFREndpointSearchTests` (`totalTimeout`), `GlobalSearchFlowTests` (both requests 10 s / 10 s), `HFRSessionTests` (redirect refusal kept).
- App: `TopicReaderModelWaitTests.theWaitLimitIsIndependentOfTheRequestTimeout` (compile-check only, no Mac).

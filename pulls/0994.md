## What and why

**Problem.** SwiftHFR had no background MP check, no local notification, no app icon badge and never asked for notification permission (operator's UI comparison of 2026-11-11 on #230). Legacy runs `BGAppRefreshTask` `com.hfrplus.refresh_mp` and posts one fixed text when the home count rises (`MPBackgroundService.swift` @ `87fe0d1c`).

**Change** (spec: `docs/lots/LOT-140-background-mp-check.md`):
- **Engine.** `MPNotificationPlan` (HFRClient, pure): one notification per conversation with news, text from the MP list row (one-to-one: interlocutor / title; group: title), identifier and thread identifier `mp-<topic>`, more than 5 → one summary. `MPCheckInterval` + `SettingKey.mpCheckInterval` (`mp_check_interval`, device-only, default 30 min).
- **Check** (`MPBackgroundCheck`): Jamais / no account / ledger interval guard (`markCheckedIfDue` with one minute of slack, shared with LOT-141) → nothing sent. Then `MPUnreadPoll` (LOT-047) and MP list page 1 on a session built from the stored cookies and written back nowhere; `nil`, expired or failure → nothing notified, recorded or badged. `recordNews` (LOT-091) gives the news; the legacy text (`mp-legacy`) only when the list could not be read and the count rose from a recorded one; badge per `mp_badge_enabled`. Max 2 requests, never a thread page.
- **Scheduling.** SwiftUI `.backgroundTask(.appRefresh("com.hfrplus.refresh_mp"))`; `earliestBeginDate = now + interval` via `submitTaskRequest`, scheduled on background, at each run and on a setting change; Jamais cancels. `Info-Keys.plist`: `BGTaskSchedulerPermittedIdentifiers` and `UIBackgroundModes` `fetch` only (legacy also had `processing`, unused).
- **Permission** at launch, as legacy (`HFRswiftApp.swift:27-29`); category `mp` with `hiddenPreviewsBodyPlaceholder` "%u nouveaux messages privés"; `.active`, sound default.
- **Tap**: `AppDelegate` is the `UNUserNotificationCenter` delegate (main-actor conformance) → `MPNotificationRouter` → the root selects Messages and `MessageListModel.open(topic:)` reloads page 1 and opens the conversation (its segment in "Deux listes"); a summary loads page 1.
- **Foreground**: the icon badge follows the Messages badge; counts HFR announces on list pages, and page 1's unread set as shown (after the newest load, a read, a mark unread), are recorded in the ledger, so what the app showed is not notified later and a reply to a conversation read here is (LOT-091 rule, legacy `HFRplusAppDelegate.m:706`).
- **Réglages › Notifications MP**: "Badge messages non lus" (legacy), "Vérifier les messages" (15 min…4 h, Jamais), the operator's footer, « Dernière vérification », « Réglages des notifications ».

**Not in this PR (pending #571).** A new reply in a conversation that is already unread only moves `repliesCount` and the last-post date (R336→R338, HFR-PROTOCOL §6c LOT-140); the LOT-091 ledger keeps only the unread set, so that reply is not notified until #571 adds the per-thread watermark. The plan reads `NotificationNews.newThreads` only, so #571 needs no change here. The #230 acceptance line "a reply in an already-unread conversation produces a notification" closes with #571: the orchestrator decides whether this PR keeps `Closes #230`.

**Device check** (BGTask via `e -l objc -- (void)[[BGTaskScheduler sharedScheduler] _simulateLaunchForTaskWithIdentifier:@"com.hfrplus.refresh_mp"]`, cold-launch and background taps, locked/unlocked texts, Show Previews = Never) goes to the general review list on #893.

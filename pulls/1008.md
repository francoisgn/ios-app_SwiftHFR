**Problem.** A tap on a member's avatar or pseudo showed the author menu (« Post de <pseudo> ») as a panel in the top-left corner over the title bar, far from the tapped post, while the « + » menu of the same post opens as the system's horizontal callout at the tapped spot.

**Cause (not reproduced here: Linux session, no simulator).** The author menu was a SwiftUI `popover` attached to a 1×1 `Color.clear` view that an overlay positions at the tapped rectangle (`ReaderMessageMenuAnchor`). The observed top-left placement means the popover took its anchor at the origin; the likely reason is that it resolves its anchor when the item is set, before the clear view has moved to the new rectangle. Either way it is a fragile way to anchor, and the « + » menu does not use it: it is a `UIEditMenuInteraction` on the web view (#594), fed the rectangle the bridge reports.

**Change.** The author menu now goes through the same callout: `showMessageMenu` presents any menu the model holds (message or avatar) with `ReaderMessageEditMenu.placement(of: anchor, topInset:, in:)`, so it opens above the tapped pseudo or avatar (below it within 40 pt of the bars), pages with « › » when long, and falls back to the right edge under the bars (never the top left) without a usable anchor. The popover view `ReaderMessageMenuAnchor` / `MessageMenuList` and its overlay in `TopicReaderView` are deleted. Entries and the action each runs are unchanged (`model.perform`). The callout shows the entries as a horizontal list with their icons; a vertical list is not kept (the issue allowed the system callout).

**Check of the note on #652 / #953.** A tap on the author of a post with a profile link opens the profile directly (`requestMenu` returns the menu for « Profil »); the author menu shows only for a post without one. That path is untouched: I found no second bug there (`TopicReaderModel+Menu.requestMenu`).

**Tests** (fail without the change): `ReaderMessageEditMenuTests.theControllerShowsBothMenusAsACallout` — an avatar menu with an anchor becomes `messageMenu.shownMenu` and its callout target (`shownTarget`, new read accessor) is the rectangle the bridge reported; on `dev-swift` `showMessageMenu` refused any non-message menu (the old test asserted exactly that). The placement rule itself (`placement(of:)`) was already tested and is unchanged. SwiftLint `--strict` clean. App tests not run (Linux).

**Device-check points** (for #893)
- Tap a pseudo and an avatar on a post **without** a profile link (the author menu only opens there): the callout opens at the tapped spot, above it, never in the corner; entries MP / Blacklist / Whitelist.
- Near the top bar: it opens below. Landscape, iPad, pinch-zoomed page.
- The « + » menu is unchanged.
- The horizontal callout has no « Post de <pseudo> » header (a `UIMenu` title is not shown by it): check what VoiceOver reads on the callout.

## Problem
Some topics stay on "Chargement des messages" until "Actualiser" is pressed. The operator's example is a large topic: Catégories → Apple. MPs are not affected.

## Cause (checked at `81d78b3`; the #566 analysis was made at d4b15a8, and this code path has not changed since)
- 🔴 **H1, confirmed.**
  - `TopicReaderView.onDisappear` calls `controller.stopLoading()`, which calls `webView.stopLoading()`. This aborts a page navigation that has not reported `ready` yet.
  - When the same view comes back, `ReaderWebController.show()` skips the document because its token is unchanged.
  - `model.onAppear()` also returns early, because `page != nil`.
  - Nothing reloads the page: the reader is stuck in state B (`page != nil`, `readyToken == nil`).
  - `FilteredPostsView` has the same pattern.
- 🔴 **H1b, confirmed.**
  - The model is shared through `NavigationModel.reader(for:)`. Fable notes that the sharing happens on size-class changes and tab switches; the `.id` replacement gets a new model.
  - B's `onAppear` sees `isLoading` and returns, then A's `onDisappear` calls `model.cancel()`.
  - The result is state A: no page, no load, no error. The old test `aCancelledLoadNeverDelivers` asserted this idle end state as the expected one.
- 🟠 **H2, confirmed.** There was no `didFail` / `didFailProvisionalNavigation` handler.
- 🟠 **H3, confirmed.** An unrequested `.failure(.cancelled)` hit a `break` and left the reader in state A.
- 🔴 **Content-process crash before `ready`** (found by Fable): the reader reloaded the page unconditionally. A page that kills the process every time therefore looped on the spinner.

The Mac trace below will show which of H1 and H1b happens on the operator's device. This PR fixes both.

## Change, and why this wide
- **`ReaderWebController`**
  - It records the token that reported `ready`.
  - `stopLoading()` forgets a document that never became ready, and leaves the controller **stopped**. While stopped, `show()` does nothing, so a re-render of the hidden view (for example #540's `isSelectedRootTab` flip) cannot restart the load it just stopped.
  - `resume()`, called from `onAppear` before `show`, clears the stopped state.
  - It remembers the shown page's `WKNavigation`.
  - A failure of that navigation before `ready` goes through `retryOrReport`: one reload, then `Events.failed(token)`. A **content-process crash** before `ready` follows the same rule. A document already shown is reloaded plainly.
  - Failures of other navigations (refused links, stopped or replaced documents) are ignored.
  - There is no "same token → reload" branch in `show()`: after a reported failure it would loop, and `WKWebView.isLoading` changes asynchronously after `load()`.
  - File moves, code unchanged, to keep `file_length` within limits:
    - the navigation delegate and the proxies go to `ReaderWebController+Navigation.swift`;
    - the reader scripts go to `ReaderWebController+Scripts.swift`;
    - the scheme handling goes into a same-file extension.
- **`TopicReaderView` and `FilteredPostsView`**
  - `.onAppear { controller?.resume(); controller?.show(…) }`.
  - A retry replaces the spinner when the web view cannot show the document.
  - The top banner only appears once a document has been shown.
- **`TopicReaderModel`**
  - `onAppear(viewer:)` records the view that appeared last, unless its `.task` is already cancelled. `viewDidDisappear(viewer:)` cancels only for that view.
  - An unrequested `.cancelled` is fetched once more (when `!Task.isCancelled`); a second one becomes `.other`.
  - `documentDidFail(token:)` sets `.other` and resets `readyToken`, so the full-screen retry shows. Only the same token becoming ready clears that error, and a new load takes the error over.
  - #108 still holds: a superseded or cancelled load never delivers. `aSupersededLoadNeverDelivers` and `aCancelledLoadNeverDelivers` are unchanged.
  - `swiftlint:disable file_length`, with the same justification as the existing `type_body_length` disable.
- **`ReaderLog`**: `#if DEBUG` only. It logs numbers, tokens and booleans, nothing else.
- No CHANGELOG-LEGACY row: legacy shows the page, and this restores it.

**Clear the `documentDidFail` error when the same document later reports ready.**

`documentDidFail(token:)` sets `error = .other` for the current document. Nothing clears that error if the same document later loads.

Trigger path:
1. The document fails twice, and `error` becomes `.other`.
2. The user leaves the reader, for example by switching tabs.
3. `onDisappear` calls `controller?.stopLoading()`. The controller forgets the unready document.
4. The user returns. `.onAppear { controller?.show(model.document) }` loads the same document again.
5. The load succeeds, so `documentDidBecomeReady(token:)` sets `readyToken`.
6. `model.onAppear` does not reload, because `error != nil`. `error` stays `.other`, and `hasShownDocument` is now true.

Result: `LoadFailureBanner` shows over a page that loaded correctly. The user sees a false "Chargement impossible".

Do not clear `error` unconditionally in `documentDidBecomeReady`. A failed refresh error must survive a content-process reload of an already shown document. Record which token failed, and clear `error` only for that token.

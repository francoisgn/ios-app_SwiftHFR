## Problem
The first daily dry run proposed to unblock LOT-161 (#251): its dependencies are merged and its `### Blocked by` section says "none". But after #382 merged, the claim holder gave the claim back and re-labelled the issue `status: blocked` by comment, on the operator's version/build decision and signing assets. `--apply` would have undone that.

## Cause
The sweep only knew labels and the body; a decision recorded in a later comment is invisible to it.

## What changed
Before proposing an unblock, the sweep reads the issue's comments: one posted after the merge of the credited PR that says `status: blocked` or `blocked on/by/until/pending` turns the action into a report ("left as is"). A note older than the merge is ignored.

## Tests
`test_a_later_comment_saying_blocked_keeps_the_lot_blocked` (late note: no action and a report; early note: still unblocked). Suite: 52 tests OK. On the live tracker the dry run now proposes 0 actions and reports #251.

**Retained concerns**
- **Low · security · inferred:** The new unblock gate treats every API-visible matching comment as a blocker without checking commenter authority. If non-operators can comment, they can suppress automatic readiness for otherwise eligible blocked lots across repeated runs. This is a bounded workflow veto, not permission to mutate labels, execute code, or access signing assets; actual non-operator exposure remains unverified.

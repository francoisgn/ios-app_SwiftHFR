## What and why

### Problem
roger21 publishes the AQ server (`roger21/toyo`, `aq/`) and the reference userscript (`roger21/hfr`), and confirmed the `aq/` code is what runs in production (#573). Our docs still said the create answer was not captured, that legacy lost accents, and that the AQ list format was unverified; and we had no rule for using third-party source code as a protocol source.

### Change
- **HFR-PROTOCOL §8**: the `aq.super-h.fr` row says create verified (`T50`, `T51`) and refusals captured on a local instance only (`T52`-`T71`); a new paragraph "server source (secondary, not a capture)" records the `addAlerte.php` contract (fields, `from`, order of checks, codes `1`/`-1`/`-2`/`-3`/`-4`, the two empty-body 403 and the empty-body 200 of the anti-flood with its deletion and ban), the unique keys and column limits, what the server stores and e-mails (hashed IP under a published key), the list and feed parameters, and how the reference userscript calls it. roger21's points 1, 2 and 4 (source = prod, `from=SwiftHFR`, load) are recorded.
- **Stale claims**: LOT-055 and LOT-071 no longer say legacy lost accents (it percent-encodes from UTF-8 before the ASCII conversion, `MessagesView.swift:389-396`, `:434-437` @ `2440d79`; same code at `2fe43da3` `:391-398`, `:436-438`); LOT-055's pending-capture line points to the captures; LOT-071 T3 and N1 mention the `from` field, the recoverable IP hash and the operator's e-mail; `AQAlert.swift:1` cites `T02` instead of "unverified".
- **ADR 0015** (Proposed): third-party open-source code is a secondary source cited `repo@SHA:file:line`, facts only and never code or data, captures stay the oracle, source-only states handled on the safe side, refusal states may come from a local instance at a pinned SHA, a third-party server in CI needs its own ADR.

## What and why
**Problem.** The captures of #285, #355 and #830 are merged. The REST client still asked for page 1 only, treated every failure the same way, opened a bucket row at its last page and had no sub-category reader, which LOT-168 (#286) needs.

**Change** (HFRClient only, no UI, no new HFRModels type):
- `RESTBrowsingClient.subcategories(in:)` reads `R285a-c`: every sub-category in order, as a `ForumLink` whose path is the list filtered on its `subcat` (`R603d`'s query, `ForumCatalogue.topicListPath`). The answer has no slug, so no `/hfr/<cat>/<slug>/` path is built. Fallback: that category's sub-forums on the home page.
- `lastTopics(in:page:)` requests page n the way `R57e` was captured (`page` alone; page 1 unchanged, `R57b`). The navigation is exact: ⌈`results_count` / `results_per_page`⌉, and `R57g` shows that the page after it is empty. A page past the last is returned empty. An empty page inside the count is refused. There is no HTML fallback after page 1: an HTML page holds 50 topics and a REST page 25, so no HTML page holds REST page n.
- Error answers (`R57i`, `R57k`: 200, `error_code` in the body) become `refused(code:)`. That is a fallback reason, or a `RESTBrowsingError` when there is no fallback. The unknown-topic placeholder (`R57j`) is `.notFound`.
- Bucket rows, from the #830 run observation (HFR-PROTOCOL §6c LOT-057 "Resume point" / "Read state"):
  - `is_read` false: `flagPath` = page ⌊`last_position` / `postsPerPage`⌋ + 1, capped at the last page, plus `#t<last_post_read_id>`, and `readState` `.unread`.
  - `is_read` true: no flag link, the row opens at its last page, and `readState` `.read`.
- `R830t`: the stale session's `.hop` page on the REST answer is `.sessionExpired` at once, under `FlaggedTopicsPoll`'s rule. If a login landed meanwhile, the answer gets no verdict and the client falls back.
- The JSON DTOs move to `RESTDocument+JSON.swift` (SwiftLint file length). A type-mismatch field is now named in snake case like every other field (`is_read`, not `isRead`).
- Spec: the two details from the Fable review of #873 are reworded (paging is captured; the sub-category mapping is no longer "pending #285"). HFR-PROTOCOL §6c LOT-057 gets one line on what the client reads.

**Caveat for the reviewer.** The resume point and read state rest on a run observation. The raw captures stay unpublished, and position aliasing hides the tie in the published files. So the decoder is tested on the published rows and on edited ones, not against a flags-page row of the same topic. Both the spec and the code say so.

Item N2 of #1394 (category lists opened by id) is split into #1428: it needs its own pager rule, and what HFR serves for a canonical list page past the end is not captured.

## What and why
- **Problem**: every page change, refresh and post-reply reload in the reader went through `forum2.php?…&page=N`. HFR answers that with one 301 (two when the topic has a sub-category) before the page (R5, `R24`). The #1388 runtime pass measured each hop on a **new TCP+TLS connection**, because HFR closes it after a 301. A linked topic took 3 transactions and 3 handshakes, 2028 ms.
- **Cause**: `ReaderTarget.atPage` rebuilt the id form, although the canonical URL of the shown page was known (`ReaderPage.pageURL`). Legacy rewrote `_N.htm` in the topic's own URL instead (`TopicPageURLRouting.replacingPage`, `HFRswift/Swift/Common.swift:2818-2834`, used by `MessagesView.urlForPage`, `MessagesView.swift:3438-3444` @ `87fe0d1c`).
- **Change**:
  - **Engine**: `HFREndpoint.topicPage(topic:page:servedAt:)`. When `servedAt` is a canonical page of the same topic on the forum origin, it asks for that path with the page changed, with no query and no fragment. `PageFetcher.topicPage` passes it through. A canonical page here means:
    - the origin is `https://forum.hardware.fr`, with no port, user info or password;
    - the whole path has the R5 shape `/hfr/<forum>[/<sub>]/<slug>-sujet_<post>_<page>.htm`, written as HFR serves it: lower case, the topic number as written;
    - no `.` or `..` segment, encoded or not.

    Any other URL falls back to the old `forum2.php` request.
  - **App**:
    - `ReaderTarget.servedPage` is set only from a served page (`TopicReaderModel.finish`, `loaded.pageURL`) and kept by `atPage`.
    - `refresh` now goes through `atPage`.
    - `LiveTopicPageSource` hands the served page to the fetcher.
  - **Unchanged**: these stay on `forum2.php`:
    - the first open;
    - message links (`numreponse`, R25);
    - the quote view;
    - private conversations, which HFR serves in place at `forum2.php` (`R388a`).
- **HFR facts used** (captures only):
  - the canonical path is served in place: `R298a`'s last hop;
  - a canonical page past the end gets a 302 to the last page: `R24`'s third hop (`…_2202.htm` → `…_2201.htm`), which the reload after a reply relies on;
  - an outdated slug gets a 301 to the current one (`R298e`).
- **Docs**: the HFR-PROTOCOL §6 "URL building" line, LOT-041 and the `topicPage` doc comment no longer say the canonical path is never requested.

| Scenario | Round trips before | After |
|---|---|---|
| Next page / refresh | 2 (3 with a sub-category) | 1 |
| Reload after a reply (`max + 1`) | 3–4 | 2 (canonical → 302 → last page) |
| First open of a topic | 2–3 | 2–3 (unchanged) |

**Problem.** Fable's round-3 review of #950 (APPROVE) left three findings on #908:
1. (Low) The task queued by the last composer closing (`owedTask`) captured the owed follow-up and ran it without checking again. After a reply is sent, the reply sheet's own reload starts in the same turn. A stale edit reload owed from an earlier disappearance could then run afterwards and cancel it: the page reloaded at the edited message and the reply was not shown.
2. (Low, L01) No test stopped the second load of a conversation reply: `settles: followUp == nil` → `true` kept every test green. The `isOnScreen` and `!isLoading` guards were untested.
3. (Detail) The doc comments and the LOT-083 spec said the owed reload runs when the screen comes back; it also runs when the last composer closes.

**Cause.** `composer(_:isOpen:)` checked its conditions only when the composer closed and handed the captured value to a task. The main actor then runs that task after anything started in the same turn.

**Change** (`TopicReaderModel` only):
- One predicate, `canRunOwed` (on screen, a page shown, nothing loading, no composer open), is used both when the composer closes and when the task runs.
- The task now calls `runOwedIfStillDue(_:)`, which returns unless `owedFollowUp` still equals the captured value and `canRunOwed` still holds. A nil, changed or superseded follow-up does nothing.
- Doc comments (`owedFollowUp`, `runOwed`) and `docs/lots/LOT-083-topic-reader.md` (edge cases) are updated. Nothing else changes: the screen-return path (`onAppear`) already checked live state.

**Tests.** The new suite is `TopicReaderOwedReloadTests`. The `TopicReaderWriteFollowUpTests` fixture moved to file scope (`followUpFixture`) so both suites share it.
- `aStaleOwedEditDoesNotCancelTheReplysReload` (topic, conversation): an edit reload is owed, the reader comes back under an open reply composer, and the reply is sent. The order is deterministic: `composer(.reply, isOpen: false)` queues the task, then `composerDidClose` starts the reply's reload in the same turn, before the test's first suspension. Expects the last page at the reply and nothing owed.
- `aConversationReplyStoppedBeforeItsSecondLoadStaysOwed`: the page-4 (`max + 1`) request is gated, then the reader disappears. Expects `owedFollowUp == .latestPost` and page 4 on return.
- `aConversationReplyStoppedBetweenItsTwoLoadsStaysOwed`: the reader disappears right after the first load delivers and before the second starts. An observation on `page` fires synchronously inside `finish`, after the settle. Expects no page-4 request, `.latestPost` still owed, and page 4 on return. This test catches `settles: true`. The gated test does not: the second load passes `followUp` again and owes it again.
- `aComposerClosingOffScreenLeavesTheReloadOwed` (topic, conversation): the `isOnScreen` guard.
- `aComposerClosingWhileTheOwedReloadRunsStartsNoOther` (topic, conversation): the `!isLoading` guard. Only the owed reload is gated, so a second reload cannot hang the test.

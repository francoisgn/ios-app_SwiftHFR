## Cause
#1009 made `HTTPRequest.timeout` an idle limit for every request, but did not follow the callers and docs that still described a total limit or the old values, nor say what happens to images.

## Change
1. **Images** (Low): reader images (`ReaderImageFetcher`) and third-party image hosts (`ImageHostTable.request`) take `RequestTimeout.standard`, so they now follow the 10 s idle limit. Choice named in LOT-040: no legacy trace covers them (legacy loads images in the web view), so they get no value of their own; an image host that waits more than 10 s before its first byte now fails.
2. **Wording** (Low): « idle limit » in `GiphyClient.swift:10`, `RehostClient.swift:12` (legacy `ReplyService.swift:1992` @ `2440d79` sets `timeoutInterval`, an idle limit, so the 60 s upload matches legacy) and `docs/lots/LOT-056-image-hosts.md:40`.
3. **LOT-047:63** (Detail): « the 30 s page default » is 10 s.
4. **Linux upload** (Detail): one comment on `dataWithIdleLimit`: only received bytes count there, so a request body that takes longer than the limit to send fails on Linux, which Apple's `timeoutInterval` does not do; the Linux build does not ship.
5. **Round 1** (this PR's review): LOT-041 (global search « 15 s », topic search « 60 s ») and LOT-046:34 (« 15 s ») now give the #683 values. GAP-750 is not touched: its `gap-edit` is in the `### Ledger` of #1009, which the steward folds.

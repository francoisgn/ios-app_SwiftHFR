## What and why

**Problem.** A plain YouTube link in a message is a bare underlined URL, and a tap opens it in the in-app Safari view (operator feedback, 2026-11-17, #1037).

**Cause.** The reader only builds LOT-108 player placeholders for LOT-035 embeds; every other link is plain text routed by `HFRLinkRoute` to `SFSafariViewController`.

**Change.**
- `YouTubeLinkDetector` (HFRParsing): `youtu.be/<id>`, `youtube.com/watch?v=<id>` (`www.`, `m.`), `youtube.com/shorts/<id>`; `t=` start via the LOT-035 parser; ASCII ids, no port, no user info. A card is for an `a.cLink` that holds text only, whose text is its own address (or HFR's shortened `<start> [...] <last 10 characters>` form, captures R20, R21, R27; a named link stays a text link), outside any table (quote, spoiler, code), and that LOT-035 does **not** turn into a player. Channels, playlists, handles and look-alikes are not videos.
- `TopicHTMLBuilder` adds a card under the message text (the link stays), with the address as posted. It reads as the pill « Vidéo YouTube · toucher pour lire » until `reader.js` has the thumbnail `https://i.ytimg.com/vi/<id>/hqdefault.jpg` (operator decision, option 2 of #1037; de-facto form, not documented by YouTube, recorded in HFR-PROTOCOL §6c with a header capture and in LOT-071 T9). The thumbnail is an ordinary image of the page: policy C, cookie-less client, no `Referer`, `RequestTimeout.standard`. Refused (images on tap), failed or late: the pill stays.
- Tap on the card, the pill or the message's own text link of that address: new bridge message `videolink`; the app re-parses the address and opens it over `https` as a universal link only, then Safari (`ReaderLinkMenu` `.app(provider: .youtube)` path, as the long-press entry). Never `SFSafariViewController`, a web view or the player sheet; start time kept. A same-address link in a quote or around a picture is an ordinary link. The long press is unchanged (#596).

**Decision to check (operator).** A link that LOT-035 turns into a player (`youtube.com/watch?v=` or `youtu.be`, alone in a top-level paragraph) keeps its LOT-108 placeholder and gets no card, as the issue says embeds stay unchanged. So the two never show for one link. If most plain links in real messages are such embeds, the cards will be rarer than the screenshot suggests; not measurable from here. Showing both would be a one-line change in `YouTubeLinkDetector.cards`.

**Known, left for the next push (review round 2, optional 🟢):** the tap match is by address, so when one message holds the same video twice (a player link or a named link plus a plain one), the other same-address link also opens YouTube; a shortened link text whose address ends in `/` gets no card; one stale comment. Rare, no data or security effect.

`MessageEmbedDetector` only gained a shared `isCandidate` helper; its behaviour is unchanged.

Verdict: REQUEST CHANGES

1. 🔴 `Packages/HFRKit/Sources/HFRParsing/Topic/YouTubeLinkDetector.swift:299`. The code skips every LOT-035 *candidate*. It should skip only candidates that `MessageEmbedDetector.embed(for:)` turns into an embed. Shorts are not embeds, and the embed regexes are case-sensitive. Failing case: `<p><a class="cLink" href="https://youtube.com/shorts/abc">https://youtube.com/shorts/abc</a></p>`, the usual shape of a link on its own line. It gets `cards == []` and `embeds == 0`, so no card and no player. The same happens with `https://YOUTU.BE/abc`. I confirmed both with a probe test. Fix: skip the link only when `isCandidate && embed(for: url) != nil`. Add tests for a top-level Shorts link and an uppercase host.
2. 🟠 `YouTubeLinkDetector.swift:316-325` (`isAddress`). HFR shortens the text of long auto-links to `<start> [...] <last 10 characters>`. The fixtures hold 126 such links, every one with an address of 55 characters or more, for example `https://www.leetchi.com/fr/c/hfr-ap [...] al_sharing`. A Shorts share link `https://youtube.com/shorts/<11>?si=<16>` is 58 characters, so it is treated as a named link and gets no card. A probe confirmed this. I have not seen it on a YouTube capture. Fix: accept HFR's shortened form, with the capture cited, and add a test.
3. 🟢 `reader.js:150-155`. Any anchor in the article whose href matches a card is intercepted. That includes a link in a quote or a signature, the plain link of a LOT-108 embed, and a posted picture wrapped in that link, which now opens YouTube instead of the image viewer. Fix: limit the match to `.content a.cLink` outside any `table`.
4. 🟢 `TopicHTMLBuilder.swift:185`. The card's href is `sourceURL.absoluteString`, which percent-encodes non-ASCII characters (probe: `?si=é` becomes `%C3%A9`). The DOM keeps the raw text, so the inline link no longer matches its card. A tap on it then goes through `events.link` and opens the in-app Safari view (`SFSafariViewController`), which the spec forbids. Fix: keep the posted href string on the card.
5. 🟢 `YouTubeLinkDetector.swift:237`, HFR-PROTOCOL §#1037. The docs say an id is `[A-Za-z0-9_-]+`, but Swift's `\w` matches any Unicode letter or digit, and `watch?v=%C3%A9t%C3%A9` gives the id `été` (probe). The host is still always `i.ytimg.com`. A port is also accepted (`www.youtube.com:8443`). Fix: use an ASCII character class and reject URLs with a port.

**Checked, no problem found:** the escaping of card attributes. The app checks the tapped address again, so only YouTube video links open. With a composer open (`ignoresPageTaps`), the tap is dropped. The thumbnail goes through the `hfrreader:` scheme, policy C, the cookie-less fetcher with `RequestTimeout.standard` and a 15 MB cap, and sends no Referer. Thumbnail load and error handling, and its effect on the scroll pin. Cards stay out of quotes, spoilers and signatures. The LOT-108 embed code and its tests are unchanged. No ledger path is touched.

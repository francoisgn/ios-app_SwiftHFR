## What and why

**Problem.** A plain YouTube link in a message is a bare underlined URL, and a tap opens it in the in-app Safari view (operator feedback, 2026-11-17, #1037).

**Cause.** The reader only builds LOT-108 player placeholders for LOT-035 candidates; every other link is plain text routed by `HFRLinkRoute` to `SFSafariViewController`.

**Change.**
- `YouTubeLinkDetector` (HFRParsing): `youtu.be/<id>`, `youtube.com/watch?v=<id>` (`www.`, `m.`), `youtube.com/shorts/<id>`; `t=` start via the LOT-035 parser. A card is for an `a.cLink` that holds text only, whose text is its own address (a named link stays a text link), outside any table (quote, spoiler, code), and that is **not** a LOT-035 player candidate. Channels, playlists, handles and look-alikes are not videos.
- `TopicHTMLBuilder` adds a card under the message text (the link stays). It reads as the pill « Vidéo YouTube · toucher pour lire » until `reader.js` has the thumbnail `https://i.ytimg.com/vi/<id>/hqdefault.jpg` (operator decision, option 2 of #1037; de-facto form, not documented by YouTube, recorded in HFR-PROTOCOL §6c with a header capture and in LOT-071 T9). The thumbnail is an ordinary image of the page: policy C, cookie-less client, no `Referer`, `RequestTimeout.standard`. Refused (images on tap), failed or late: the pill stays, no placeholder, no link text in its place.
- Tap on the card, the pill or the link: new bridge message `videolink`; the app re-parses the address and opens it over `https` as a universal link only, then Safari (`ReaderLinkMenu` `.app(provider: .youtube)` path, same as the long-press entry). Never `SFSafariViewController`, a web view or the player sheet; start time kept. The long press is unchanged (#596).

**Decision to check (reviewer, operator).** LOT-035 candidates (a link alone in a top-level paragraph) already get the LOT-108 placeholder and the player sheet, which the issue says stays unchanged. So they get **no** card, and the two never show for one link. If most plain links in real messages are such candidates, the cards will be rarer than the screenshot suggests; I could not measure it from here. Showing both for one link would be a one-line change in `YouTubeLinkDetector.cards`.

**Wider than the issue's wording:** none. `MessageEmbedDetector` only gained a shared `isCandidate` helper (its behaviour is unchanged, tests green).

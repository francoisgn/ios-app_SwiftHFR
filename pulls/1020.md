## What and why
**Problem.** The blocklist never reached the account's MPStorage document. LOT-130 shipped the sync loop and the consent API, and LOT-118 the local list, but nothing linked the two.

**Cause (legacy).** `BlackList.m:37-69` wrote to the forum first and dropped the local change on any failure. `MPStorage.m:202-225` (`updateBlackList:`) **replaced** the local list with the remote one, so an empty remote list emptied the device's list (audit E-2, ADR 0013 §2).

**Change** (spec `docs/lots/LOT-131-blacklist-mpstorage.md`):
- `PseudoListManager` holds each blocklist change in a per-session `BlocklistChangeLog` **before** its local write. After the write, the change is kept if the list changed and withdrawn otherwise. The log streams it to `BlocklistSyncModel.run()` (root `.task`).
- `BlocklistSyncModel.handle` follows `writeConsent(for: .ignoreList)`:
  - `.sync`: one `MPStorageSyncModel.edit(.ignoreList)`. This is the LOT-130/052 path: session check, merge-write-read back, success only on HFR's confirmation, `unconfirmed` kept pending and never re-sent blindly.
  - `.ask`: the question « Synchroniser la liste noire de ce compte avec le stockage MP … ? », then `setEnabled(true, from: .write)`. An existing thread turns the account `on`; with none, the legacy creation question is asked from the root.
  - `.deviceOnly`: nothing.
- `MPStorageSyncModel.afterSync(before, after)` runs after each successful call that found the thread, except an edit that changed nothing. That exception is decided per call (`run(_:merges:)`), never through model state, because calls overlap. `run` loads the device copy first when none is shown, so a write made before `start()` merges correctly. `BlocklistSyncPlan` then merges:
  - remote additions go to the device;
  - remote removals go to the device **only if the forum list still holds entries or carries a tombstone**: an emptied list never means "delete all";
  - device-only entries and held removals go to the document in one edit.

  Held changes win over the diff, so a removal not yet written is never imported back. They are released per pseudo, on that pseudo's last change.
- `creationPrompt` keeps the creation alert of Réglages in Réglages, and shows the one a write starts from the root (`BlocklistSyncQuestions`, also on the profile sheet). No new forum request, no new HFR fact.
- Not touched: the « MP multiples → dark topic » switch and `shippedFunctions` (#1014, cloud/i1016-sonnet).

Why this wide: the hook in `MPStorageSyncModel` is the only place where a fresh document is known. The log is needed because `PseudoListManager` lives in `AppEnvironment`, which is built before the root's per-account model exists. Without it, a merge racing a just-made removal would undo that removal.

Follow-up: #1024. It holds the two Low, non-blocking findings of the round-3 review (a stale plan inside a millisecond window, and held changes kept after declining).

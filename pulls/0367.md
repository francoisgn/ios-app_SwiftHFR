**Problem.** After #320 (PR #364), `SessionRefreshFlow` probes keep the source session's host policy, but three other flows still built theirs with `HFRSession(cookies:)` / `HFRSession()`, i.e. `.forum`: a test session restricted to the loopback host could yield a probe allowed to reach the forum. No production impact (every production session is `.forum`).

**Change.** The same pattern as `SessionRefreshFlow`: the test factory becomes optional, and one internal instance method builds the default from the source session's `probe(cookies:now:)` (#364):
- `MPUnreadPoll.probe(cookies:)` → `account.probe(cookies:now:)`.
- `SmileyLookupFlow.probe(cookies:)` → `account?.probe(cookies:now:)`, a forum session when no account is logged in (no policy to keep).
- `LoginFlow.jar(for:now:)` → `session.probe(cookies: [], now:)`: still a fresh, empty jar; only the host policy comes from the target session.
- LOT-043, LOT-047 and LOT-053 specs: one line each.

**Tests (offline, nothing is sent; LESSONS 56).** `ProbeHostPolicyTests`: each flow's default probe on a loopback-restricted session has `.exactHost("127.0.0.1")`, on a production session `.forum`; the login jar starts empty. Each test fails when its default goes back to `HFRSession(cookies:)` / `HFRSession()` (three mutations, checked offline). Full HFRKit suite green locally, SwiftLint strict clean, `check-lot-deps` 0 violations.

**Merge.** Touches sessions and login (`LoginFlow`): for the steward or the maintainer (AGENTS §8).

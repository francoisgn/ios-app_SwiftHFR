**Problem.** With an image inserted in the modern composer's docked card, the card is one image-chips row (66 pt) taller than the room the screen leaves, so its bottom can go past the keyboard's top.

**Cause.** `ReplyComposerView.editorCard` read `measured.editorHeight`, but `measured.chips` was only set on the copy the sheet's `detent` builds. `textCap` therefore ignored the chips row for the editor, while the detent counted it.

**Change.** `ComposerCardLayout.withChips(height:)` (pure); the view's `layoutWithChips` feeds the detent, the editor card and the layout probe. No change to the legacy composer, nor to the room/keyboard model (`ComposerKeyboardRoom`), which is consistent: #1285 and the text-only #1286 are a placement matter (a `safeAreaInset` bottom placed by SwiftUI's keyboard safe area) that needs a device reproduction first.

**Tests.**
- `ComposerCardGrowthTests.theChipsRowIsTakenOffTheRoomWhenAnImageIsInserted`: pure arithmetic of `withChips` (card never above the room, editor loses exactly the chips height). It does not by itself catch the view regression (review round 1).
- `ComposerLayoutHostedTests.anInsertedImageKeepsTheCardWithinTheRoom`: the real composer hosted, a keyboard notification, a chip and 30 lines; the editor and the drawn card must match the layout with the chips row. Goes red if the editor reads `measured.editorHeight` again (the drawn card is 66 pt taller than `textCardHeight`), per the reviewer's reasoning; not run here, the cloud cannot build the app. Two Low notes of the round 3 verdict (a guard that the cap differs with and without chips; `makeKeyAndVisible()` if the test turns flaky) are not applied.

Device check owed (#893): modern composer, insert an image, type past the cap: the card stays above the keyboard.

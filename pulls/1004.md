**Problem.** Turning on Réglages › Expérimental › « Chargement des images » restored the stored `display_images`. A beta that had stored « Jamais (au toucher) » therefore brought it back at the first activation. The operator decided on #1003 (2026-11-17, « forcer toujours ») that the first activation starts at « Toujours ».

**Cause.** `ImageLoadingChoice.autoLoad` and the picker read `display_images` as stored. #984 kept that on purpose.

**Change.**
- `ImageLoadingChoice.willTurnOn(store:)`: the first time the option is turned on, it writes `display_images = always` and the flag. Later activations do nothing.
- `ExperimentalSettings.set` calls it when `.imageLoadingChoice` turns on, **before** writing the switch, behind `// EXPERIMENTAL(imageLoadingChoice, #1003)`. The reader reads both values off the main actor, so it never sees the option on with a stale choice. The Expérimental page's toggle goes through `set`, and the picker appears after the write, so it shows « Toujours ».
- **Remembering "first":** a new device-only key, `experimental.imageLoadingChoice.started` (`Setting.bool`, default false; an absent or unreadable value reads as false).
  - It is separate from the switch's own key. A member who used the option in a build before #1003 gets « Toujours » at their first activation after this update, as #1003's persistence point asks.
  - It is added to the `SettingKey` catalogue and to ADR 0013's matrix row (6 keys; the flag is read only by `ImageLoadingChoice`). The `display_images` doc is updated.

**Open for the operator** (also on #1003, so it outlives this PR). Both cases are pinned by `anActivationBeforeTheUpdateDoesNotCount(wasOn:)`; either answer is a few lines.
- A choice made while the option was on in a build since #984 is replaced by « Toujours » at the first activation after the update. The alternative is to keep it, which would also keep a stored « Jamais ».
- If the option is still on at the update and is never toggled, its stored choice stays. The alternative is a launch-time reset.

**Tests.**
- `ImageLoadingChoiceTests` (app):
  - `theFirstActivationStartsAtToujours(stored:)`: with « Jamais » or « Wi-Fi uniquement » stored, the first activation gives « Toujours », `autoLoad == .always`, and the flag set. It fails without the change.
  - `laterActivationsKeepTheMembersChoice`: « Wi-Fi uniquement », then off and on, is kept, and again after a relaunch. It fails if the reset ignores the flag.
  - `anActivationBeforeTheUpdateDoesNotCount(wasOn:)`: the switch stored off or on by an earlier build gives « Toujours » at the next activation; turning off keeps the choice.
  - `theReaderNeverSeesTheOptionOnWithTheStaleChoice`: a spy store records `autoLoad` after every write of an activation, and every record is `.always`. It fails with the old write order.
  - `otherSwitchesAndTurningOffLeaveTheChoiceAlone`: the switch is seeded on, so turning it off really runs.
- `SettingKeyTests` and `SettingScopeTests` (HFRKit, run locally): the new key is in the catalogue, default false, `.device`.
- Mutations run by the reviewer: each of these fails at least one test: the old write order, a reset on turning off, a reset only on « Jamais », no call, no guard.

**Device check (general review)**
- [ ] With « Jamais » stored by an earlier build, turn the option on: the picker shows « Toujours » and images load.
- [ ] Choose « Wi-Fi uniquement », turn the option off and on, relaunch: still « Wi-Fi uniquement ».

Two trivial HIG items (operator triage of 2026-11-19, priority high) in one PR because both touch `TopicListView.swift`.

### #1162: the row context menu
- **Problem**: « Filtrer les posts » and « Suppression… » showed dimmed in the Favoris row context menu (HIG › Context menus: hide unavailable items, don't dim them). Legacy has the same (`MainWindow.swift:656`, `Favorites.swift:1166` @ 87fe0d1c), so this is an evolution, not a parity fix.
- **Cause**: the menu used `.disabled(filtering.isBusy)` and `removeButton`, whose `.disabled(removing)` is meant for the swipe.
- **Change**: `TopicListModel.menuOffersRemove(_:)` (`canRemoveFlag && !isRemovingFlag`) and `menuOffersFilter(_:filterIsBusy:)` (Favoris, a topic number, no filter run busy) decide the two menu entries; the view builds them only when true. The trailing swipe button and the VoiceOver action keep their own state: `removeButton` still dims « Suppression… » there.

### #1163: first-load captions
- **Problem**: five list screens showed `ProgressView` with vague or unevenly punctuated captions (« Chargement… », « Chargement des sujets », « Chargement des messages », « Chargement du profil… ») (HIG › Progress indicators: avoid vague « loading »).
- **Change**: a bare `ProgressView()` on the first load of Alertes Qualitay, the topic lists, Messages, the profile and « Filtrer les posts », as the issue proposes. The specific « Recherche des MP multiples » caption stays. Not touched (not in the issue): Catégories (« Chargement des forums »), the reader's first load, the GIF picker.
- The shared state component of #693 is not in `dev-swift`; each view keeps its own `ProgressView()` (one word each, nothing to abstract).

### Tests
`TopicRowActionsTests` (written first): `theContextMenuHidesWhatCannotRunInsteadOfDimmingIt` («  Supprimer » is offered, disappears from the menu while the removal is in flight (the swipe's `canRemoveFlag` stays true), is back after; « Filtrer les posts » is absent off Favoris on a Drapeaux list) and, since review round 1 (the first version asked a Drapeaux model for the Favoris entry and would have failed), `theFilterEntryIsOfferedOnFavorisWhileIdleAndHiddenWhileBusy` on a real Favoris list. **The menu wiring itself (the view builds only what the two predicates allow) is not covered by a test: it is checked by hand on the next device review (#893).** #1163 has no test: the change is removing text; the issue's own check is a text review and the first load of each list on the device review. Not run here (Linux); `compile-check` runs on the head.

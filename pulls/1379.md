### Problem
Every profile sheet of SwiftHFR fails since 2026-11-26. HFR now answers a cookie-less `GET /hfr/profil-<id>.htm` with **403**, the web server's own page (`R1363a`), and serves the profile to a logged-in session only (`R1363b`). SwiftHFR fetched profiles without cookies on purpose (LOT-116 difference 1), so the sheet showed « Erreur du forum ». The MP list's avatar lookup (#714) read profiles the same way, so every lookup failed and was retried every 60 s.

### Cause
`LiveUserProfileSource` called `fetcher.profile(memberID:as: .anonymous)`; the parser had only been verified on logged-out pages (#124), so the session was never sent.

### Change
- `LiveUserProfileSource` (`App/SwiftHFR/Profile/UserProfileSource.swift`) sends the current account's `HFRSession` (`.authenticated`).
  - Without a login (`HFRSession.isLoggedIn`) no request leaves. The sheet shows « Connexion requise » / « Le forum réserve les profils aux membres connectés. Connecte-toi à un compte puis réessaie. » (`ListLoadError.profileLoginRequired`).
  - A 401 or 403 is `ListLoadError.profileAccessDenied`: « Le forum a refusé l’accès au profil. Ta session a peut-être expiré : reconnecte-toi puis réessaie. » Another status keeps « Erreur du forum ».
  - This ports legacy `bb58131d` (#1349): `HFRswift/Swift/UserProfileService.swift:23-48` (no request without an account, `loginRequired`; 401/403 → `accessDenied`) and `UserProfileLoadingError.swift:22-26` (strings, in the app's « tu »). Legacy uses the main account; SwiftHFR uses the current one, like every other page.
- No new `ListLoadError` case: the two states are `.notAuthenticated(message)` values, so no switch elsewhere changes. The source is built once in `AppEnvironment` from the environment's session.
- `LiveUserProfileSource(session:)` builds its fetcher from the session it checks: one value for both (review round 1, finding 3).
  - It takes a `ProfileSession`: an `HTTPTransport` plus `profileLoginState()` (logged in, login generation). `HFRSession` conforms in the app; tests use a recording double that cannot reach the forum (round 2, finding 2, LESSONS 56).
- `LiveMemberAvatarLookup` (#714) reads the profile through the same source, so it now carries the session too. Its `profilebdd.php` id lookup stays cookie-less (`R716c`).
  - Review round 1, finding 2: without a login, nothing is sent, not even the id lookup.
  - A refusal (no login, or HFR's 401/403) is a new result, `.refused`. It suspends every lookup, so the 60 s retry loop does not come back.
  - The suspension lifts when the session's login generation moves (round 2, finding 1). A re-login in place keeps the same session and environment (#1195), and the refused pseudo is then asked again.
- Stale "without cookies" claims about profiles are updated (finding 1): `App/README.md`, `AuthorActionHandlers.swift`, LOT-126, and LOT-027 (logged-in profile no longer pending). The `### Ledger` now also has a `changelog` row that reverses row 65.
- A capture issue for a stale or refused session on a profile request is open: #1383, cited in the LOT-116 spec (finding 4).
- Fixtures `R1363a` (anonymous 403) and `R1363b` (logged in, 200). Both are read-only GETs of 2026-11-27 on the kit account user1's **own** profile (a consenting operator account), anonymized with the kit. See the review below.

### Problem
On iPhone (compact width), every topic opened after the first one in a process never shows its messages (#750: 11 of 11 reopens and every other topic after one, measured on `7847accf` and on `942afdde`; operator device on `f74710d0`). The same topic opened again shows a blank page; another topic stays on "Chargement des messages". Actualiser does not recover it. #643 is the same signature on MP conversations.

### Cause
SwiftUI sends `onAppear` and then `onDisappear` to the reader pushed again in a collapsed `NavigationSplitView`, in the same millisecond and **before its web view is in a window**, and then never sends `onAppear` again although the reader stays on screen. Measured on the simulator with a window log added to the reader (ReaderLog, baseline `f74710d0`):
```
show loads token=1                      <- onAppear of the new view
appear model=A viewer=2 page=true
onDisappear viewer=2 inWindow=false     <- same millisecond
stopLoading token=1 ready=false         <- the not-ready document is forgotten, the controller stopped
window in=true stopped=true             <- ~150 ms later the web view enters the window: nothing restarts it
```
`TopicReaderView.onDisappear` took that as final: `ReaderWebController.stopLoading()` stopped the web view (nothing but a later `onAppear` called `resume()`), and `TopicReaderModel.viewDidDisappear` cancelled the load of a new model (the #643 sequence). A real Back is the other way round: the web view leaves its window first, then `onDisappear`.
- **Topics vs MPs:** `NavigationModel.reader(for:)` keeps the topic's `TopicReaderModel` after Back (`currentReader` is only dropped on a source change), so a reopen reuses a model that has a page: no load, and the model still counts the old web view's `ready` (`hasShownDocument`), so the screen shows the new, stopped web view blank. `MessageListModel.selected` drops its reader on deselect (`didSet`), so an MP reopen always has a new model and only the cancelled-load variant (#643) applies; why the operator's `f74710d0` device no longer hits it on MPs is not established (timing), but it is the same code path and this change covers it.
- **Legacy** has no such state: its reader reloads the page on every open and bounds the fetch with a 10 s timer that ends in "Le chargement du topic a expiré. Réessaie." (`HFRswift/Swift/MessagesView.swift:3668-3704`, `beginTopicLoad`/`completeTopicLoad`, with `HFRNetworkTimeout.content = 10`, `HFRswift/Swift/Common.swift:1906-1907`, @ `87fe0d1c`).

### Change
1. **The window decides (the cause).** The reader's web view reports `didMoveToWindow` (`QuoteMenuWebView.onWindowChange`). `ReaderWebController+Presence`: `onDisappear` leaves (`events.left`: model, offline save, web view stop) only when the web view is in no window; a disappearance while in a window waits for the web view to leave it; a stopped reader whose web view enters a window resumes, shows its document again and tells the view (`events.returned`), which hands the model's document and calls `model.onAppear(viewer:)` (restarts a cancelled load). `TopicReaderView` routes `onAppear`/`onDisappear` through it; the cover guards (followed link, image viewer) stay, and are checked again on the window path.
2. **A new view does not inherit the old web view's ready.** `TopicReaderModel.onAppear(viewer:)` clears `readyToken` when it was reported while another viewer was on screen, so a reused model waits (spinner) for the new web view instead of showing it blank.
3. **Safety net: no endless spinner.** `TopicReaderModel` watches each wait on screen (from `onAppear` to the screen leaving; a retry after a timeout waits again under a new watch) on "Chargement des messages" (no page yet, or a page the web view has not shown): after `waitLimit` it stops the load and sets `.timedOut`, i.e. the existing failure screen with "Réessayer". A document that still becomes ready shows and clears the error (it is recorded as the failed document); a screen that comes back after the timeout loads again. **30 s** = HFRNetwork's limit for a topic page request (`RequestTimeout.standard`, legacy `kTimeoutMini`), counted over the fetch **and** the web view. Legacy's 10 s covers the fetch only; the #750 measurement puts most of a first open in the web view (cold opens up to 20 s to the first message on the loaded simulator), so 10 s over both would fail working opens. Ledger row below.
4. "Réessayer" and "Actualiser" also `resume()` the web view (they are tapped on screen; #643 "Actualiser does not recover it").
5. `SafariView`, `ExternalLink` and `VideoItem` move out of `TopicReaderView.swift` unchanged (file length).

Class covered: every screen that hosts `TopicReaderView` (topics in Catégories/Favoris, MP conversations, pushed link readers, search, About, offline reader) goes through the same controller and model. The lists do not stop anything on `onDisappear`.

**#785** (text size change, then messages never load): on the simulator, the first open after a fresh launch and a text-size change loads; the opens after it (same topic, another topic) fail with exactly the #750 sequence above, and with this change 3 of 3 load after a text-size change (85 → 105 %). The text-size path itself does not stop a load (new test `aTextSizeChangeDuringALoadKeepsPagesLoading`, green before and after). Not closed here: the MP side is unverified (logged-out harness) and the operator's device check is pending.

# PR #1279: Reader: a picture inside a link opens the linked image or asks before leaving (#912)

**Problem.** `reader.js` posted only the picture's own `src` on a tap and ignored the `<a href>` around it: a thumbnail linking to its full-size image opened the thumbnail, one linking to a page opened the picture and never the page, and nothing warned before leaving.

**Cause.** LOT-109's tap message had no field for the wrapping link, so the app could not decide anything about it.

**Change.**
- `reader.js` sends `link` (the resolved `href` of `picture.closest("a[href]")`, null outside a link) with the existing `image` message; the page never navigates. `ReaderBridgeMessage.image(urls:index:link:)` reads it strictly (absent or null is unlinked; another type rejects the message; longer than `maximumLinkLength` is dropped, the tap then opens today's viewer).
- `ReaderPictureTap.decide` (new): http(s) link that is an image (image extension from the path, or a rehost the `ImageHostTable` serves extension-less) and that policy C lets the viewer fetch -> `.linkedImage` (viewer opens it through `ImageGallery.build(linked:)`, the preview stays the fallback `shown`); other link -> `.link`; no usable link -> `.viewer`. A linked image on a third-party host the user did not allow (consent covers the picture's own host) is not fetched: it falls to the link route with the warning.
- `ReaderPictureLinkPrompt` (new): « Ce lien ouvre une page externe » + the domain, **Ouvrir** / **Annuler**; Ouvrir follows « Navigateur par défaut ». A forum link takes the LOT-137 route with no warning.
- One implementation of the full-size rule: the viewer still goes through `ImageGallery.fullSize(of:)` / `ImageHostTable.fullSizeURL` (#917 unaffected).
- CSP and the no-page-script guarantees are untouched; the link only decides which URL the app-side gallery fetches (policy C, cookie-less client) or routes through `ReaderLinkAction`, never the session client.
- `TopicReaderView.swift` stays at 399 lines (the linked-reader binding moved to `LinkedReader.binding(of:)`, the link switch became `open(_:asking:)`).

**Tests** (iPhone 17 clone, iOS 27.2, unsigned).
- New `ReaderPictureLinkTests` (8 tests): model rules (image file in any case, query not read, rehost shape, host alone is a page, page, forum, no/unusable link, other third-party host, blocked address), `PendingPictureLink` (forum and profile never warn), message decoding, controller routing, and one hosted WKWebView tap test (`aTapOnAPictureInsideALinkSendsTheLink`) driving `reader.js` on three pictures (image link, page link, no link) and asserting no navigation.
- Red: the model tests reference types absent from dev-swift (compile failure without the change); with only `reader.js` reverted to dev-swift, the hosted tap test fails (5 issues) and the other 7 pass.
- Green: 72 tests in 10 suites passed (ReaderPictureLinkTests, ImageGalleryTests, ReaderImageViewerBridgeTests, ReaderBridgeMessageTests, ReaderBridgeWiringTests, ReaderWebSecurityTests, ReaderWebControllerTests, ReaderImageBaselineWebTests, ReaderComposerSuspensionTests, ImageViewerModelTests).
- Built from the unsigned build-for-testing of the same tree; SwiftLint counted by hand (lines <= 140, files <= 400, no `Bool?`).

**Legacy check** (`87fe0d1c`). Legacy does neither of the two in general:
- `MessagesView.swift:1150-1235`: the tap script reads the picture's `longdesc` attribute (not the wrapping `<a>`), and only for a small (<= 200 px) `img3.super-h.fr` thumbnail whose linked image has the same identity (`.th.` stripped) and an image extension (`Common.swift:2243-2256` `isImageURL`); then it opens the viewer on the linked URL. Parity: a link to an image opens that image.
- Every other tap falls through to the link's own navigation; a search of `87fe0d1c` for a warning string (`page externe`, `lien externe`) finds none. So the warning, and following a wrapping link to any image (not only small img3 thumbnails), are deliberate differences.
- Rule (b) (generic image extension) cites legacy's `imageExtensions` list (`Common.swift:2231-2242`). No corpus capture of a thumbnail linking to another host was checked: the rule is the operator's (#912) and the third-party-host case is guarded by policy C.

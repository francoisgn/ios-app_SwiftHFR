**Problem.** `reader.js` posted only the picture's own `src` on a tap and ignored the `<a href>` around it: a thumbnail linking to its full-size image opened the thumbnail, one linking to a page opened the picture and never the page, and nothing warned before leaving.

**Cause.** LOT-109's tap message had no field for the wrapping link, so the app could not decide anything about it.

**Change.**
- `reader.js` sends `link` (the resolved `href` of `picture.closest("a[href]")`, null outside a link) with the existing `image` message; the page never navigates. `ReaderBridgeMessage.image(urls:index:link:)` reads it strictly (absent or null is unlinked; another type rejects the message; longer than `maximumLinkLength` is dropped, the tap then opens today's viewer).
- `ReaderPictureTap.decide` (new): http(s) link that is an image and that policy C lets the viewer fetch -> `.linkedImage` (viewer opens it through `ImageGallery.build(linked:)`; the table's full size of the picture, then the preview, stay the fallbacks); other link -> `.link`; no usable link -> `.viewer`.
  - "Is an image": on a host with an `ImageHostTable` rule that serves extension-less images, the path must have the shape of the rule's image (`img3.super-h.fr/images/`, `rehost.diberie.com/Picture/Get/f/`), whatever its extension; elsewhere, an image extension read from the path. `reho.st` has no captured image shape, so its links are page links (capture issue #1280), except that a `reho.st/thumb/…` picture with a same-host link takes the `.viewer` exception (no corpus case).
  - The host's own viewer page of a thumbnail the table can enlarge (img3 `/image/<id>` around `…th.png`) is today's `.viewer`, on the full size: no regression from dev-swift and no warning.
  - Consent is per address: a third-party linked image is fetched only when its own address is consented or "load third-party images" is on, or it is the picture's own full size (which the viewer fetches anyway). Otherwise (even on the picture's own host) it is a `.link`: it gets the « page externe » warning, and Ouvrir loads it in the browser, not in the viewer (no silent third-party fetch).
- `ReaderPictureLinkPrompt` (new): « Ce lien ouvre une page externe » + the domain, **Ouvrir** / **Annuler**; Ouvrir follows « Navigateur par défaut ». A forum link takes the LOT-137 route with no warning.
- One implementation of the full-size rule: the viewer still goes through `ImageGallery.fullSize(of:)` / `ImageHostTable.fullSizeURL` (#917 unaffected).
- CSP and the no-page-script guarantees are untouched; the link only decides which URL the app-side gallery fetches (policy C, cookie-less client) or routes through `ReaderLinkAction`, never the session client.
- `TopicReaderView.swift` stays at 399 lines (the linked-reader binding moved to `LinkedReader.binding(of:)`, the link switch became `open(_:asking:)`).

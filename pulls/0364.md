Closes #320
Claim: ext/ezzz-opus-1

**Problem.** `SessionRefreshFlow()` built its probe with `HFRSession(cookies:now:)`, so the probe always had the `.forum` host policy, even when the refreshed session is a test session restricted to the loopback host (`.exactHost`). No production impact (every production session is `.forum`); the exposure is a test that could send a real profile-page GET with fake cookies if a seam regressed (CodeRabbit thread on #319, traced by moust4ki).

**Change.**
- `HFRSession.probe(cookies:now:)`, `package nonisolated`: a fresh session seeded with `cookies`, its own jar, no `hash_check`, and the source session's host policy and network configuration.
- `SessionRefreshFlow`: `makeProbe` is optional; without a test factory the probe is `SessionRefreshFlow.defaultProbe(for:cookies:now:)` = `session.probe(...)`.
- `SessionHostPolicy` is `Equatable` and `HFRSession.hosts` internal, so the tests can read the policy. No public API change, no production behaviour change.
- LOT-044 spec: one line in Behaviour.

**Tests (offline, nothing is sent).** `SessionRefreshProbeTests.theDefaultProbeKeepsTheRefreshedSessionHostPolicy` (fails when `defaultProbe` goes back to `HFRSession(cookies:now:)`: checked), `HFRSessionProbeTests.aProbeKeepsTheHostPolicyAndHoldsOnlyItsSeed` (policy, seed cookies, no token, source jar untouched; fails when `probe` forgets the policy: checked). Full HFRKit suite green locally, SwiftLint strict clean, `check-lot-deps` 0 violations.

**Note.** A first version had a test that sent a request to `https://forum.hardware.fr/` through a restricted probe, expecting a local refusal; under the mutation (probe back to `.forum`) that request may have gone out once from the author's machine, with a fake `md_user` cookie. That test was removed before this PR: a test of this hazard must never be able to reach the forum.

**Merge.** Touches sessions (`HFRSession`): for the steward or the maintainer (AGENTS §8).

**Problem.** Fable's adversarial review of #490 (merged as 501d1be) left three items:
1. **Low**: `JSONTreeEncoder`'s `superEncoder()` (keyed and unkeyed parents) wrote `{}` when the super encoded a single value or an unkeyed container; `JSONEncoder` writes the value (`{"super":1,"x":2}`). No `HFRModels` type uses `superEncoder` today, so no stored document was affected.
2. **Nit**: `JSONTreeNode.count` returned 1 for a `.value` node (and the member count for an object); only array nodes are asked.
3. **Nit**: `JSONTreeEncoder.claim` silently replaces a node of another kind where `JSONEncoder` traps.

**Cause.** The super encoder was given an empty-object placeholder node already set in the parent; it was reused only when the super asked for a keyed container, so a value or an array replaced the child's node and the parent kept the placeholder.

**Change.**
- `JSONTreeNode.Content.deferred(JSONTreeEncoder)`: the parent holds the super's encoder and reads its node when the tree is finished (`{}` if it wrote nothing, as before). Both super-encoder sites use it; no placeholder any more.
- `count` answers for array nodes only (0 otherwise), with a comment on why.
- `claim` documents the intended difference from `JSONEncoder` (replace instead of trap: only a malformed `encode(to:)` hits it, and the app should not crash on it). No behaviour change.

Nothing else touched; no public API change.

**Tests.** `JSONWriterTests.superEncoders(shape:)` (parameterised: single value, unkeyed, keyed super) encodes a type through `superEncoder()`, `superEncoder(forKey:)` and an unkeyed `superEncoder()`, and compares with `JSONEncoder`'s text. Without the fix the `.single` and `.unkeyed` cases fail (`Expectation failed: text == (try Self.foundation(value))`); with it all pass. Full suite on Linux (Swift 6.2.4): 1497 tests green; `check-lot-deps.py` 0 violations.

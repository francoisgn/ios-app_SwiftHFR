### Problem
iPad multi-window (legacy `UIApplicationSupportsMultipleScenes` true at `2fe43da3`). The generated scene manifest is already multi-scene in Xcode 27.2 (measured; an explicit build setting or a manifest in `Info-Keys.plist` does not change it), so several windows already open, but code written for one scene misbehaves with two.

### Cause
`WindowGroup` content closures run once per window, and the `App`'s `scenePhase` is the aggregate of all windows. Each window also built its own `PrivateMessageCount`, and every root watched the one MP notification router.

### What changed (and why this wide)
- `AppLifecycle` (steps injected, live over the shared models): the launch sequence (legacy import, reconcile, restore) is one shared `Task` every window awaits, so a second window never reads the accounts before the import wrote them; the account-change import, foreground re-check, background scheduling, lock/season handler and offline eviction act once per change. `SwiftHFRApp` calls it from each window's content.
- `SharedPrivateMessageCounts`: one Messages count per session generation (badge and app icon agree across windows).
- `RootNavigationView.takeNotification`: an MP tap is taken only by a window whose scene is `.active`; it stays in the router otherwise.
- `SceneClaims` / `SceneGate`: the dated-icon question, the icon error alert and the import summary sheet are presented by one window (as `alertScene` does for the arrival alert); `AppIconSeasonModel.checkOnceAtLaunch()` keeps a new window from clearing the question.
- Spec completed; legacy pointers updated.
Not changed: per-window restoration, "open in a new window" (LOT-145, M5); the same-topic draft: [#1028](https://github.com/ezzz/HFRnow/issues/1028).

### Tests (`App/SwiftHFRTests/Root/MultiWindowTests.swift`, 13 tests)
Each was run with its fix reverted and failed (round 1 mutation run: `:60`, `:80`-`:84`, `:90`-`:93`, `:102`-`:103`; round 2: `:123`, `:125`, `:128`; round 0: `:21`, `:32`, `:40`, `:46`, `:53`, `:79`, `:107`):
- `twoWindowsLaunchingAtOnceRunTheSequenceOnceAndBothWaitForIt`, `aWindowOpenedAfterTheLaunchDoesNotRunItAgain`, `everyWindowSeeingAChangeRunsItsReactionOnce`: `AppLifecycle` with two callers, steps recorded in order.
- `aTapStaysInTheRouterUntilAWindowIsActive`: the router keeps the tap for a non-active window.
- `onlyTheFirstWindowPresentsWhatASharedModelRaisesAndTheNextOneTakesOverWhenItCloses`: `SceneClaims`, including the hand-over when a window goes to the background (`aWindowGoingToTheBackgroundHandsWhatItPresentsToOneOnScreen`).
- `aSecondWindowDoesNotResetTheIconQuestionTheFirstShows`, the count and two-roots tests, the helper tests; `theBundleDeclaresMultipleScenes` guards the manifest (passes without a change by design).
Not covered by a test: the SwiftUI wiring itself (the calls from the `WindowGroup` content and the `SceneGate` modifiers); device-check below.

**Adversarial review (opus-5.5, mac/M1-r1027-opus, bb922a86)** — REQUEST CHANGES

1. **High** — `SwiftHFRApp.swift:75-79` (launch `.task`), and the spec claim "Already once-only and kept: `runAtLaunch`, `restore`". These calls are once-only, but the order "import, then restore" is not kept across windows. `LegacyImportModel.runAtLaunch()` (`LegacyImportModel.swift:47-51`) returns at once on a second call, without waiting for the import already running.
   - Scenario: a legacy iPad user had two windows open. At the first SwiftHFR launch both scenes connect. Window 1 starts the import. Window 2's `runAtLaunch()` returns at once, then it runs `reconcileAccountSync()` and `restore()` on the store before the import has written to it. Window 1's later `restore()` gets back the same `restoreTask`. `accountDidChange` doesn't fire either, because `current` stays nil. The imported accounts don't show until the next launch, which breaks the LOT-158 order.
   - Fix: run the whole launch sequence once, as one shared `Task` that every window awaits (or have `runAtLaunch` await the run in flight). Add a test with two concurrent callers.
2. **Medium** — `AppIconSeasonModel.swift:113-117` and `RootView.swift` (`.sheet(item: legacyImport.summary)`). The icon question, the icon error alert and the import summary sheet are bound to shared models and presented in every window. With two windows the same alert appears twice. `aSecondWindowDoesNotResetTheIconQuestionTheFirstShows` checks that the question is not cleared, not that it is shown once. The spec says only the seasonal alert is handled, which is true: it uses `alertScene`, `SeasonalThemeModel.swift:163`.
   - Fix: present each one from a single scene, as `SeasonalThemeModel.alert(for:)` does, or record the gap in the spec and #893.
3. **Medium** — `MultiWindowTests.swift`, against LESSONS 2. The tests cover the helpers (`AppWideEvents`, `mayOpenNotification`), never how `SwiftHFRApp` and `RootNavigationView` use them. No test references `SwiftHFRApp`. Removing any of the five `events.isNew`/`firstTime` guards, or `.onChange(of: scenePhase) { takeNotification() }`, leaves every test green.
   - Fix: move the handlers into testable `@MainActor` functions and test them with two callers.

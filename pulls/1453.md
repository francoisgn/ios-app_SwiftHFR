## What and why
**Problem.** A group MP opened for a few seconds is read on HFR, and nothing in the list says where the member stopped. SwiftHFR read the MPStorage flags other clients write (LOT-130) but never moved them, and a row never opened at its flag.

**Cause.** The reader's flag write and the open-at-flag tap were left out of LOT-130 ("Out of scope"); legacy only had them with « Stockage MP » on (`mpstorage_active`, default off, `AppSettingsView.swift:112-113` @ 87fe0d1c).

**Change** (items 1–3 of the issue, operator 2026-11-12), all behind the existing experimental option « MP multiples → dark topic » (#1014), so the default build keeps legacy; one-to-one MPs are untouched (item 4: not needed):
1. **Legacy flag write** — each page the reader shows moves the group's flag forward to that page's last message (`page >= stored page`, `href` `t<numreponse>`, `p`, `uri`: `MessagesView.swift:3582-3623` @ 87fe0d1c; a missing page reads as -1, `MPStorage.m:547-563`). Engine: `MPStorageMPFlag.init(conversation:page:lastMessage:pValue:)`, `MPStorageMPFlag.messageNumber`, `MPStorageDocument.moveMPFlag(_:stamp:)` (keeps keys another client added). App: the flag moves in the **device copy** at each page (`MPStorageSyncModel.editLocally`) and goes with **one sync when the conversation is left** (`sendMovedFlags`), not one forum write per page as legacy did; the send waits for page loads in flight (`noteReached`) and also fires when the reader leaves the screen or the app the foreground. A group row with a position **opens there** (page + `#t` anchor: `HFRMPViewController.m:228-251`, `Common.swift:2738-2742` @ 87fe0d1c).
2. **App-only position, MP storage off too** — the same position is kept in LOT-090's reading-position store (the one the reader already records into, iCloud-mirrored by LOT-172), read by the list after each load (`MPReadingPositions`, `MPDarkTopicPositions`). The row's `⚑ page / pages` and its opening use the furthest of the app's position and the MPStorage flag, so a flag another client moved further is honoured.
3. **"Not fully read" mark** — while the position's page is before the row's page count, the row shows unread (dot, tint) whatever HFR's icon says (`showsUnread`); display only, the badge and segment counts stay HFR's. A new message on the page reached already makes HFR's own state unread; one on a new page brings the mark back. No automatic `nonlu.php`.

**Merge rule (Fable round 1).** A read position only moves forward, so an `mpFlags` conflict in the LOT-062 merge now keeps the further flag (page, then message), with or without a base; a tie falls back to the default rule (`MPStorageMPFlag.conflictWinner`). Without it, a stale device copy plus a page read here took back a flag another client had moved further. LOT-062 spec, the merge's header comment and ADR 0013's merge row say the exception.

Why this wide: the three items share one position; the option gate (#1014) was already the switch for the flags, and the #859/#1014 switch itself is untouched. LOT-130's spec rows that called this a follow-up are updated. `dev-swift` merged in (b70b3c39; two hand-resolved conflicts reviewed in round 2).

## What and why
**Problem.** SwiftHFR ships as an in-place update of `hfrplus.red.super` (Q-1). LOT-067 (#703) built the importer of the legacy data, but nothing ran it: an updated user would find no account, no lists, no drafts.

**Cause.** LOT-067 is the engine half; the app half (when to run it, what to show, where the pending items are placed) is this lot.

**Change** (spec: `docs/lots/LOT-158-first-launch-import.md`):
- `SwiftHFRApp`: the import runs at launch **before** `AccountsModel.restore()`, so the accounts it writes into the LOT-065 Keychain item are listed; it runs again on each change of the current account while the report is incomplete (D3: global items wait for an account; retriable failures retry). When such a run imported accounts, the account list is read again.
- `LegacyImportModel` (`@Observable @MainActor`): launch run once, account-change runs, retry, runs in flight; `LegacyImportSummary` (pure): French rows, counts only, shown only when a data step imported something or failed (or items were refused). A fresh install or a launch after a complete import is silent.
- `RootView`: "Import des données de HFR+…" on the launch progress view; the summary sheet with "Réessayer" (retriable failures only) and "OK".
- Pending super-favourites (D2): placed at each favourites-list load (`FavoritesOptionsModel.placePendingSuperFavorites`, called from `TopicListModel.load` after the prune). Pending reply drafts (D1): placed when the reader delivers a page of the topic, and awaited by `ReplyComposerModel.start()` before it reads the draft (so a fast "Répondre" still finds it).
- The importer writes through the app's single live store of each file; two new device-only files under `Application Support/LegacyImport/` (state, pending).

Why this wide: only the call sites the LOT-067 spec and ADR 0013 Amendment 3 name. No engine change, no new dependency, no `HFRModels` change, no ADR.

**Decision to confirm** (the spec proposes, the operator decides): the summary's wording and placement (sheet over the root screen after the launch run; see the spec's table). Progress is an indeterminate label, since the engine reports once at the end (a per-step callback would be an engine change).

1. **Medium** — `App/SwiftHFR/LegacyImport/LegacyImportServices.swift:26`: the importer gets a second `KeychainCredentialStore` on the item `AccountsModel.live()` writes. Its read-modify-write lock is per instance (`KeychainCredentialStore.swift:22,36-38`), so "keeps no state" does not make it safe, and the spec's own "one instance per file" rule is broken. Scenario: `accounts` failed at launch; a later run (login or "Réessayer") updates the book off the main actor while `AccountsModel` runs `store.update` (`AccountsModel.swift:308,346`: session write-back, avatar). The last writer wins: imported accounts vanish with the step marked done for good, or fresh cookies are replaced by stale ones. Fix: one shared instance for both.
2. **Low** — `SwiftHFRApp.swift:50`, `RootView.swift:34`: `retryRestore()` only waits when a restore is running (`AccountsModel.swift:108`), which is always so when `onChange` fires from the restore's own publish. Accounts imported by that run stay unlisted until relaunch, contrary to the spec's Keychain edge case. Fix: read again after the running restore.
3. **Low** (LESSONS 2) — `LegacyImportModel.swift:80-82`: replacing `else if summary != nil` with `false` leaves all 20 tests green. Scenario: `accounts` failed, retry finds nothing; the sheet keeps "Échec" and "Réessayer". Fix: assert `summary?.canRetry == false` in `aRunSaysWhenItImportedAccounts`.
4. **Low** — `RootView.swift:31`: the summary is presented from the root while the login or accounts sheet (`AccountMenuButton.swift:51-54`) is still up, which is the D3 path. Not verifiable on Linux and absent from the Mac checks. Fix: add that Mac check.
5. **Nit** — spec "Learnings" is empty.

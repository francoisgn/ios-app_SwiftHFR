# PR #516: Composer: focus the first empty field once the draft is read

- State: open
- Author: francoisgn · created 2026-11-06T09:18:08Z · updated 2026-11-06T09:22:23Z
- Labels: —

Refs #499 (partial: the focus bug found by the Mac check of #458; the rest of #499 stays open)
Claim: mac/m2-lead

**Problem.** Simulator (iPhone 18 Pro, iPad Pro 13, iOS 27.0): a new private message does not open on "Destinataire", the new-topic sheet not on "Sujet": no caret, no keyboard after 8 s.

**Cause.** `messageFields` is `.disabled(!model.canEdit)` and `canEdit` needs `hasRestored`. `.task { await model.start(); focused = firstEmptyField }` sets focus in the same turn as `hasRestored = true`, before the view re-enabled the field: the assignment hits a disabled field and is lost. Not a simulator effect: the login sheet shows its caret on the same simulator.

**Change.** One view. The first focus moves to `.onChange(of: model.canEdit)`, once (`didFocus`), so a later `canEdit` flip (a send) never steals focus. `firstEmptyField` and its rule unchanged. No sleep. The reply composer shares the code path (not driven on a device: it needs a topic, and the check opens none).

**Tests.** Pure rule unchanged; the bug is view timing (disabled state vs focus), only observable on a real focus state, so no unit test. Local XCUITest driver (not committed) reading `hasKeyboardFocus`, 3 s after the sheet appears:

| | before | after |
|---|---|---|
| iPhone 18 Pro, new MP, Destinataire | focus 0, keyboards 0 | focus 1, keyboards 1 |
| iPhone 18 Pro, new topic, Sujet | 0 / 0 | 1 / 1 |
| iPad Pro 13, new MP | 0 / 0 | 1 / 1 |
| iPad Pro 13, new topic | 0 / 0 | 1 / 1 |

Nothing sent; drafts emptied. No CHANGELOG-LEGACY row (the port's intent, not a legacy change).

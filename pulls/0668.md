## What and why
UX-09: the technical spec of the survey form, `docs/ux/questionnaire/formulaire-spec.md` (French), so that UX-10 (#634, Sonnet) builds the form without back-and-forth and UX-11 (#635) has a reference for the security review.

It follows `cadrage-construction.md` (IDs §2, contracts §3, constraints §4) and the PO decisions D1, D2 and D3 (statistics after 20 answers). It covers:
- stack: one Go binary (standard library + `embed`) with SQLite through `modernc.org/sqlite`, the **only third-party dependency** (pure Go, no cgo); static front with no framework or build step; container or binary with systemd;
- content file transcribed from `questions.md`, and a test that IDs, codes, labels and order match;
- flow: theme 2 branching on `P1` (front and enforced again by the server), random order of `C01`–`C10`, accessible card sort with up/down buttons, dark mode, local draft, single submission;
- data model: answers stored with no IP, no token and the day only; pseudo in its own table for purging; token and salted IP hash in separate tables erased at closing;
- anti-duplicate, rate limiting, honeypot, `Origin` check, trusted-proxy rule for `X-Forwarded-For`;
- API, end-screen statistics (threshold 20, also per question), HTTP security headers, logs without IP or pseudo;
- configuration, deployment, closing, CSV/JSON export (formula injection neutralised, pseudos only on request), pseudo purge, removal;
- the 21 tests UX-10 must write, plus manual accessibility checks.

**D4 is still open**: the spec stays portable; §13 lists what the PO must provide before deployment (OS and architecture, existing reverse proxy and TLS, Docker or systemd, sub-domain and DNS, proxy log policy, backups, time zone).

Points for the PO / reviewer: the SQLite driver is a third-party dependency (the alternative, Python, needs a framework or a non-production HTTP server); export and admin actions are CLI-only on the server, so there is no admin route to protect online; the restricted trial uses HTTP Basic (`UX_CODE_ACCES`).

The specification can permit publication of results derived from a single optional answer. It also uses weaker publication thresholds for retained results than for live statistics. These are material privacy-design issues, but the changes are a specification rather than a deployed service and the exposure is limited to questionnaire results.

**Retained concerns**
- **High · security · inferred:** D1 permits independently omitted sections, but aggregate-export suppression counts all respondents who sorted. Ten valid sorts can therefore pass the question and sorting thresholds even when only one respondent answered a particular section. Publishing that section's state or median rank can expose a singleton contribution; the retained snapshot preserves the same export content.
- **Medium · security · inferred:** The public statistics lifecycle does not preserve one disclosure threshold. Live statistics suppress questions below 10 respondents, while aggregate exports suppress only below 5. Erasure copies the export into the snapshot subsequently served by the statistics endpoint, allowing questions with 5–9 contributors to become visible after deletion unless an additional filter is introduced.

### Problem
Operator device test 2026-11-17: the title pill of #978 never shows (main pages after the large title collapses, pushed category lists from the start); Recherche has no large title.

### Cause (hypothesis, to confirm on the device, #893)
`ScreenTitleModifier` used `.toolbar(removing: .title)` plus a `.principal` item whose content was an `if` (empty until the pill was due). The pushed lists (`.pill`, always true) drew nothing either, so the most likely culprit is `toolbar(removing: .title)` taking the pill's slot with it. The mode → visibility rule itself was right (existing tests passed). Not reproducible on Linux.

### Change
- `ScreenTitle.swift`: no `toolbar(removing:)`; the `.principal` item (which takes precedence over `navigationTitle`, so the system title stays away) always holds the pill through a private `PillSlot` view, `.opacity(0)`, no hit testing, hidden from VoiceOver and its popover folded while `PillPresentation == .reserved` (large title on screen). New pure rule `ScreenTitleStyle.pillPresentation(headerVisible:)`.
- `TitleVisibility` (`@MainActor @Observable`): the large title's visibility, written by `ScreenLargeTitle` and read only by `PillSlot`. The six views (Réglages, Messages, Catégories, Favoris/topic lists, Plus, Recherche) held a `@State Bool` read in their `body`, so every crossing of the large title re-ran the whole list body: this is suspect 1 of #1015 (orchestrator's study), folded in because the same code is reworked.
- `ForumSearchView.swift`: `ScreenLargeTitle` first row, `.largeThenPill`.
- Category lists keep `.pill` with their name (unchanged call site, now drawn).

### Tests
- `theCentreSlotIsNeverEmptyWhateverTheModeAndTheLargeTitle`: the mode × header-visible table maps to `.shown` / `.reserved`, never absent; it does not compile without the change.
- `aMainScreenStartsWithItsLargeTitleOnScreen`: the tracker starts at "large title on screen" and the pill follows it.
- Not covered by an automated test (device check, #893): the view wiring (`toolbar(removing:)` gone, principal item always present), `.opacity(0)` hiding the glass capsule, and that no list body reads `TitleVisibility` again (the regression of #1015's suspect 1; check with `_printChanges()` on the Mac).

### CI notes
SwiftLint's one serious violation is not in this diff (SwiftLint run on the changed files: clean; local full run: only `MessageListModel.swift` file length, untouched here). The draft gate for the app build is expected. Compile check green on head 58f1ffc.

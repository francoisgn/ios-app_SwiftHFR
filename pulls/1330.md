### Problem
`ReaderResetAgreementWebTests.aLandingWaitsForTheResetThenRunsAtOnce` failed in CI job 138855383148 (PR #1322, unrelated): `waited > 1000` (message 2 at `-0.0` at frame 5) and `fired == 0` (message 2 at `1563` three frames later).

### Cause
The issue title says "wall-clock", but these two assertions are not durations. They are pixel positions read after a counted number of animation frames. The failure is a race in what the test assumes about the page:

- The test asked `landOnPost(2, 0)` with the page at `scrollY` 300 and delivered its "late reset" by moving the page to **0** at frame 5 (`ReaderResetAgreementWebTests.swift:77-80` before this PR; `aRestore…` the same at `:61-64`).
- 0 is also where WebKit's own late reset of a new document puts the page (#995, the phenomenon `afterAgreement` exists for: `reader.js:264-273`, `:295-305`). `pageAway()` checks only one instant where the page and the scroll view both show 300 (`scrollPage`, `ReaderWebTestSupport.swift:107-115`). A reset still on its way to the page can arrive after that.
- If the page reaches 0 by any route during frames 2-5, `afterAgreement` sees `scrollY == from` (`reader.js:298`) and the landing runs early. That is correct behaviour. Message 2 then sits at 0 at frame 5 (`waited` -0.0). The landing has already run, so the test's own `scrollTo(0, 0)` leaves message 2 at its natural 1563 (`fired` 1563). These are exactly the CI values.

Evidence:
- **Local replay:** a scratch test (not committed) moves the page to 0 at frame 3 of the wait, as a late reset would. The old assertions then give exactly the CI pair `[-0, 1563]`, 2/2. The new test passes under the same stray reset (`agreedAt 5, ranAt 6`, trace `1:300 2:300 3:0 4:0 5:0 6:1563`).
- **Not seen locally:** the natural late reset did not show in 28 runs of the old test on iOS 27.2 (10 alone, 15 under `yes ×4`, 3 in the same run as the Presence/Insets/PageEnd web suites under load). Page and scroll-view traces were clean every time. CI runs the iOS 27.0 runtime, which is not installed here. So the stray mover in CI is inferred from the values, not observed. The CI log shows no WebContent process death in that test (WebContent[32554] lived through it).

### Change
Test-only. `aRestoreWaitsForTheResetThenRunsAtOnce` and `aLandingWaitsForTheResetThenRunsAtOnce` now:
- ask with `from` **600**. WebKit never resets a page to 600, so a real late reset to 0 can no longer satisfy the test's agreement.
- deliver the reset by moving the page to 600 from frame 5. They repeat it each frame until the scroll runs, so a WebKit reset to 0 between two frames cannot undo it.
- assert on events counted in the page, not on positions at a fixed frame: the agreement came at frame 5, and the scroll ran after it and within 3 frames (the cap is 30). A failure message gives the page's `scrollY` at each frame.

Round 1 (Fable r1330, findings 2 and 3): the three sibling tests go through the same frame-counted helper, also with `from` 600. A stray reset to 0 could make each of them pass without testing anything:
- **Cap test** (`aRestoreWhoseResetNeverReachesThePageStillScrolls`): no reset is delivered. It checks the restore ran at the cap (frames 30-40) and not before.
- **Touch tests** (`theMemberTouching…`, `aTouchInTheSameTurn…`): the touch comes, then the reset from frame 5. They check that the restore never ran within 45 frames, which is past the cap. A restore that ran is seen in the trace, no longer hidden by a later `scrollTo(0, 0)`.

`agreedAt` is renamed `resetDeliveredAt`: it is the frame at which the test delivers the reset, not an observed agreement. No app code changes.

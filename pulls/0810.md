# PR #810: [SwiftHFR] Keep the pseudo field text typed while add() waits for removals

Closes #707
Claim: cloud/i707-sonnet

**Problem.** In the pseudo list editor, text typed in the field while `add()` waits for the queued swipe-removals (`settleRemovals()`) was wiped: the add submitted the earlier text, then `draft = ""` cleared the newer one (late CodeRabbit finding on #700).

**Cause.** `add()` captured `trimmedDraft` before the wait but cleared `draft` unconditionally after it.

**Change.** `add()` keeps submitting what the field held when the user tapped "Ajouter", and empties the field only if it still holds that text (`draft == submitted`). Nothing else changes (the already-listed case clears the same way).

**Scope item 2 (test structure, `PseudoListTests.swift:240`): not applied.** CodeRabbit asks for a deterministic checkpoint proving `add()` passed the wait; that needs a test hook in production code, which does not simplify anything. The existing yield-based tests keep their form (same trade-off accepted on #700 for the reload test).

**Tests.** `textTypedWhileAnAddWaitsForRemovalsIsKept` (Swift Testing): with a swipe write held, `add()` waits; the user types "Quatre" meanwhile; after release the store holds the added "Trois", and the field still reads "Quatre". Without the fix the last `#expect(model.draft == "Quatre")` fails (the field was cleared to ""); the test commit precedes the fix commit. Cloud cannot build the app: CI is the first compile.

**Adversarial review (Opus 5.5): APPROVE** — head 21c134c

Delta reviewed since 5d29999: merge 72d6d34 and 21c134c.

1. **Low**, App/SwiftHFRTests/PseudoLists/PseudoListTests.swift:141, and the message of commit 21c134c. The commit says the trait makes the suite "fail after 5 minutes instead of hanging the job". That only half holds. Swift Testing's `.timeLimit` records the timeout issue as soon as the limit passes, which helps diagnosis. It then cancels the test's task group, but a task group waits for all its child tasks before it returns. A body stuck in `gate.wait()` (a DispatchSemaphore, which ignores cancellation) or in `await removal.value` (an unstructured task's value does not pass cancellation through) never finishes, so the job would still hang. Keep the trait, which matches the other app suites. Do not count on it to unblock CI, and reword the claim if it is repeated on the PR.

No hang path found in the new test or in `add()`:
- **One gate, one waiter.** `open()` signals once, and the semaphore can block only one save. In `textTypedWhileAnAddWaitsForRemovalsIsKept`, only the removal's save can run while the gate is closed. `add()` calls `settleRemovals()` first, which waits for `removalTail` to finish. That tail finishes only after `open()`, and `open()` clears `closed`, so the add's save never blocks.
- **Race with `open()`.** If `open()` runs before the removal's save reaches its check, the save sees the gate open and does not wait. The leftover semaphore count belongs to that test's instance only, so it is harmless.
- **Thread starvation.** The semaphore blocks a cooperative thread (the store actor). `open()` is called from the main actor, which is not part of the cooperative pool. Even if the three gated tests together held every cooperative thread, each can still reach `open()`, so they cannot deadlock.
- **Bounded loops.** The `Task.yield` loops run 20 times. `settleRemovals` ends once `pendingRemovals` drops to 0 after the tail finishes.

`@MainActor @Suite(.timeLimit(.minutes(5)))` on a struct is the exact form already used by eight app suites, for example ContentLoaderTests.swift:5.

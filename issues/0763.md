# Issue #763: [SwiftHFR] Fixture anonymizer: an unbalanced </span> inside a signature lets the text after it survive, and check ignores attributes

### Summary
As a maintainer publishing captures, I want the anonymizer and its check to close every way member text can survive a signature, so that no pseudo or personal text reaches a public fixture.

### Facts (independent leak check of the #267 batch, 2026-11-10; both pre-existing, not caused by that change)
1. **Unbalanced `</span>` in a signature**: for a signature holding `… </span>TEXT<span class="x">`, `_find_para_blocks` closes the block at the stray `</span>`, so `TEXT` survives `anonymize`, and `check` reports 0 findings. Same behaviour before and after the #267 rule. Not seen in any capture so far (HFR's own markup is balanced), but a member's signature is member input.
2. **`check` is text-only**: a signature span whose text is the allowed placeholder but which carries a member value in an attribute (`title=`, an empty `<a href=…>`, `<img alt/src=…>`) passes `check`. `anonymize` itself removes the inner content, so no real input was found that leaves such an attribute.

### Scope
- Find the signature's end by its structure (the closing clear div and the `span.signature` end at the same depth), not the first `</span>`; a test with the unbalanced input.
- `check` also asserts the signature span holds no element other than the allowed head and tail, and no attribute values beyond the span's own class.
- Re-run `check --corpus` on the whole corpus.

No real leak found: every committed fixture passes the independent check. A hardening of the publishing tooling, not a vulnerability of the app.

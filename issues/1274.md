# Issue #1274: [Legacy 4.0.x + SwiftHFR] Composer: pick and upload several photos at once (up to 6, img3 limit)

### Summary

As a poster, I want to pick several photos at once in the composer's "Insérer une image" panel and have them all uploaded and inserted, so that I do not repeat the picker → upload → insert loop once per photo.

_Operator request, 2026-11-19. The img3 server (Chevereto v4.5.x) is configured to accept **up to 6 files** in one go: the app should allow up to 6._

### Today

- **Legacy** (`HFRswift`, 4.0.x): `ReplyPhotoLibraryPicker` (`HFRswift/Swift/AnswerView.swift`, around line 3082) wraps `PHPickerViewController` with `config.selectionLimit = 1`, and its coordinator only reads `results.first`, loads one `UIImage` and calls `onPick(image)`. The panel has a single `isUploading` flag and one "Upload en cours..." spinner (around lines 2789-2868).
- **SwiftHFR** (`dev-swift`): `ImageUploadView` (`App/SwiftHFR/Composer/ImageUpload/ImageUploadView.swift`) uses `PhotosPicker(selection: $photo, matching: .images)` with a single `PhotosPickerItem?`; `ImageUploadModel` uploads one prepared image at a time (`ImagePreparer`, `ImageUploadServices`).
- The Chevereto API V1 upload (`POST /api/1/upload`, capture `U01`) takes **one file per request** (`source`): several photos mean several requests, not a single multi-file call.

### Proposal

- **Picker**: allow multiple selection, limit **6** (legacy `selectionLimit = 6`; SwiftHFR `PhotosPicker(selection: [PhotosPickerItem], maxSelectionCount: 6, selectionBehavior: .ordered, matching: .images)`). Keep the limit in one constant (or a setting / remote value) so it can follow the server configuration.
- **Upload**: one request per photo, in selection order, **sequential or with a small concurrency (2)** to stay polite with the server and its flood protection; each photo goes through the same resize (« Dimension maximale ») and preparation as today.
- **Progress**: "Envoi 2/5…" plus a per-photo state (waiting, uploading, done, failed); the user can cancel what is not sent yet.
- **Insertion**: once done, insert the BBCode of every successful upload, in selection order, one per line, with the current BBCode mode (image / link / thumbnail); each upload also lands in the history (LOT-103), and in the delete-link store once #1050 exists.
- **Partial failure**: insert what succeeded, list what failed with a "Réessayer" for those only; never insert a broken link.
- **Camera** stays single-shot.
- **Limit reached / server refusal**: if the server answers a rate or quota error, stop the queue and say so plainly (message to capture, see below).

### Open questions

1. Is the "6" a per-batch limit of the web uploader, a flood-protection limit (uploads per minute / hour), or both? It decides whether the app may send 6 requests back to back. To check in the img3 Chevereto admin (Settings › Upload / Flood protection).
2. Insertion layout: one image per line, or side by side on one line (HFR shows `[img]` inline)? Operator's choice.
3. Should the selection order be kept (`.ordered`), or the library order?

### Captures needed

- The answer to a 7th upload in a row (or whatever the flood limit is) from the app's key, if the limit is a flood protection: status, JSON error code and message. Operator go needed (it publishes images on img3; use throwaway 16×16 images as in #302).

### Acceptance criteria

- [ ] Legacy and SwiftHFR: picking 1 to 6 photos uploads and inserts all of them, in order; the picker refuses a 7th.
- [ ] Progress "n/N", cancel, and partial-failure retry work; a failed photo never inserts a link.
- [ ] Each uploaded photo appears in the upload history.
- [ ] SwiftHFR: the queue logic lives in `ImageUploadModel` (`@Observable @MainActor`), tested with Swift Testing (all succeed, one fails, cancel mid-queue, limit), each test shown to fail without the change; UI strings in French; VoiceOver reads the progress.
- [ ] Checked on device with 6 full-size photos (memory and time acceptable).

## Analysis (read-only, sub-orch) 2026-11-07

Read from `origin/dev-swift` @ `4b1e77f`; legacy @ `2440d79`.

### SwiftHFR today
- **No link menu is implemented.**
  - `ReaderWebController.swift:108` sets `webView.allowsLinkPreview = false`.
  - The `WKUIDelegate` extension (`:341-368`) implements only `createWebViewWith`; there is no `contextMenuConfigurationForElement`.
  - What a long press shows today is WebKit's fallback with previews off. It must be checked on device: if it offers an "Open" or "Share" sheet, that sheet bypasses the app's routing.
- **A tap** goes through `decidePolicyFor` (`:342-353`, `.linkActivated` only) → `events.link` → `TopicReaderModel.action(forLink:defaultBrowser:)` (`TopicReaderModel+Links.swift:28-33`):
  - forum topic or MP → in-app reader (LOT-137, `ReaderTarget(link:)`);
  - profile → the LOT-116 sheet;
  - any other http(s) link → `SFSafariViewController`, or the default browser (LOT-119 setting);
  - any other scheme → ignored.
- **Videos** (LOT-035/071) are `<button class="video">` placeholders, not links (`TopicHTMLBuilder.swift:174-183`), so a long press finds no `linkURL` on them.

### Legacy @ 2440d79: no link menu
- `MessagesView.swift:1242-1278` implements `contextMenuConfigurationForElement`, but `imageURLForContextMenuElementInfo` (`:2147-2154`) returns nil for any link that is not an image URL, which ends in `completionHandler(nil)`.
- Only **image links** got a menu: "Ouvrir l'image", "Save to Photos", "Copier le lien".
- So this issue is a **(b) UX addition** (ROADMAP M5 / AGENTS §4 H.2), not parity. The spec and a GAP row must say so explicitly.

### What WKWebView offers
- `webView(_:contextMenuConfigurationForElement:completionHandler:)` gives `elementInfo.linkURL`. We return a `UIContextMenuConfiguration(identifier:previewProvider: nil, actionProvider:)` built from app actions.
- `allowsLinkPreview` most likely has to be **true** for WebKit to consult the delegate. With it off, WebKit falls back to its own sheet. Verify on device before relying on either.
- **The preview must stay nil.** With previews on and no configuration, WebKit renders the destination in a preview: a request to a member's URL that nobody consented to. So always return our configuration (nil provider) or an explicit empty menu, and implement `contextMenuForElement:willCommitWithAnimator:` as a no-op so committing never navigates.

### Proposed menu (long press on an `http(s)` link)
Title: the link's host, from `URL.host()`, never page text.
1. **Ouvrir**: `events.link(url)`, the same routing as a tap (reader, profile, in-app Safari or default browser).
2. **Copier le lien**: `UIPasteboard.general.url = url`, then the reader toast ("Lien copié", like the LOT-087 Link handler).
3. **Ouvrir dans Safari**: `UIApplication.shared.open(url)`. Caveat: iOS may hand a universal link to its app instead of Safari; there is no public option to force Safari. Use the label "Ouvrir dans le navigateur" when the default-browser setting is on.
4. **Ouvrir dans l'app**: `UIApplication.shared.open(url, options: [.universalLinksOnly: true]) { opened in … }`. If `opened == false`, fall back to entry 3 (operator's wording), or show a toast "Aucune app n'ouvre ce lien"; to choose.

**What "Open in app" can and cannot do without new entitlements or an app list**
- `.universalLinksOnly` needs no entitlement and no `LSApplicationQueriesSchemes`.
- It only reports *afterwards* whether an app took the link. The app cannot know in advance whether an app is installed, nor its name. So the entry is generic ("Ouvrir dans l'app") and always shown for external https links.
- A named label ("Ouvrir dans YouTube") is possible without a new list for the providers LOT-035 already recognises (`EmbedProvider` → `TopicHTMLBuilder.providerName`: YouTube, Vimeo, Streamable). It is only a label, and it still falls back if no app answers.
- Custom schemes (`youtube://`) would need `LSApplicationQueriesSchemes` (an app list): out of scope.
- Hide "Ouvrir dans l'app" for forum links: the app is the forum's app.

Optional: **Partager…** (`UIActivityViewController`, legacy shared permalinks this way). Image links (`a` around `img.hfrplusimg`, or `a.image-link` from `reader.js:15-23`) can keep the same menu; the LOT-109 viewer stays the tap action.

### Security
- No preview, so nothing is requested on a long press.
- Copy, Safari and app hand the URL to the system. Safari uses its own cookies; the app's `HFRSession` is never involved.
- "Ouvrir" reuses the tap routing, so a forum link reaches the reader through `HFRLinkRoute` / `ReaderTarget` only. That is the existing LOT-137 rule: only forum topic/MP routes load with the session, and everything else opens outside. A member's external link is never fetched by the app, with or without the session.
- Accept only `http`/`https` `linkURL`s. Never offer `hfrreader:`, `javascript:`, `data:` or `file:`, and do not echo `mailto:` beyond "Copier".
- Never use `elementInfo` for anything but the URL. Keep `upgradeKnownHostsToHTTPS` and the non-persistent store as they are.

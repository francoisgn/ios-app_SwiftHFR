### Findings

**P1, medium-high: the MPStorage thread is identified by its public subject alone.**
- Code:
  - `Packages/HFRKit/Sources/HFRParsing/MPStorage/MPStoragePageParser.swift:18-19`: the first matching row wins.
  - `:88-90`: `isStorageSubject`.
  - `:98-101`: `hidingStorageThread` removes every matching row. It is used by `App/SwiftHFR/Messages/PrivateMessageSource.swift:29`.
- Scenario:
  - Another member sends you an MP with the storage subject. The app hides it from your list: you cannot read, answer or delete it in the app.
  - If that row is found first, `MPStorageTransport.swift:117` throws `.editLinkMissing`. `MPStorageSync.locate` (`:158-172`) does not treat it like `.notAddressed`, so the blocklist, bookmark and MP-flag sync stays broken until the thread is deleted from a browser.
  - Fixture `R333b` already has two storage-subject rows. Today's tests pin « hide every row » and « first row wins ».
  - Legacy `MPStorage.m:713-723` @ 87fe0d1c has the same finder but never hides the row.
- Fix:
  - Hide only the located thread: the cached thread whose first message carries the account's edit link.
  - `findThread` returns every candidate, and the transport skips a candidate without an edit link.
  - A foreign storage-subject row stays visible.
- Tests: `MPStorageTransportTests.skipsForeignThreadWithStorageSubject`, `MPStorageThreadHidingTests.keepsForeignStorageSubjectRowVisible`, both red on today's code.

**P2, low: flag writes lack the login fence.**
- Code: `Packages/HFRKit/Sources/HFRClient/Flags/TopicFlagFlow.swift:86-103,118` runs `confirm(check)` then the write, with no `hashCheckSeed()`.
- Compare: `Polls/PollVoteFlow.swift:50-52` and `MPDelete/DeletePrivateMessageFlow.swift:53-63` do seed it.
- Scenario: a logout or re-login in the one-hop window sends `addflag` without cookies, and HFR answers with the success bytes (`P03q` = `P03a`, #314).
- Fix: seed before the check, use `PostingSession.send(since:)`, and add `TopicFlagError.sessionChanged`. A test shows the write refused when the session changes between the check and the send.

**P3, low-medium: an unreadable account-sync state is overwritten.**
- Code:
  - `Packages/HFRKit/Sources/HFRStorage/AccountSync/AccountSyncState.swift:41,78`: a state of an unknown version, or an undecodable one, is read as « off, nothing known ».
  - It is then saved over at `AccountSync.swift:358,369`.
- Scenario: after a rollback, the switch reads off and `honouredDeletedAt` / `hadLocalAccounts` are lost. No tombstone is written while the synchronizable item keeps the accounts, so a device can bootstrap again despite an earlier opt-out.
- Fix: tell an absent state from an unreadable one, and never overwrite an unreadable state (ESSENTIEL persistence rule). Tests: absent vs unreadable vs future version.

**P4, low: the legacy accounts archive is decoded without secure coding.**
- Code: `Packages/HFRKit/Sources/HFRStorage/LegacyImport/KeychainLegacyAccountSource.swift:59` sets `requiresSecureCoding = false`. The data comes from the app's own Keychain item.
- Fix: decode with secure coding, restricted to the expected classes. A test shows an archive with an unexpected class rejected and the legacy fixture still imported.

**P5, unverified lead: `http` is accepted on the forum host.**
- Code:
  - `Packages/HFRKit/Sources/HFRNetwork/Endpoints/HFREndpoint.swift:68-76` (`absoluteURL(href:)`) and `Session/SessionHostPolicy.swift:19` accept `http`.
  - `App/SwiftHFR/Navigation/ForumDataSource.swift:52-57` sends the result without an https check, unlike `ReplyPosting.swift:62-63`.
- Reachability: only if a parser hands back an absolute `http://forum.hardware.fr…` link (LESSONS 37). No such path was found, but none was proven absent either.
- Fix: upgrade to `https`, or refuse, on the forum host at the endpoint layer. A test covers an absolute http href.

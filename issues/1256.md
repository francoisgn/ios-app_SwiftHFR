# Issue #1256: [SwiftHFR] Smiley and GIF pickers: each thumbnail builds its own image loader, so its own URL sessions

### Summary
As the maintainer, I want the smiley and GIF pickers to share one image loader per picker (or per app), so that showing a grid of thumbnails does not create a fetcher, a transport and URL sessions for each cell, with no connection reuse to the same host.

### Evidence (`dev-swift` @ 90b23273, read from the code, not measured)
- `App/SwiftHFR/Smileys/SmileyThumbnailView.swift:49-51`: `makeCoordinator()` returns `Coordinator(loader: source == .gif ? .gif() : SmileyImageLoader())`. Each coordinator, so each thumbnail view identity, builds its own `SmileyImageLoader`. That loader owns a `ReaderImageFetcher()` with its default `AnonymousTransport`, and its URL sessions (`URLSessionTransport`: a base session plus the no-follow session).
- The comment at `:58` ("Built once per cell: a loader per update would leak an HTTP session each time") avoids one build per update, not one per cell.
- Callers:
  - smiley picker grid and preview: `SmileyPickerView.swift:280,298`;
  - GIF picker grid and preview: `GifPickerView.swift:86,149,151`.
- The decoded-image cache is already shared (`SmileyImageLoader`'s static `NSCache`), so only the transports are duplicated.

### Scope
- Build one loader per source (forum smileys, GIF), shared by the cells: a static per source, or one owned by the picker and passed down.
- Keep the host rules as they are: `allowsThirdParty: false` for smileys, `.gif()` (Giphy CDN only) for GIFs.
- Same pattern as #1249, where the image panel's thumbnail loader was moved to one per panel.

### Acceptance criteria
- Showing N thumbnails builds at most one `ReaderImageFetcher` per source, checked by a test through a counting seam or by construction.
- The loader's host filter stays the same for each source (a test, as in #1249's `thePanelsLoaderFiltersOnTheRehostHost`).

# Issue #1194: [SwiftHFR] app tests: timing-based tests in Composer and MPStorage can pass without exercising their case

- State: closed
- Author: francoisgn · created 2026-11-18T20:09:45Z · updated 2026-11-28T06:40:40Z
- Labels: type: chore, priority: high, difficulty: medium, area: app, origin: audit, m4-review: quality
- Source: https://github.com/ezzz/HFRnow/issues/1194

### Summary
As the maintainer, I want tests that wait on a fixed sleep to wait on a signal, so that they cannot pass without running the interleaving they document (LESSONS 2) and do not join the flaky list (#704, #772, #521 were the same pattern).

### Scenario
On a loaded CI runner, the `handle` task of the blocklist test has not queued its edit when the gate opens; the final lists are the same in both orders, so the test passes without the "edit queued behind start's read" case. In `ComposerPlacementTests`, a layout pass slower than the sleep makes a "nothing changed" assertion pass before the value could change.

### Evidence (`7a61018f`)
- `App/SwiftHFRTests/MPStorage/BlocklistSyncTests.swift:251-254`: `let handling = Task { await sync.handle(…) }`, `try await Task.sleep(for: .milliseconds(50))`, `await gate.release()`.
- `App/SwiftHFRTests/Composer/ComposerPlacementTests.swift:96-100` (and `:122`, `:153`, `:304-368`): `Task.sleep(200 ms)` then a negative assertion.
- `App/SwiftHFRTests/Composer/ArchivedDraftsTests.swift:198`: same shape.

### Fix
Replace each sleep with a deterministic signal (a second gate or a counter the fake remote exposes when the edit is queued; a layout probe callback for the hosted tests). A negative is asserted after a positive event that proves the pass ran.

### Proof
Mutation: remove the serialization the BlocklistSync test protects, or the inset rule in `ReaderComposerPresenter.docked`; the rewritten tests fail on every run (not checked today: no mutation was run in this review).

Rework model: Sonnet 5.5, reviewed by Opus 5.5.

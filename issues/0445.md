# Issue #445: [SwiftHFR] MessageContentNormalizer: superlinear parse time on repeated crossed tags

- State: open

### Summary

As a reader, I want a message made of many crossed tags (`[u][b]x[/u][/b]` on every line, the shape HFR's own toolbar produces when a member underlines then bolds) to render in time proportional to its length, so that a long post or its preview does not freeze the reader.

### Scope

Found by the LOT-097 code review (ADR 0014 §4, PR #444). HFR writes crossed tags crossed (`<span class="u"><strong>x</span></strong>`, `R41a` → `R20`); the reader parses a message twice (`MessageBlockParser.contentHTML`, then `MessageContentNormalizer.normalize(contentHTML:)`), and the second parse reopens the `<strong>` around everything that follows each crossed pair, so the `<strong>` count doubles and the normalizer's time grows superlinearly:

| Size of `[u][b]x[/u][/b]\r\n` repeated | normalizer (debug build) | page parse |
|---|---|---|
| 32 KB | 1.3 s | 0.4 s |
| 64 KB | 4.2 s | 0.7 s |
| 128 KB | 14.2 s | 1.3 s |

The output is right (it is what the browser shows for the posted message); only the time is at stake. LOT-097's renderer reproduces the reader's path on purpose, so the preview pays the same (LOT-152 renders off the main actor and debounced). The normalizer walks an explicit stack (LOT-034), so the cost is in SwiftSoup's tree builder, in the reconstruction of active formatting elements, or in the serialization of the doubled tree.

### Sources

`Packages/HFRKit/Sources/HFRParsing/Topic/MessageContentNormalizer.swift`, `MessageBlockParser.swift`; the shape in `HFRBBCodeWriterTests.linearWork` (last of `shapes(_:)`); `R20` `para2666649` for a real message with 13 crossed pairs.

### Acceptance criteria

- [ ] Measure where the time goes (tree builder, adoption agency, serialization) on the shape above at 32, 64 and 128 KB.
- [ ] Either bound it (a repair pass before the second parse, or a cap on the reopening) or record the limit in LOT-034's spec and HFR-PROTOCOL with the measurement, and say what the reader does with a message that exceeds it.
- [ ] A test on the shape with a bound that holds on CI.

Second shape, found by code review round 5 of #444 (ADR 0014 §4, commit 1eb50fa on #442): **deeply nested blocks**. `[quote]`×n or `[spoiler]`×n is a table in a table n deep, and **both** SwiftSoup parses (page parse and normalizer) grow quadratically in the depth, the writer staying linear:

| Nested `[quote]…[/quote]` | size | page parse | normalizer |
|---|---|---|---|
| 1 000 | 15 KB | 3.6 s | 3.8 s |
| 2 000 | 30 KB | 14 s | 14 s |

Debug build, Linux. Same conclusion as the crossed tags: the output is right, the time is at stake, the reader pays it on a posted message and the preview on a draft. A SwiftSoup parse cannot be cancelled, so LOT-152 skips the live preview above a depth or size it sets (an on-demand preview stays possible). Fixing it here means either a bound in the reader before the parse (depth or size of the HTML) or a cheaper tree builder for nested tables.

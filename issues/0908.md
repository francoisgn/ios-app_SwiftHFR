# Issue #908: [SwiftHFR] After a successful reply or edit (MP and topics), the reader refreshes and shows the new text

- State: closed
- Author: francoisgn · created 2026-11-15T12:20:51Z · updated 2026-11-27T22:42:13Z
- Labels: type: bug, priority: high, difficulty: medium, area: app, beta-test finding, origin: swift-feedback
- Source: https://github.com/ezzz/HFRnow/issues/908

### Summary

As a member who edits a message or posts a reply, I want the conversation to show the result right after a successful send, so that I never see the version from before the edit and do not have to tap the reload button. (Operator feedback on the latest iPhone build, 2026-11-15.)

### Observed (operator, 2026-11-15, MP)

- In an MP, the operator edited one of their replies and sent it, and the send succeeded.
- The reader still showed the message **as it was before the edit**.
- Only a manual reload (the round arrow at the top) showed the edited text.

### Expected

- **A successful send triggers a refresh**, for both a reply and an edit, in topics and in MPs. The reader shows the updated message:
  - for an edit, at the edited message;
  - for a reply, at the new message on the last page (LOT-084: page `max + 1`, `R24`/`R61d`).
- **Only on success**, that is HFR's own confirmation sentence (LOT-037, LOT-048).
- No refresh on a failure, a closed composer or a kept draft.
- An *unconfirmed* send keeps today's rule: reload to show what the forum holds, never send again.

### What the code already does (to explain the gap, not a guess at the cause)

- `App/SwiftHFR/Reader/Actions/MessageWriteModel.swift:76-84` (`editorDidClose`):
  - on `.sent` it calls `reader?.showConfirmation(…)`;
  - then it calls `await reader?.reloadPage(at: post)`.

  So a reload is requested after a confirmed edit, yet the operator saw stale content.

To check in the fix, with a test for each:
1. whether `reader` is still set in the **MP** reader when the composer closes (a weak reference released, or the MP reader taking another path);
2. whether `reloadPage(at:)` bypasses every cache (the HTTP cache and the reader's page cache) and re-renders the web view;
3. whether the reply path (new message) has the same gap.

### Acceptance criteria

- [ ] After a confirmed **edit** in an MP and in a topic, the reader shows the edited text at that message, without a manual reload.
- [ ] After a confirmed **reply** in an MP and in a topic, the reader shows the new message on the last page.
- [ ] No refresh after a failed send, a closed composer or a kept draft; an unconfirmed send reloads once, without sending again.
- [ ] Tests on the model (scripted poster: success → one reload of the right page; failure → none) and one hosted test showing the new text in the web view. The tests are shown to fail before the fix.

### If the MP path diverges (operator, 2026-11-15)

If the cause is that the MP reader takes **another path** than the topic reader (another write model, a reader reference set differently, another reload), the fix is **not** a patch on the MP side. The two paths are merged onto **one shared implementation**, the best of the two, and that version is reused wherever it applies. This is the consistency and reuse the end-of-M4 reviews look for, #775 (quality, refactor and consistency) and #836 (duplicates and factoring). The PR states which path was kept and why, and lists the other places that used the dropped path.

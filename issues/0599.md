### Summary
As a member composing a new MP, I want the formatting bar to stay still above the keyboard instead of moving up and down. Part of #592, under umbrella #414 (M4). Operator report, 2026-11-07.

### Analysis (#592)
- Reply and new MP share `ReplyComposerView`. The bar is a plain `VStack` child, not a `safeAreaInset` or a keyboard toolbar.
- A new MP moves focus from recipient, to subject, to text. The bar stays enabled while the recipient field has focus, and a tap on it runs `focused = .text`, which steals focus.
- This is the suspected cause of the bounce. It is a hypothesis: reproduce it first.

### Fix
- Anchor the bar to the keyboard: `safeAreaInset(edge: .bottom)` or the keyboard toolbar placement.
- Enable it only while the text field has focus.
- No layout jump when focus moves between fields, in both the reply and the new-MP composer.
- Coordinate with #429 (swipe-down saves the draft), which edits the same file.

### Tests
- A model or view test that the bar is disabled unless the text has focus, and that a bar action never moves focus off the recipient or subject field.
- Show that it fails without the change.

### Mac check
- New MP on iPhone with the keyboard up: recipient → subject → text, with no vertical jump.
- Reply composer unchanged.
- iPad with a hardware keyboard.

## Reproduction (mac/m2-lead repro) 2026-11-07: the bounce comes from the return key, not from the bar

**Build** `f9901d9` (origin/dev-swift). **Device**: iPhone 18 Pro simulator, iOS 27.0, portrait, software keyboard. A new MP composer, logged in. Nothing was sent: every run ended with Annuler → Supprimer le brouillon. Driven by a UI test while the simulator screen was recorded. The bar's position was read from every frame of the recording (the edge between the page and the bar, 3 px per pt). Harness notes: the build was signed ad hoc (`CODE_SIGN_IDENTITY=-`) instead of unsigned, because an unsigned build cannot use the keychain to log in. The runs with XCTest's `typeText` were checked again with taps on the on-screen keys, and the results below hold for those taps.

| Action (new MP, keyboard up) | Bar position | Bounce? |
|---|---|---|
| Tap Gras while the **recipient** has focus | still at 502 pt | no. Focus jumps to the text, which gets `[b][/b]` |
| Tap Gras while the **subject** has focus | still at 502 pt | no. Same focus jump |
| Tap Gras while the text has focus | still at 502 pt | no |
| Tap the recipient, subject and text fields in any order | still at 502 pt | no |
| Type in the recipient, subject and text (on-screen keys) | still at 502 pt | no |
| **Return key ("suivant") in the recipient** → focus goes to the subject | the keyboard and the bar **drop off screen and come back**, about 0.5–0.6 s | **yes** |
| **Return key ("suivant") in the subject** → focus goes to the text | same drop and return | **yes** |

Each return-key bounce was seen in two runs: once with `typeText("\n")` and once with a tap on the on-screen "suivant" key. A frame strip was checked by eye. The keyboard goes fully down, then slides back up with the bar.

### What this says about the cloud's assumed cause
- **The assumed cause is wrong.** A tap on a bar button while the recipient or subject has focus does **not** bounce.
- What it does do: it moves focus to the text and inserts the tag there. That is a separate problem. Disabling the bar outside the text, as the issue proposes, fixes it.
- **The bounce comes from `.onSubmit { focused = .subject }`** on the recipient (`ReplyComposerView.swift` `messageFields`), and the same pattern on the subject. The return key ends editing, so the keyboard starts to hide. Then the focus change brings it back.
- Anchoring the bar with `safeAreaInset` or a keyboard toolbar will **not** stop this, because the keyboard itself goes away. The fix must keep the keyboard up while moving to the next field.
- Candidates (not verified here):
  - set the next focus without letting the field end editing;
  - or handle return in UIKit (`textFieldShouldReturn` returning false, then `becomeFirstResponder` on the next field).
- Test to add: the bar's position does not change across a return-key move from the recipient to the subject to the text. A UI test that records the screen can show this; a model test cannot.

Not checked: a physical iPhone, the iPad with a hardware keyboard, and the reply composer, which has no recipient or subject field (no return-key move to test).

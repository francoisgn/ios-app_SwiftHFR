# Issue #1425: [SwiftHFR] Account sync: the shared copy can end with no main account, and a newer login from the copy drops the device's avatar

- State: open
- Author: francoisgn · created 2026-11-27T23:10:29Z · updated 2026-11-27T23:10:29Z
- Labels: type: bug, priority: low, difficulty: easy, area: storage, status: ready, origin: audit
- Source: https://github.com/ezzz/HFRnow/issues/1425

### Summary
As a user setting up a new device with the account sync on, I want it to pick the main account the other devices use and to keep the avatars it already has, so that a merge never leaves the shared copy without a main account nor blanks an avatar.

### What happens (after #1406, head df8833d)
Non-blocking residuals of the final adversarial review of #1406 (Fable round 4):
1. **No main in the copy.** `AccountSyncMerge.swift:53-54,66`: an entry kept from the copy keeps the copy's main flag, and this device's flag replaces them only when its main is an entry of its own side. Scenario: A logs in `w` as main (copy main `w`); B, whose main is `x`, logs in `w` again with new credentials as non-main. B's `w` is own-side with B's false flag, B's main `x` is a copy entry, so the copy's flags are kept: no main. A then takes `w` from the copy with that false flag; a new device C bootstraps with `x`. Same when the copy's main is removed. The LOT-173 spec sentence "the copy holds one main across merges by every device" is false there.
2. **Avatar dropped on a newer login from the copy.** `AccountSyncMerge.swift:50`: taking the copy's newer (different) login replaces the device's `avatarData` (and `hashCheck`) with the copy's nil; only the same-login adoption keeps them. The avatar is safe to keep; whether `hash_check` survives a new login is not established (HFR-PROTOCOL), so it is left as is unless a capture shows it.

### Proposed fix
1. When no merged entry is main, fall back to this device's own flags. Test: the scenario above, C bootstraps with `w`.
2. Keep the device's avatar when the copy's newer login has none.

Refs #1390, #1406.

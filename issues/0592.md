### 1. Bar size, density, text size
- Current: `App/SwiftHFR/Composer/FormattingToolbar.swift:10-17` (horizontal `ScrollView`, `HStack(spacing: 2)`, `.background(.bar)`), button `:47` `frame(minWidth: 44, minHeight: 44)`, colour swatch `:35` fixed 24x24. Icons carry no explicit font: they inherit the root `.scaledFont(.body)` (`SwiftHFRApp.swift:32`, `appTypography`, `ListDensity.swift:94-100`), so the **glyph** follows `textScale` and Dynamic Type if the environment font reaches the sheet (to reproduce on the Mac: 70 % and 130 % in Réglages).
- Not scaled: the 44 pt frame and the 24 pt swatch are fixed (no `@ScaledMetric`, no `textScale.scaled(_:)`). `listDensity` is **never read** in `App/SwiftHFR/Composer/` or `Smileys/` (grep): compact density has no effect, and the composer has no density rule at all.
- Legacy: bar was glass capsules, icon `font(.system(size: 17, weight: .medium))` in an 18 pt frame + 8 pt padding = 34 pt (`AnswerView.swift:868-891`), not scaled by `textScale`. So Swift is not smaller than legacy; "slightly small" is the 17 pt glyph with a 44 pt cell and no padding above/below.
- Gap/cause: size constants are literals. Fix: derive cell side and swatch from `@ScaledMetric` x `textScale.factor` (the `ListDensity` pattern: regular 44, compact 40, never below ~40 for touch), glyph `.scaledFont(.title3)` (regular) / `.body` (compact). Add a `ListDensity` member for the bar and a layout test like `ListDensityLayoutTests`. Decision for the operator: how much bigger "regular" should be (proposal: 48 pt cell, `.title3` glyph).

### 2. Bar not locked vertically (new MP)
- Reply and new MP use the **same** view, `ReplyComposerView.swift:53-74`: `VStack { banners; messageFields (MP: Destinataire + Sujet TextFields); editor (TextEditor); FormattingToolbar }`. The bar is a plain `VStack` child, not a `safeAreaInset(.bottom)` or a keyboard-placement toolbar, and the page has no outer `ScrollView`. It therefore rides on the keyboard safe-area animation of the whole stack.
- Difference with a reply: a new MP opens on the **recipient** field (`firstEmptyField`, `:308-312`), then Sujet, then text, so focus moves TextField -> TextField -> TextEditor. Each change can re-present the keyboard (different keyboard/predictive bar height) and the stack, bar included, re-lays out and bounces. A reply focuses `.text` directly.
- Also: the bar stays enabled while `recipient`/`subject` has focus, and a tap then calls `refocus()` = `focused = .text`, which moves focus and the keyboard again. That is the likely "moves up and down" trigger. **Not proven: reproduce on the Mac** (new MP, tap through the three fields, then tap a bar button; also with the hardware-keyboard shortcut bar on iPad).
- Fix proposal: pin the bar with `.safeAreaInset(edge: .bottom)` on the editor (or `ToolbarItemGroup(placement: .keyboard)`), enable it only when `focused == .text`, and do not steal focus from the recipient/subject. Test: model-level (`isEnabled` depends on the focused field) plus a hand check.

### 3. URL in two forms
- Today (`ComposerFormattingModel.swift:60-74`): with a selection and a clipboard http(s) URL -> alert, then `[url=<clip>]selection[/url]` (`ReplyTextInsertionEngine.wrapSelectionWithURL`); with a selection and no URL -> `[url]selection[/url]`; with no selection -> `[url][/url]` with the caret inside, or, if the clipboard holds any text, the generic "insert clipboard text with Lien?" alert giving `[url]clipboard[/url]`. **`[url=…]…[/url]` with no selection is never offered**, and the user cannot choose the form.
- Legacy @ 2440d79 (`Classes/HFRTextView.m:205-262`, alerts; `:308-336` handler): clipboard + `url` tag, **selection** -> one choice `[url= Oui ]`; **no selection** -> two choices `Oui [url=XXX]` and `Oui [url]XXX[/url]` (tags 668 / 667). The Swift port dropped the two-choice alert (`ComposerFormattingModel.Pending.link` is selection-only).
- Fix: a `confirmationDialog` (not an alert, three buttons) when `.bbCode(.url)` is tapped: "Lien avec nom `[url=adresse]nom[/url]`" / "Lien simple `[url]adresse[/url]`" / "Annuler". With a selection: selection = name (form 1) or address (form 2). Without a selection: insert the clipboard URL if any (legacy), else empty tags with the caret inside the right slot. Both forms are rendered by HFR (HFR-PROTOCOL BBCode round trip, "`url` -> `a.cLink` (both forms)", `W61`/`R95c`): no capture needed. Engine functions are pure and testable.

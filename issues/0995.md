**mac/M1: 80 Mac runs, no failure; what the traces prove, and a proposed fix**

| Run set (iOS 27.0 simulator, `dev-swift` c78a1a56 + trace prints) | `aRefreshReopens…` |
|---|---|
| alone, 10 busy loops (cold, 2.6–5.4 s) | 🟢 20/20 |
| `ReaderInsetsWebTests` + `ReaderPageEndWebTests`, 10 busy loops (warm, 0.75–1.5 s, CI's timing) | 🟢 20/20 (and `ReaderPageEndWebTests` 20/20) |
| `ReaderInsetsWebTests`, 30 busy loops | 🟢 40/40 |

**Proven by the traces** (KVO of `contentOffset` and each `WebKitResetWatch` step):
- 76/80: commit (offset 900) → ready (watch waits) → reset (900 → −100) → restore (900). Correct.
- 4/80: the reset came before ready. In 3 of them the "reset" is `−100` then `900` **in the same UI turn (< 0.1 ms apart)**: WebKit's first layer-tree commit puts the scroll view at its top, then applies the scroll position the new page asked for. That position is 1000, inherited from the old document's offset. So the scroll view reaching its top does **not** mean the page was reset. The page and the scroll view are reconciled by asynchronous messages in both directions after that commit, and the watch sees only the UI side.

**Hypothesis for job 133859276257 (not reproduced):** the UI side's reset ("top") reaches the page **after** the restore's `scrollTo(1000)` (two frames after the action is sent). It puts the page back to 0 once loaded, which is what both CI failures show (`scrollY` 1000, then 0).

**Proposed fix (product, `reader.js` + `ReaderWebController+Scroll`):** the restore, and the landing, which goes through the same watch, wait for **the page to agree with the scroll view** before they scroll. Native passes the scroll view's current reading top. The page scrolls once its own `scrollY` equals it, which means the reset reached the page, with a frame cap as a safety net. This is the right signal, not a sleep. It is the same agreement `restored` checks in the test.

What I cannot give yet: a test that **fails without** the change. 80 runs did not hit the order, and making WebKit deliver the reset late on purpose is not deterministic from a test.

- (a) Land the fix above with its tests on the agreement rule (pure JS logic plus one web test), the 80-run proof, and CI as the arbiter.
- (b) Or first merge a diagnostic: the test's failure message records the offset history, so the next CI failure shows the order.

I lean to (a)+(b) in one PR. I am leaving #995 claimed and going on with #1015 / #979 meanwhile.

### Summary

As the maintainer, I want the MPStorage thread to be hidden **everywhere** by **one shared rule**, so that no screen, orientation or device shows it. The operator saw it **in landscape but not in portrait** on the same build, which suggests the MP list is built by more than one code path. (Operator, 2026-11-17 23:00 Paris.)

### Facts

- On dev-swift there is **no filter** for the storage thread in the app or the client: a `git grep` of `MPStorageDocument.subject`, `isStorageSubject` and `MultiMP` finds only the MPStorage transport and parser. So its absence in portrait does **not** come from a hide rule. Something else differs between the portrait list and the landscape list on that build:
  - a different list implementation or data source;
  - segment assignment (« MP » vs « MP multiples »);
  - paging, how many rows are loaded;
  - or the row was simply out of view.
  Find which, with `file:line`. Do not assume.
- The operator's build predates #955 (merged 2026-11-17), after which a large iPhone in landscape no longer splits. The landscape path seen there may be the iPad / regular-width split path.

**Portrait vs landscape, from the code.** No code path depends on orientation: a single `MessageListModel` feeds both hosts. The only list-shape input is `display` (`MessageListModel.swift:26`, set from the setting `mp_list_display` at `:171,:182`): « Tout en un » shows page 1 only, « Deux listes » filters by segment and, when the segment is empty on the page, loads later pages (`:148-158`, bounded). The storage thread is a 1-to-1 thread (« MP » segment) and sits on an older page (R333b: page 2, row 1). So, from the code alone, a layout that auto-advances or a person scrolled/paged to the page holding it can see it where another list on page 1 cannot. I could not confirm which one the operator had (no orientation-specific code, no filter in either path): that stays a device observation, not a code fact. The #955 change (large iPhone landscape no longer splits) only changes the navigation container, not the list model.

**Duplicates for #836:** none found. There is one list implementation and one source, so nothing to record there.

**Fix:** filter once at that source (`hidingStorageThread()`, PR #1076), which every row-based path above inherits. HFR's header badge number stays HFR's.

### Summary

As a reader, when a member posts a rehosted image in its **medium** size (a lighter rendition, so the page stays light), I want the viewer to open the **full-size** image, so that a screenshot posted that way is readable on a phone. Today it stays an unreadable « pixel soup ». (Operator feedback, 2026-11-15, from the HFR+ topic: members asked for it on the evening of 2026-11-15, and the maintainer confirmed the legacy app was meant to do it on img3 and a few other hosts, but it does not work there either.)

### Observed

- A member posts an `img3.super-h.fr` image as the **medium** rendition: the file name carries `.md.` (`…/images/<yyyy>/<mm>/<dd>/<name>.md.jpg`).
- In the reader the picture is small, which is intended. Opening it in the viewer still shows the medium file, so the text in the screenshot cannot be read.
- Members say that removing `.md` from the URL gives the full image. Legacy has the same gap, though the maintainer says it was meant to work.

### Today (dev-swift)

- `ImageHostTable.fullSizeURL` (`Packages/HFRKit/Sources/HFRNetwork/ImageHosts/ImageHostTable.swift:64`) upgrades a thumbnail to the full image in the viewer (LOT-056, LOT-109). For `img3.super-h.fr` the only rule removes `.th.` (`ImageHostTable.swift:20`, `.fileNameMarker(pathPrefix: "/images/", marker: ".th.")`).
- There is **no rule for the medium marker `.md.`**, so the viewer opens the medium file.

### Requested

1. Add the medium marker to the `img3.super-h.fr` rule: `.md.` is removed like `.th.`. The viewer then opens `<name>.jpg`, and the reader keeps showing the medium in the post, as the poster intended.

3. If the full-size file fails to load (404, refused), the viewer falls back to the medium.

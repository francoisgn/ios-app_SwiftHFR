# Issue #342: [SwiftHFR] PostingForm: refuse a submit when the session changed account since the form was loaded

### Summary

Follow-up to #308 / PR #315. Two cases need fixing:
- A `PostingForm` loaded before an account switch in the same `HFRSession` still carries the old page's `hash_check` and `pseudo`.
- A `PostingForm` loaded before a logout has the same problem.

Submitting such a form sends it through the new cookies. HFR refuses it with the bad-token answer (`W17b`), so nothing crosses accounts, but the user sees HFR's refusal instead of a clear local error.

### Scope
- Keep the `HashCheckSeed` taken by `PostingFlow.loadForm` in `PostingForm` (`Packages/HFRKit/Sources/HFRClient/Posting/PostingForm.swift:29`).
- `submit` refuses locally, before any request, when the session no longer matches the seed's identity (`userKey`). It returns a typed error, for example `sessionChanged`.
- Optional nits from the same review, if this PR already touches these files:
  - `Posting/HashCheckSeed.swift:4` duplicates the concept of `Session/RefreshUpdate.swift:6` (`RefreshSeed`). Move it to `Session/` or cross-reference the two.
  - The doc comment of `Tests/HFRClientTests/Support/ScriptedFlagSession.swift:6` still says "A flag session". The two scripted sessions also share the same login-adoption code.

### Sources
- The Fable review on #315 (finding 1, low).
- PR #315, section "Out of scope".
- The app uses one `HFRSession` per account (`AccountsModel`), so this needs a re-login with other credentials into the same session, or a logout. That makes this low priority.

### Acceptance criteria
- A test loads a form, adopts a login of another account (or a logout) in the session, then submits. It expects the local error and no POST.
- A same-account re-login does not trigger the local refusal. The refreshed token is HFR's to judge, as in #315.
- `swift test` passes; SwiftLint passes.

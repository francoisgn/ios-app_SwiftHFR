# Issue #566: [SwiftHFR] Topic reader stuck on "Chargement des messages" until Actualiser

- State: closed
- Author: francoisgn · created 2026-11-07T11:44:00Z · updated 2026-11-09T15:04:15Z
- Labels: type: bug, priority: high, difficulty: medium, area: app, beta-test finding, origin: swift-feedback
- Source: https://github.com/ezzz/HFRnow/issues/566

### Summary
Some topics open on "Chargement des messages" and the spinner never goes away. "Actualiser" (the reload arrow) unblocks them. MPs and group MPs are not affected. This is a critical bug: the operator cannot test the reader on a device.

### Report
- Operator, 2026-11-07, logged in, on device.
- Example: Catégories → Apple → "Super HFR+ l'app du forum pour iOS". It is a large topic with many pictures and several pages.
- The spinner stays forever. Pressing "Actualiser" loads the page's messages.

### Analysis
Static read of `dev-swift` @ d4b15a8 by `ext/francoisgn-suborch-1`; not reproduced yet.

**What the report rules out:**
- "Actualiser" is disabled while a load runs (`TopicReaderView.swift:72-73`). It could be pressed, so `isLoading` was false and the fetch was not hanging.
- The same label is shown in two states (`TopicReaderView.swift:145-163`):
  - (A) `page == nil && error == nil`;
  - (B) `page != nil && readyToken == nil`.
- `ready` is posted by `reader.js:196-201` once `images` returns. It waits for no picture and no scroll. The LOT-186 scroll and inset work runs after `ready` (`ReaderWebController.swift:236-247`), so it cannot hold the spinner.

**Hypotheses, most likely first:**
1. **H1: `onDisappear` aborts the navigation, and nothing reloads it (state B).**
   - `TopicReaderView.swift:134-141` calls `controller.stopLoading()`, then `webView.stopLoading()` (`ReaderWebController.swift:134-139`).
   - When the view appears again, `show(document)` returns early because the token is unchanged (`ReaderWebController.swift:118`), and `model.onAppear()` returns because `page != nil` (`TopicReaderModel.swift:110-113`).
   - Large topic pages widen the window before DOMContentLoaded.
   - The 3-column `ReaderColumn` with `.id("\(topic.id)#\(readerGeneration)")` (`RootTabsView.swift:141-151`) gives a different lifecycle than `MessageReaderColumn`.
   - `FilteredPostsView.swift:127-131` has the same pattern.
2. **H1b: a replacement view shares the cached model, and the old view's `onDisappear` cancels the new load (state A).**
   - The model is shared through `NavigationModel.reader(for:)` (`:89-104`).
   - `model.cancel()` (`TopicReaderModel.swift:295-302`) leaves `page == nil`, with no load and no error.
3. **H2: a failed main-frame navigation goes unnoticed.** There is no `didFail` or `didFailProvisionalNavigation` in `ReaderWebController` (`:341-368`).
4. **H3: an unrequested `.cancelled` from the transport leaves state A.** `TopicReaderModel.swift:387-388` handles it with `break`.

**Suspected origin:**
- The trap has been latent since LOT-083 (ad071f0).
- LOT-125 (#542, 7af37db) made view replacement with a shared model possible (`readerGeneration`, cached `currentReader`).
- LOT-186 (#552, a51797a) may change the lifecycle order on device, but its code is not on the `ready` path.
- No single commit is proven yet.

### Proposed fix
- **`ReaderWebController`:**
  - remember the token that reported ready;
  - `show()` reloads the same token if it never became ready and nothing is loading;
  - `stopLoading()` forgets a document that never became ready;
  - add the two `didFail` handlers: reload the current document once, then surface an error. Never leave an endless spinner.
- **`TopicReaderView` and `FilteredPostsView`:** add `.onAppear { controller?.show(model.document) }`.
- **`TopicReaderModel`:**
  - an unsuperseded `.cancelled` sets an error or retries once;
  - the idle state (no page, no load, no error) loads itself again;
  - a view's `onDisappear` cancels only a load that this view instance started.

### Tests (each shown to fail without the fix)
- **Web test, real `WKWebView`** (the `ReaderInsetsWebTests` harness): `show(token 1)`, then `stopLoading()` in the same main-actor turn, then `show(token 1)`. Expect `ready == [1]`.
- **Model test:** view A `onAppear` with a suspended source, then view B `onAppear`, then A's `cancel()`, then resume. Expect a page or an error, never idle.
- **Model test:** an unrequested `.cancelled` gives an error or a retry, not idle.

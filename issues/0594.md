## Analysis (read-only, sub-orch) 2026-11-07

### Current code path of the per-message "⋯"
1. **HTML.** `TopicHTMLBuilder.swift:148-151` writes `<button type="button" class="menu-button" data-menu="message" data-post="N">⋯</button>`. It is a `<button>`, not an `<a>`, so WebKit has no link to preview or long-press. The header sits outside `.content`. This rules out the "the ⋯ is a link" candidate.
2. **JS.** `reader.js:80-86`: the document click listener (in the app's content world) matches `button[data-menu]` and posts `{type:"menu", post, source:"message"}`. It never reaches `decidePolicyFor`, so the LOT-137 link router (`ReaderWebController.swift:342-353` → `TopicReaderView.swift:275-283`) is **not** involved. This rules out "routed to the link handler".
3. **Bridge.** `ReaderBridgeMessage.swift:83-86` → `ReaderWebController.handle` `:220-222` → `events.menu` → `TopicReaderView.swift:288` → `openMenu` (`TopicReaderModel+Quote.swift:72`) → `requestMenu` (`TopicReaderModel+Menu.swift:69-75`). The entries are the policy's (`MessageMenuAction.swift` `MessageMenuPolicy`) **minus every action with no registered handler** (`MessageActionRegistry.swift:298-306`).
4. **Presentation.** `TopicReaderView.swift:122-132`: a SwiftUI `.confirmationDialog`, `titleVisibility: .hidden`, attached to the **whole reader view**, with no anchor.

### Why a "link" popup at the top centre (most likely cause)
Two facts together give exactly what the report describes:
- **Position.** Since iOS 26, a `confirmationDialog` is presented as a popover-style sheet from the view it is attached to. Here that view is the full-screen reader (`TopicReaderView` body), not the "⋯". The sheet therefore anchors to the reader's frame, which puts it at the top centre, far from the tapped button.
- **Content.** The handlers installed are only those in `TopicReaderView.swift:247-266`: `LinkActionHandler` always, plus the two quote handlers (only when `canQuote`: `quoting != nil && replyTarget != nil`, `TopicReaderModel+Quote.swift:124`), `FavoriteActionHandler` (only with `services.flagActions`), and Editer/Supprimer (only with a composer, own posts).
  - "Alerter" has no handler: LOT-135 #225 is `status: ready`, not done.
  - AQ (LOT-134) and Bookmark (LOT-132) have none either.
  - So on any page without the answer form, or with no composer, or with no flag actions, the dialog shows **one row, "Link"** (title hidden). That is the "link popup".
  - A private conversation reached by a followed link has `composer: nil` (`TopicReaderView.swift:140`), so its menu shows only "Link" too.
- **Lifetime trap (secondary, to confirm).** `installMenuActions()` runs once, in the first `.task` (`:159-162`). It reads `composer` and `services.flagActions` at that moment. A reader created before the session was restored keeps a Link-only registry until it is recreated: nothing re-runs it when `composer` changes.

**Device check needed to confirm.** Was the operator logged in? Was it a public topic with an answer form, or an MP? How many rows did the popup show? Logging `presentedMenu.entries` with #575's `ReaderLog` would settle it.

### What LOT-186 changed
`contentInsetAdjustmentBehavior = .never` plus `obscuredInsets` (`ReaderWebController.swift:64-67, 113`) puts the page under the glass bars.
- A "⋯" scrolled under the top bar is covered by the bar, so a tap there does nothing.
- It cannot produce a link popup.

LOT-186 is not the cause. It is not #566 / #575 (lifecycle) either.

### Legacy @ 2440d79
- `MessagesView.swift:1521-1569` `presentPopupMenu`: the message menu is a **`UIEditMenuInteraction` anchored at the tapped point**.
- `popupAnchor` `:1571-1595` takes the JS viewport offsets, adds the insets, and sets the arrow up or down.
- Title "Post de <pseudo>" (`:1597-1610`); entries `:1612-1800`; policy `:196-290`.
- Legacy shows the full list (Citer, Citer ☐, Favoris, Link (share sheet), Alerter (form or mail fallback), AQ, Bookmark, Editer, Supprimer) because every action was wired.

### Proposed fix
1. **Anchor the menu on the "⋯".**
   - `reader.js` adds the button's `getBoundingClientRect()` (four numbers) to the `menu` message.
   - `ReaderBridgeMessage` decodes them, finite and clamped to the viewport, ignored otherwise.
   - The controller converts them to web-view coordinates (plus `obscuredInsets.top`).
   - Then either (a) a `UIEditMenuInteraction` on the web view, as legacy does, or (b) a SwiftUI `.popover(attachmentAnchor: .rect(...))` with `presentationCompactAdaptation(.popover)` and a button list.
   - (b) keeps the LOT-087 learning: give the action the menu it was shown for.
2. **Title "Post de <pseudo>".** As legacy: `titleVisibility: .visible`, or the menu title. Without it, a one-row popup reads as an unexplained "Link".
3. **Rebuild the registry when `composer` or `flagActions` change.** Use `.task(id:)` on an identity of both, so a reader opened before login completion gets the quote, flag and edit handlers.
4. **Not in this fix.** "Alerter" comes with LOT-135 #225, "AQ" with LOT-134, "Bookmark" with LOT-132. Say so in the PR so the device check expects them missing.

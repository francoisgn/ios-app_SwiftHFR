**Phase 1: diagnosis** (cloud/i1375-opus, Opus 5.5, `dev-swift` @ `df095b2`, legacy @ `87fe0d1c`; read only, no fix pushed yet)

### TL;DR
- 🔴 **Proven, fixable now: the composer screenshot.** « Le forum ne répond pas : rien n'a été envoyé » can only come from the **form fetch** that runs before the POST. SwiftHFR gives that GET an idle limit of **10 s**. Legacy gave it **60 s**, because it used a plain `URLRequest(url:)`. The POST itself already has 60 s. Fix: PR A below.
- 🟠 **List loads: same limit as legacy (10 s), and no code path found that turns a non-timeout into « ne répond pas ».** The code alone cannot explain a list timeout that legacy does not get. The best-supported hypothesis is a **connection-level difference**: URLSession reuses idle connections, maybe over HTTP/2, and opens a new connection for every probe and every POST. ASI reuses a connection only as long as the server's `Keep-Alive` says. Only the device trace (#1276 branch) can settle this. Exactly what to read is below.
- 🟢 Error mapping and retry: same as legacy. One reader-only mapping question goes to the orchestrator (finding 4b).

### 1. Timeouts per request kind
| Request | SwiftHFR | Legacy @ `87fe0d1c` | |
|---|---|---|---|
| Lists, favourites, topic pages | 10 s idle (`RequestTimeout.standard`, `HTTPRequest.swift:21`) | 10 s (`kTimeoutMini`, `Classes/Constants.h:70-71`; `ObjCFavoritesLoaderWorker.m:45`; ASI idle check `ASIHTTPRequest.m:1466-1483`) | 🟢 same |
| **Form fetch at send / quote / edit form** (`PostingFlow.loadForm`, `.get(url)`, `PostingFlow.swift:133`; `QuoteFlow` uses the same) | **10 s** | **60 s**: `URLRequest(url:)` with the default `timeoutInterval`, in `HFRswift/Swift/ReplyService.swift:238-243` (reply form) and `:804-809` (quote), `:1046-1047` (delete form) | 🔴 **6× shorter** |
| POST | 60 s (`PostingFlow.postTimeout`, `PostingFlow.swift:259`) | 60 s (`ReplyService.swift:183`, default) | 🟢 |
| Background MP poll | 5 s (`HFREndpoint.swift:25`) | 5 s (`MPBackgroundService.swift:86`) | 🟢 |

So a slow forum (>10 s before the first byte of the composer page) fails the send in SwiftHFR, while legacy waits up to 60 s. That matches the screenshot exactly: `ComposerMessages.network(.timedOut)` (`ComposerMessages.swift:248`) is the « nothing was sent » branch, used when the form could not be fetched. A POST timeout would show « n'a pas confirmé l'envoi » instead.

### 2. URLSessions and connections
Every `HFRSession` holds **2** `URLSession`s (its own plus `URLSessionTransport.noFollowSession`, `URLSessionTransport.swift:16`), and so does every `AnonymousTransport`. On Darwin, each `URLSession` has its own connection pool. At a cold launch on Favoris, with one account:

| What | Session | New TCP+TLS |
|---|---|---|
| Session check (profile page 1) | `probe`, a fresh `HFRSession` (`SessionRefreshFlow.swift:31`, `HFRSession.swift:86`), one per account (`AccountsModel.checkSessions`) | 1 per account |
| `/` (badge) + `forum1f.php` (+ Catégories) | the account's session | 1 (h2) or up to the per-host limit (h1) |
| AQ feed, images, avatars | `AnonymousTransport` (other hosts) | separate |

Later, every MP poll (`MPUnreadPoll.swift:49`), flag poll and session re-check opens a fresh probe and pays a fresh handshake. **Every POST** goes through `noFollowSession` (`redirectPolicy: .doNotFollow`, `PostingFlow.swift:193`), so it cannot reuse the connection the form GET just warmed. Legacy used one session for both the form GET and the POST (`ReplyService.swift:121-141`), and ASI keeps one shared persistent-connection pool for the whole app.

How long a connection is kept also differs. ASI reuses a connection only for the server's `Keep-Alive: timeout=` (`ASIHTTPRequest.m:2246-2275`), or 60 s otherwise (`:288`). It retries once on a new connection when a reused one turns out closed (`:3613-3632`). URLSession keeps idle connections for a period Apple does not document. If HFR answers over HTTP/2, all requests share **one** connection. A connection silently dropped by a NAT or the server (common on 4G, and on Wi-Fi after idle) then gets no RST: the request waits its whole 10 s idle limit and fails as `URLError.timedOut`, i.e. « Le forum ne répond pas · Réessaie dans un instant », and the retry works on a new connection. That fits the report. But **whether HFR speaks h2, and whether the failing requests rode a reused connection, is not in any capture or legacy file**, so I am not claiming it.

### 3. Launch fan-out and serialization
- No app or engine lock serializes the Favoris GET behind another request. It only awaits `isLoggedIn()` (in memory, `NavigationModel.swift:84-87`), then the GET. Session checks run one after another (`AccountsModel.swift:207-232`), but in their own probes, and nothing awaits them on the list path. The `HFRSession` actor is reentrant across the transport await.
- Concurrent requests to `forum.hardware.fr` at launch, from mac/mac-mbp's simulator trace on #1276: profile check, `/`, `forum1f.php`. That is 3 at once with the same account's cookies. Whether HFR serializes concurrent requests of one account server-side is unknown (never guess). The trace's in-flight count and timings answer it.
- The #1202 MPStorage walk does not run at a cold launch on Favoris on iPhone (mac/mac-mbp, #1276).

### 4. Error mapping
- (a) 🟢 Lists and composer: only `URLError.timedOut` becomes `NetworkError.timedOut` (`URLSessionTransport.map`, `URLSessionTransport.swift:160-170`). A cancellation becomes `.cancelled`: not shown, retried once by `ContentLoader` (`ContentLoader.swift:37,74-78`), then shown as `.other`. A lost connection (`-1005`) and DNS or connect failures become `.transport`, shown as « Chargement impossible ». A cancelled session check is `.unconfirmed` (`AccountServices.swift:83-86`). None of these produces « ne répond pas ».
- (b) 🟠 Reader: the 30 s wait watchdog (`TopicReaderModel.swift:129, 519-527`) sets `.timedOut`, i.e. « Le forum ne répond pas », **also when the page did arrive and only the web view never became ready**. In that case the forum did answer. This is pinned on purpose by `TopicReaderModelWaitTests.aDocumentNeverReadyTurnsIntoATimeoutThatALateReadyClears` (#750), so changing it is a product call, not a bug fix. Question for cloud/orch below.

### 5. Retry
- Legacy: **no retry on a timeout**. `numberOfTimesToRetryOnTimeout` is never set in app code, so it stays 0 (`ASIHTTPRequest.m:1498-1507`). The one retry is on a closed persistent connection (`:3613-3632`). URLSession does the equivalent internally for idempotent requests.
- SwiftHFR: `ContentLoader` retries only an unrequested `.cancelled`. 🟢 Parity. Retrying a `.timedOut` GET would go beyond legacy (operator call), and would double the wait to 20 s before the error.

### What the device trace must show (branch `chore/1276-favoris-trace-do-not-merge`, already logging these)
For **each failing request** (`URLError timedOut -1001`), and for the 2 requests before it:
1. `metrics rN`: **`reused`** (true/false), **protocol** (`h2` / `http/1.1` / `h3`), and DNS / connect / TLS / request-start / response-start ms. Reused=true with no response start means cause 2 (stale connection). Reused=false with connect or TLS near 10 s means a network or handshake problem. Response-start near 10 s means HFR is slow on the first byte.
2. The end line: duration, bytes received (0 or more), and the in-flight count at start.
3. The same run with **legacy** cannot be traced, so ask the operator for one thing: whether the failures cluster **after the app sat idle** (back from reading, back from background) or at cold launch.

If the trace shows cause 2, the fix is engine-only and has two candidate shapes, for the operator to choose (neither is in legacy as such):
- (i) one transparent retry of an idempotent GET on `.timedOut` when the connection was reused, as ASI does for a closed one;
- (ii) shorter connection reuse.

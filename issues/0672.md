# Issue #672: [Legacy 4.0.x + SwiftHFR] Reader: no page swipe while scrolling horizontally inside a [fixed] / [code] block

- State: open
- Author: ezzz · created 2026-11-08T21:00:41Z · updated 2026-11-09T06:45:19Z
- Labels: type: bug, priority: medium, difficulty: medium, area: app, status: needs-triage

### Summary

As a reader, I want the page-change swipe to stay out of the way while I scroll horizontally inside a `[fixed]` (or `[code]`) block, so that scrolling back to the start of the block does not send me to the previous page.

### Report

User feedback, reported by the operator on 2026-11-08, paraphrased: could the swipe be blocked while navigating inside a `[fixed]` tag? The user has lost count of the times they went back one page while trying to return to the beginning of the tag.

### Why it happens

**Legacy** (`HFRswift`, `origin/legacy/duo-inner-cover`, same on `master`): the page swipe is a `DragGesture` attached with `.simultaneousGesture(…, including: topicPageSwipeNavigation ? .all : .none)` on the topic's web view (`HFRswift/Swift/MessagesView.swift`, around lines 5328-5357). Being *simultaneous*, it fires even when the drag was consumed by the web view's own scrolling. A long fast horizontal drag (more than 120 pt, impulse more than 70 pt, vertical less than half) to the right inside a wide `[fixed]` block meets the rule and loads `page - 1`. The only guards are the setting, the favourite-post filter and `isMessageTextInteractionActive`; nothing knows the touch started in a horizontally scrollable block.

**SwiftHFR** (`dev-swift`): same design, so the same bug. `TopicReaderView.swift:85` attaches `.simultaneousGesture(pageSwipe, …)`; the decision is `PageSwipe.of(translation:predictedEnd:page:maxPage:)` in `ReaderPageSwipe.swift`, and `reader.css:123` makes `table.code td, table.fixed td { overflow-x: auto; }`, so these blocks scroll horizontally.

### Proposed fix (both apps)

1. In the reader's JavaScript, on `touchstart`, walk up from the target to find an element that scrolls horizontally (`scrollWidth > clientWidth` and `overflow-x` `auto`/`scroll`: `table.fixed`/`table.code` cells, and any other wide content). Post a message to the native side (`webkit.messageHandlers`) with "drag started in a horizontal scroller" plus whether it can still scroll left/right; reset on `touchend`/`touchcancel`.
2. Native side: the swipe decision ignores the drag when it started in such an element. Option to discuss: still allow the swipe when the block is already at its edge in the drag's direction (as photo galleries do), or simply never swipe from inside a block (simpler, more predictable; the user's request).
3. SwiftHFR: keep the decision pure and tested (`PageSwipe.of` gets an extra input, Swift Testing cases: inside block, outside block, block at edge).

### Acceptance criteria

- [ ] Horizontal scrolling inside a long `[fixed]` or `[code]` line, back and forth, never changes the page (legacy and SwiftHFR).
- [ ] The swipe still changes the page when started outside such a block, and with the "Swipe changement de page" setting off nothing changes.
- [ ] Vertical scrolling and text selection unaffected.
- [ ] Checked on iPhone and on iPad / Duo split view.
- [ ] SwiftHFR: unit tests for the new rule, each shown to fail without the change.

### Legacy (`legacy/duo-inner-cover`, PR #372)
- Commit b16eb82d, plus a follow-up in 5f6c411c and 87fe0d1c (the guard is reset when the page changes). Backlog entry HFR-098.
- A user script in `HFRswift/Swift/MessagesView.swift` (`horizontalScrollTouchTrackingScript`) works on `touchstart`, in the capture phase:
  - it walks up from the target to find an element with `overflow-x` set to `auto` or `scroll` and `scrollWidth > clientWidth`;
  - it posts the result to the `horizontalScrollTouch` handler;
  - the page `DragGesture` returns early when `isTouchInHorizontalScroller` is set.
- It implements the "never swipe from inside a block" option, which is what the user asked for.
- One deliberate difference from the proposed fix: the flag is **reset on the next `touchstart`, not on `touchend`/`touchcancel`**. A `touchend` message is asynchronous and could reach Swift before `DragGesture.onEnded`, which would re-enable the swipe for the very gesture we want to block. The `touchstart` message arrives well before the drag reaches the 120 pt threshold.
- Not yet checked on a device.

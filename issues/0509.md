As a member, I want to choose which private messages notify me (all of them, one-to-one MPs, group MPs) and to **mute one group MP**, so that a busy group conversation with many members and replies stops pinging me while my one-to-one MPs still do.

### What legacy does (oracle)
One global count `nb_mp` read from the home page. A local notification "Vous avez un nouveau message privé" when the count rises, plus an app badge driven by `mp_badge_enabled`. It never knows **which** conversation is new, nor whether it is a group (`MPBackgroundService.swift:93-101`; GAP-191). There is no per-type setting and no mute.

### Assessment

**1. Feasibility: the key constraint**
- The home-page count (LOT-047) cannot tell a group MP from a one-to-one MP. To filter by type or mute one thread, the background check must also read **the MP list page** (LOT-126's parser already exposes `PrivateMessageThread.isGroup` and the unread state). It then feeds `NotificationSummary.unreadThreads` (LOT-091, already designed for this) with each unread thread's topic number and `isGroup`.
- Cost: **one extra GET per background check**, and only when a filter or a mute is active. With every option at its default, the check stays the single home-page request.
- Fits the BGAppRefresh time budget. Read-only, so the posting flood limit does not apply.
- **Pending capture (no guessing):**
  - Does an unread conversation always sit on page 1 of the MP list (ordered by last message)? If it can be on a later page, a filtered check can miss it, so bound the read and fall back to a generic notification.
  - Does the list row's reply count change for a muted group? This only matters for the badge.
- No server push exists. Everything is local, so mute and filters are **client-side only**. HFR keeps sending nothing either way; nothing is changed on the forum.

**2. Proposed settings (Réglages › Notifications MP, the legacy section)**
- `Notifications MP` (master, on by default = parity)
  - `MP` (one-to-one), default on
  - `MP multiples` (group), default **on** for parity, **or off**: operator decision D1
- `Pastille sur l'icône` (existing `mp_badge_enabled`)
- `Conversations en sourdine`: the list of muted group MPs, with "Réactiver"

The settings model should be extensible to the next notification kinds (flags, FEAT-005; "On t'a cité", FEAT-018) without a migration: one entry per kind.

**3. Mute one group MP**
- **Where:**
  - a swipe or context-menu action on a group row in the MP list ("Mettre en sourdine" / "Réactiver");
  - a toolbar button in the reader of a group thread;
  - a `bell.slash` mark on the row.
- **Scope:** group MPs only (D2: allow it on one-to-one too?).
- **Storage:** a per-HFR-account set of muted topic numbers, in a small store (LOT-064 core). Optionally mirrored to iCloud KVS (LOT-172, ADR 0013 tier decision D3), so that a mute follows the user to the iPad.
- **Lifetime:** a mute stays until reactivated (D4: offer a timed mute, 8 h / 1 week, like Messages?).
- **iOS side:**
  - set `threadIdentifier` = the conversation on each notification, so iOS groups them per conversation;
  - an actionable notification "Mettre en sourdine" on a group MP notification (cheap, high value).

**4. Badges (decision D5)**
- (a) The icon and tab badges keep counting everything; mute only silences the alert (Messages-like).
- (b) Muted and disabled kinds are excluded from the badges.

Recommendation: **(a)** for the tab badge, with the icon badge following the same toggles as the alerts.

Routing: Sonnet authors and Opus reviews. The background path is device-verified on the Mac (BGTask simulated), as LOT-140 requires.

### Decisions needed (operator)
- **D1:** default for "MP multiples": on (parity) or off.
- **D2:** mute for group MPs only, or for one-to-one MPs too.
- **D3:** sync mutes and notification settings through iCloud (LOT-172), or keep them per device.
- **D4:** permanent mute only, or timed mutes too.
- **D5:** badges, option (a) or (b) above.

### Acceptance criteria (draft)
- [ ] With every option at its default, behaviour equals LOT-140: same single request, same notification and badge.
- [ ] With "MP multiples" off, a new message in a group MP gives no notification, and a new one-to-one MP still does. Tested on captured MP list pages (`R13u1` and new captures), with no live HFR call in tests.
- [ ] A muted group MP never notifies; reactivating it restores the notifications from the next new message (ledger baseline, no backlog burst).
- [ ] Mute and settings are per HFR account; switching accounts never applies one account's mutes to another.
- [ ] An unread thread the bounded list read cannot see falls back to the generic notification: nothing is silently lost.
- [ ] Checked on a device (Mac check): settings, swipe and toolbar mute, notification grouping, the notification action.

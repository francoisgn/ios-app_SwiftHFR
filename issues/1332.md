Agent: cloud/i1332-sonnet. Code trace, no PR (no claim taken: nothing to build).

**Result: the code does not expose a landing or restore to a late reset that arrives within the window the CI evidence shows (≈5 frames). One residual window exists but cannot be shown from code.**

Trace (`WebKitResetWatch.swift`, `ReaderWebController.swift:270-309`, `reader.js:229-300, 373-422`), for the case in the issue (scroll view already at its top at ready):
1. `start` at commit arms the observation; `documentIsReady` → `perform`: `isAtTop` → action runs (page scroll queued behind 2 rAF + agreement wait), `isSecondChance = true`, action kept (`:47-51`).
2. A late reset moves the scroll view from the landed offset back to top → `moved` fires (`isAtTop`), `end()`, `resetToken = token`, action re-queued on the next turn (`:74-87`). So a reset that arrives after the landing and before the watch ends **is** undone-then-redone. This is the CI case (page 300 → top within 5 frames): covered by the second chance.
3. What ends the second chance early is `pageReportedPosition()` (`:274`). Reports come only from `scheduleReport`, a 500 ms debounce started by a page `scroll` event while not pinned (`reader.js:418-421`, `:386-393`). A page that has not scrolled sends none, so no report can precede the landing's own scroll; the landing's scroll schedules the report 500 ms later; a pinned landing (images loading) schedules none until released. A reset that reaches the page as a scroll event (case "page's position pushed back") is the reset itself, already consumed by `moved`.
4. Scroll view away from its top at ready: `perform` only holds the action until the reset (`:46-52`); there is no window.

**Residual window:** a reset arriving more than ~500 ms after the landing's last scroll (report fired → second chance ended → reset not re-run). That needs a layer-tree commit starved for >500 ms after ready. The only evidence (job 138855383148) shows 5 frames; nothing in the code makes the delay bounded, nor shows it can exceed 500 ms. Proving it needs a measurement (log reset-vs-ready timing on an iOS 27.0 runner), which cannot be done from Linux.

Not fixing: a fix (e.g. keep the second chance until the reset is seen, regardless of reports) would be a guess at an unmeasured case, and would re-run a landing over a reader who scrolled without events (VoiceOver, status-bar tap), the reason `pageReportedPosition` exists. Suggest closing as "not exposed within measured timing", or keeping it `host: mac` with a timing log if the operator wants the >500 ms case measured.

### Summary
As the maintainer, I want to decide whether the anonymizer should raise when a signature or mood is cut past its first balanced `</span>`. Today an unknown HFR element printed right before HFR's known tail is deleted silently with the block. This is #797 point 3's own example.

### Facts
- #794 (#763) runs a signature or mood to the last `</span>` before HFR's next element. That redacts a member's unbalanced markup on purpose: `…</span>Secret Handle<span class="x">…`. Its tests pin this redaction.
- PR #812 (#797) raises when anything other than HFR's own tail follows that `</span>`. An unknown HFR element followed directly by the known tail is still cut, for example the invented `<br/><span class="MDStatus">…</span>` after a mood followed by `</td>` or the avatar. Byte for byte, it looks the same as the member shape above: members get classed spans from BBCode (`span.u`, `span.red`, …).
- Nothing leaks: only HFR content is lost, and no corpus page has the shape.

### Options
1. Keep the current behaviour (documented in `tooling/fixtures/README.md`).
2. Raise whenever the depth count and the boundary disagree. This closes the gap, but #794's unbalanced-markup captures would then need an extension before they can be published, and #794's redaction tests would become raise tests.

### Acceptance
The operator picks an option. If option 2: tests first, then `check --corpus`, `manifest_check.py` and the tooling tests green.

## francoisgn · 2026-11-11T20:26:52Z

**Operator decision, 2026-11-11: option 1.** The current behaviour stays, as documented in `tooling/fixtures/README.md`.

A signature or mood is cut at the last `</span>` before HFR's next element. An unknown HFR element printed right before the known tail is removed with the block.

Rationale:
- The anonymizer fails safe: nothing leaks, and at worst some HFR content is over-redacted.
- Raising instead would let a member's own unbalanced signature markup block publishing a capture.
- The shape appears on no page of the corpus.
- The differential tests against the current app would show missing HFR content.

No code change. Closing.

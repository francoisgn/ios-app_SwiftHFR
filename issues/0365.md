# Issue #365: [SwiftHFR] MPUnreadPoll, SmileyLookupFlow, LoginFlow: probes keep the source session's host policy

### Summary

As a maintainer, I want every probe session built from an account session to keep that session's host policy, so that a test session restricted to the loopback host can never yield a request to the forum.

### Scope

Follow-up of #320 (PR #364, which adds `HFRSession.probe(cookies:now:)`, `package`, and uses it in `SessionRefreshFlow`). Three other flows build their probe with `HFRSession(cookies:)`, i.e. the `.forum` policy, whatever the source session's:

- `Packages/HFRKit/Sources/HFRClient/MPPoll/MPUnreadPoll.swift:26` (LOT-047): `makeProbe: { HFRSession(cookies: $0) }`.
- `Packages/HFRKit/Sources/HFRClient/Smileys/SmileyLookupFlow.swift:23` (LOT-053): the same default.
- `Packages/HFRKit/Sources/HFRClient/Login/LoginFlow.swift:18` (LOT-043): could build its fresh session with `session.probe(cookies: [], now:)` on its `into:` session.

No production impact (every production session is `.forum`): test hygiene, as #320.

### Acceptance criteria

- [ ] Each default probe is built with `probe(cookies:now:)` on the source session (or the reason it cannot is stated).
- [ ] An **offline** test per flow asserts the default probe's host policy (LESSONS 56: no test may rely on a local refusal that a mutation removes); each fails without the change.
- [ ] `swift test` green on Linux and macOS CI; `scripts/check-lot-deps.py` passes; the LOT-043, LOT-047 and LOT-053 specs updated (one line each).

Depends on #364 being merged.

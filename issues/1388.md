### Summary
As the maintainer, I want an independent audit of how SwiftHFR decides to send requests, so that no event chain can turn into a request loop or a burst again. Trigger: #1276 / #1375, where a launch account check and the session-change reloads fed each other (36 forum requests in under 3 s, then a 47.5 s timeout; fix in #1385). Operator, 2026-11-27: « On n'aurait jamais dû avoir ce genre de boucle, on doit auditer ce genre de comportement. » Part A of #774 (performance, response time), started ahead of the rest of #774.

### Scope (read the code; measure with engine tests and loopback transports; no request to forum.hardware.fr)
1. **Feedback loops**: every observer, `onChange`, `task(id:)`, notification, counter or published value that triggers a request, and every request whose result can re-trigger it (session changes, cookie writes, account checks, sync adoptions, badge/poll updates, theme or settings writes). Draw the graph; flag every cycle and how it is broken (or not).
2. **Redundant and duplicate requests**: the same URL fetched twice for one user action; parallel fetches of one resource without coalescing; reloads after a change that changed nothing (e.g. HFR re-sending the same cookies with a new expiry).
3. **Request budgets**: count requests per scenario: cold launch per tab, return from background, pull to refresh, opening a topic, posting, account switch, several accounts. Compare with legacy where the legacy path is clear (cite `file:line` @ 87fe0d1c).
4. **Re-entrancy and cancellation**: tasks restarted before the previous one ends, cancelled work that still writes state, retries.
5. **Guard rails**: propose one cheap, permanent safeguard (e.g. a debug-build request-rate assertion or a test that runs each scenario against a counting transport and fails above a budget).

# Issue #1186: [SwiftHFR] parsing: one unreadable message block makes the whole topic page unreadable, while list parsers skip an unreadable row

### Summary
As a reader, I want a topic page with one odd message block to show its other messages, as legacy did and as our list parsers already do, so that one block does not turn a page into an error.

### Scenario
A page with one `messagetable` block lacking its `t<n>` anchor, its `s2` cell or its `para` div: `MessageBlockParser.extract` throws `missingElement` for the page, and the reader shows an error. The deleted-post wrapper `messagetabledel` is still pending capture (#123, `docs/lots/LOT-030-message-blocks.md:47,90`), so the shape of the block most likely to hit this is unknown. No capture shows a failing page today.

### Evidence (`7a61018f`)
- `Packages/HFRKit/Sources/HFRParsing/Topic/MessageBlockParser.swift:29-33`: in the loop, `guard let author = try author(in: elements) else { continue }`, then `let numreponse = try numreponse(in: elements)` and `let content = try content(in: elements, numreponse: numreponse)`: each throws for the page.
- `MessageActionsParser.actions(in:)` and `MPStoragePageParser.firstMessage` inherit it through `extract`.
- `Packages/HFRKit/Sources/HFRParsing/TopicList/TopicListParser.swift:49-57`: an unreadable row is skipped; the page is malformed only when all rows fail (LESSONS 44).
- Legacy is nil-tolerant per message: `ParseMessagesOperation.m:139-177` @ `87fe0d1c`.

### Fix
Skip a block that cannot be read; throw only when the page has `messagetable` elements and none is readable; keep the skipped count for diagnostics. Do not hand-build the deleted-post placeholder: #123 captures it.

### Tests (first one fails before the fix)
`MessageBlockParserTests.skipsUnreadableBlock`: an `R20` capture with the anchor removed from one block gives N-1 blocks in order (today `missingElement`); a second case with every block broken still throws.

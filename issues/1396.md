### Summary
As a user of the MPStorage blocklist, I want the reconcile to stop when its own write did not land, so that a document dated ahead of my clock can never turn into a request loop (the same class as #1276: same content, another date). Audit #1388, finding A3. Latent: no known writer produces the triggering document today.

### The cycle (read at `dev-swift` `1685bcc`)
- `BlocklistSyncModel.reconcile` writes what only the device has with `mpStorage.edit(.ignoreList)` (`App/SwiftHFR/MPStorage/BlocklistSyncModel.swift:94-117`, the edit at `:112`).
- `MPStorageSyncModel.edit` syncs when the edit changed the local document (`MPStorageSyncModel.swift:251-268`), and the sync ends in `afterSync`, which is `reconcile` again (`BlocklistSyncModel.swift:38`).
- The only breaker is the comment's rule: "an edit that changes nothing triggers no sync". It assumes the write always lands.

### Failing scenario
The document holds a tombstone for pseudo P dated after this device's clock. The user blocks P here: the edit reports a change, the merge drops the add (`MPStorageMerge.keepOneSided`, `Packages/HFRKit/Sources/HFRModels/MPStorage/MPStorageMerge.swift:193-197`), the document read back still lacks P, and `BlocklistSyncPlan.make` plans `addRemotely [P]` again (`BlocklistSyncPlan.swift:71-76`).
Count: **3 GETs per turn (thread page, edit form, edit form again), with no delay, until the clock passes the tombstone's date or the network fails.**
Why latent: SwiftHFR writes no tombstones (`recordsTombstones` defaults to false, `MPStorageStamp.swift:19`); a future client or another device's clock is enough to make it real.

### Proposed fix
A reconcile started by reconcile's own write never writes again: a depth flag, or stop when the plan equals the previous plan. Test: a document with a future-dated tombstone, block the pseudo, count the transport's requests (bounded, e.g. one sync).

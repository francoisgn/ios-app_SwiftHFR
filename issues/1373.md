# Issue #1373: [SwiftHFR] MPStorage search marks another member's storage-subject MP read without the member opening it

### Summary
As a member who receives an MP whose subject happens to be the MPStorage subject, I want it to stay unread until I open it, so that the storage sync running in the background does not hide a new message from me.

### Problem
The storage search (`MPStorageTransport.findThread`, `Packages/HFRKit/Sources/HFRClient/MPStorage/MPStorageTransport.swift:66-92` at `dev-swift` 97a060bd) GETs the first page of every storage-subject row it meets before the account's own one, to see whether its first message carries the account's edit link (#1200 P1). Captured on #1203 (PR #1367, HFR-PROTOCOL §6c LOT-038): **that GET alone marks the thread read** for the account (`R1203a` → `R1203b` → `R1203c`: « Nouveau message » → « Pas de nouveau message », `sujetCase8` 0 → 1, the list's unread count down by one). The row is kept visible on purpose (#1200 P1), but a member's new MP with that subject is marked read without being opened. Legacy took the first storage-subject row as the account's thread (HFR-PROTOCOL §6c LOT-038), so it read that row's thread too; whether this is worse or equal to legacy depends on the row order.

### Options (needs a choice before coding)
- Skip a row that does not name the storage recipient as its only interlocutor before fetching it (the account's own rows do, `R13u1`, `R333b`, `R1203a` row 47); fetch only rows that might be the account's. Check what that does to a storage thread whose recipient row is aliased or renamed.
- Or keep the GET and accept the side effect, documented.

### Sources

### Summary
As a member who locks the phone or leaves the app, I want SwiftHFR not to start loading lists while it goes to the background, so that I do not come back to « Le forum ne répond pas ». On the iPhone Duo, every trip to the background rebuilds the root twice and reloads Favoris in the background; when the phone is locked, that request is frozen and ends in `URLError.timedOut` 25–56 s later.

### Facts (device pass of #1388, operator's iPhone Duo, iPhone19,4, local trace build `dev-swift` 1685bcc1 + #1385 + `[T1276]` triggers, 2026-11-27 17:53, operator's account, read-only)

- 3 trips to the background in 3 minutes, **3 background reloads of Favoris**, 2 of them timed out. Every trip shows `usesSidebarRoot` twice (6 lines; 10 in a second 4-minute run, where an unlocked trip to the home screen also reloaded Favoris in the background, at 77390 ms, which completed).
- No session check and no home reload on return (`recheckSessions` sends nothing): the reload comes only from the root rebuild.
- This is a likely path for the operator's original #1276 symptom (« Le forum ne répond pas » on Favoris, on the 15 Pro Max too if its snapshots cross a size class), independent of the launch loop fixed by #1385.

### Scope
- The root swap driven by `usesSidebarRoot` must not rebuild the lists for a background snapshot (ignore size-class changes while `scenePhase != .active`, or keep the list models alive across the swap so `onAppear` finds them loaded), and a list `onAppear` while not active must not start a load.
- A request started before the app is suspended should not surface as `timedOut` on return (cancel on background, or retry once on `active`).
- Tests: a hosted test that flips `usesSidebarRoot` while `scenePhase` is `.background` and counts Favoris loads (0), red first.

### Acceptance criteria
- On the Duo, lock / unlock and home screen / back send no Favoris request while in the background and show no error on return (device check on #893).

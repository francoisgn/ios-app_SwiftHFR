# Issue #1433: [SwiftHFR] UX survey: warn when the trusted proxy sends no usable client address

### Summary
As the PO, I want one log line when a request from the trusted proxy carries no usable `X-Forwarded-For`, so that a relay that does not forward the client's address is seen at once in the log, and not only when the fourth tester gets a 429.

Refs #635 (finding 4 of the UX-11 review).

### What happens today
`adresse` (`tooling/ux-survey/internal/web/ip.go:12-29`) falls back silently to the connection's address when the header is missing or cannot be parsed. Measured on loopback at `ffa9418d`, with the loopback address as trusted proxy: without the header (or with `unknown`, an `ip:port` or a bracketed form), every client shares one counter: the fourth submission gets 429, and ten wrong access-code tries by anyone lock everybody out for ten minutes. The fallback is the safe side (nobody gains a counter), but nothing in the log says why.

### Scope
- When the connection comes from `UX_PROXY_DE_CONFIANCE` and no client address can be read from the header: one warning line per hour at most (like the hourly-cap line of `plafond.go`), with a fixed message and **no address, no header value**.
- The PO checklist (`docs/ux/questionnaire/verification-image.md`, points 3 and 4) says to look for that line.
- No new variable: per Tailscale's published source the HTTP proxy mode sets `X-Forwarded-For` itself (v1.80.0, `ipn/ipnlocal/serve.go:817-825`), so `UX_EN_TETE_CLIENT` is not needed unless the on-host test says otherwise.

### Acceptance criteria
- A test: a request from the trusted proxy without the header, then with an unparseable one, produces the warning once; a request with a valid header, or with `UX_PROXY_DE_CONFIANCE=aucun`, produces none; the line holds no address (seen to fail before the change).
- `go vet ./... && go test -race ./...` green.

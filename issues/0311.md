# Issue #311: LOT-172: iCloud key-value sync store (settings, Apple-only lists, fine reading position)

### Summary

As a member using SwiftHFR on an iPhone and an iPad, I want my content preferences, my allowlist, super-favourites, app-local smiley favourites and my fine reading position to follow my Apple ID, so that I configure the app once and resume where I was on the other device.

ADR 0013 (storage tiers, operator decisions 2026-10-28) puts these items in the iCloud key-value store (`NSUbiquitousKeyValueStore`); MPStorage keeps what other HFR clients share (blacklist, bookmarks, `mpFlags`); secrets never enter iCloud KVS.

### Scope

- **`SyncedKeyValueStore`** protocol in `HFRStorage`: `value(for:)`, `set`, `remove`, `synchronize()`, an `AsyncStream` of external changes (keys changed, reason: server change, initial sync, quota violation, account change). Implementations: `UbiquitousKeyValueStore` (Apple, under `#if canImport(Darwin)`: the class is not in swift-corelibs-foundation) and `InMemorySyncedKeyValueStore` (tests, Linux, previews).
- **UserDefaults mirror**: the synced settings keep their legacy `UserDefaults` names (LOT-060), so `@AppStorage` and the synchronous `SettingsStore` keep reading the mirror; a write goes to both stores; an external change updates the mirror. `Setting<Value>` gains `scope: .synced | .device` per the ADR 0013 matrix (appendix).
- **Lists**: allowlist (global), super-favourites and app-local smiley favourites (per HFR account, key suffix = the account key of ADR 0013 §7: `md_user` pseudo with U+200B removed then lower-cased, frozen even after LOT-072 (#96); the legacy global lists are imported into the account active at the first import, LOT-067 (#92), CHANGELOG-LEGACY row 30), one key per list, JSON envelope `{version, items:[{id, addedAt}]}`; LOT-061 / LOT-064 documents stay the local copy. Conflict policy: last writer wins per key (ADR 0013 §3); union merge with tombstones is a documented later upgrade.
- **Fine reading position** (LOT-090 (#182)): per topic, debounced (one write per topic per minute at most, and on leaving the topic), bounded (e.g. 200 most recent topics, one key per HFR account) so the budget holds. The coarse cross-platform position stays HFR's own flags.
- **Initial sync and account change**: on `NSUbiquitousKeyValueStoreInitialSyncChange` the cloud value wins over the local one; on `AccountChange` (another Apple ID, or sign-out) the previous mirror values and any pending KVS write are **quarantined** in a device-only file (never uploaded under the new Apple ID), synced reads and writes are blocked until the new account's initial sync completes, then the new account's values are applied to the mirror; device-scoped settings are untouched; the quarantine is restored only if that Apple ID becomes active again and deleted after 90 days (ADR 0013 §3); a `schemaVersion` key lets an older build ignore values it cannot read; a quota violation is logged and the write kept locally.
- **Budget**: < 1024 keys and < 1 MB in total; a test counts the keys and bytes of a worst case (5 accounts, full lists, 200 positions).
- Out of scope: the iCloud capability and entitlement (LOT-160 (#250), LOT-161 (#251)), the Keychain sync of accounts (LOT-173), the settings screen (LOT-119 (#210)), the legacy import order "device first, then cloud" (LOT-067 (#92) / LOT-158 (#248)).

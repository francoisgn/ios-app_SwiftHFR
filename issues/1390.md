# Issue #1390: [SwiftHFR] Account sync: a cookie-expiry-only refresh is treated as new credentials (iCloud Keychain write and `replaced` report on every valid check)

- State: closed
- Author: francoisgn · created 2026-11-27T14:55:15Z · updated 2026-11-28T05:36:10Z
- Labels: type: bug, priority: high, difficulty: medium, area: storage, origin: audit, m4-review: performance
- Source: https://github.com/ezzz/HFRnow/issues/1390

### Summary
As a user with the account sync on, I want a session check that only renewed my cookies' expiry dates to change nothing in the shared copy, so that no device ever sees "new credentials" where there are none. This is the source of the #1276 loop: #1385 stops its effect in the app (`takeOver`), the engine still produces the echo. Audit #1388, finding A1.

### What happens (read at `dev-swift` `1685bcc`)
1. Every valid check ends in `AccountsModel.persistSession` (`App/SwiftHFR/Accounts/AccountsModel.swift:218-220`, `:322-360`). HFR re-sends `md_user` / `md_passs` with a new expiry on every logged-in answer (HFR-PROTOCOL §6c, `R74`), so `stored == before` is false and `noteSyncChange(.refresh)` runs (`:349`).
2. `AccountSync.localChange(.refresh)` stamps `credentialsAt = now` (`Packages/HFRKit/Sources/HFRStorage/AccountSync/AccountSync.swift:107-109`) and reconciles: the merged envelope differs from the item, so the **synchronizable Keychain item is rewritten** (`:309-312`).
3. On every other device, the next reconcile (each foreground, `AppLifecycle.swift:97-101`) finds the remote copy newer: `AccountSyncMerge.replaced` compares whole `Account` values, dates included (`AccountSyncMerge.swift:58-62`; a tie keeps the remote, `:67-71`) and reports the account `replaced`.

### Failing scenario and count
- One device, one account, sync on: **1 iCloud Keychain write per valid check** (each launch), for a change that is only dates.
- Two devices: each launch of A makes B report `replaced` at its next foreground. Before #1385 that is 1 profile check + 1 home page + up to 4 list reloads on B, whose own write-back then does the same to A. With #1385 the take-over is skipped only while B's session is `valid` with the same login; `restored` / `checkFailed` sessions still adopt, signal and check.
- A copy dated ahead of this device's clock: the #1276 loop itself (13 checks, 36 requests in 2.7 s).

### Proposed fix
- In the engine, a `.refresh` whose login identity (`md_user`, `md_passs`, `md_id` values) equals what the copy holds does not move `credentialsAt` and does not rewrite the item; `replaced` compares the login identity, not the dates.
- Keep #1385's app-side guard as the second line.
- Test (Linux, `HFRStorageTests`): two `AccountSync` over one in-memory item; a refresh with new expiries only → `itemWritten == false`, the other device's reconcile → `replaced.isEmpty`; a real re-login still propagates.

### Acceptance
- An expiry-only refresh writes nothing to the synchronizable item and is never reported as `replaced`.
- A re-login on one device is still adopted once by the other.

Sessions and credentials: merged by the core orchestrator or the maintainer (AGENTS.md §8).

Refs #1388, #1276, #1385.

**mac/mac-mbp**: one more case from the Fable review of #1385 (finding 4). It happens at `dev-swift` too, and #1385 does not fix it. #1385 changes only the app's take-over; the engine-side echo described here stays.

**A copy dated ahead freezes the stored credentials.** While the synchronizable copy's `credentialsAt` is later than this device's clock, every write-back of this device loses the merge (`AccountSyncMerge.newer`, a tie keeps the remote: `AccountSyncMerge.swift:67-71`). The merge then writes the copy's account into the device-only store (`AccountSync.swift:316-321`).
- Reviewer's control probe: after a valid check, the stored `md_user` keeps the copy's expiry (1 day), not the refreshed one (+30 days).
- The next cold launch rebuilds the session from that frozen copy. Once its cookies lapse, the account is logged out at every launch.
- A re-login on this device (`.login`, stamped with this device's `now`) also loses the merge while the copy stays ahead.
- ADR 0013 accepts clock skew only for `enabledAt` and `deletedAt`, not for `credentialsAt`.

**Fix direction** (to decide here, alongside A1): the A1 fix (an expiry-only refresh does not move `credentialsAt`) does not cover this case by itself, because a real re-login here still loses. Options:
- (a) Clamp: a local change is stamped `max(now, remote.credentialsAt + step)`, the same way `enabledAt` is (`AccountSync.swift:273-274`).
- (b) Compare the login identity first: when local and remote hold the same `md_user`/`md_passs`, keep whichever cookie expiries are later, whatever the stamps say.

Test (Linux, `HFRStorageTests`): two `AccountSync` over one item, B's clock one hour ahead. A's refresh after B's write must leave A's later expiries in A's store, and a re-login on A must win.

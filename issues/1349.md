## Symptom

Beta 4.0.3 (build 37): tapping a member's avatar opens the profile sheet, which shows **« Profil indisponible — Profil impossible à lire. »** instead of the profile.

Reported cause: forum.hardware.fr now requires an authenticated session to view `/hfr/profil-<id>.htm`, and answers 403 otherwise.

## Server-side findings (confirmed 2026-11-26)

Anonymous requests (no cookie), whatever the User-Agent (CFNetwork-style app UA, curl, mobile Safari):

| URL | Status |
|---|---|
| `https://forum.hardware.fr/hfr/Hardware/liste_sujet-1.htm` | 200 |
| `https://forum.hardware.fr/hfr/profil-802171.htm` | **403 Forbidden** (Apache's default page, not a forum page) |

So the 403 is not a User-Agent block: profiles are now refused to anonymous visitors. Not yet verified: that a request **with** valid `md_user` / `md_passs` cookies gets a 200 (needs a real account's cookies).

## Code analysis (master @ 20a4b2f, `HFRswift/Swift/UserProfileView.swift`)

```swift
struct UserProfileService: UserProfileServicing {
    var session: URLSession = .shared
    func fetchProfile(url: URL) async throws -> UserProfile {
        let request = URLRequest(url: url, cachePolicy: .reloadIgnoringLocalCacheData, timeoutInterval: HFRNetworkTimeout.content)
        let (data, _) = try await session.data(for: request)   // status code ignored
        ...
        return try UserProfileHTMLParser.parse(html: html, sourceURL: url)
```

1. **Is the request authenticated?** In principle yes: `URLSession.shared` uses `HTTPCookieStorage.shared`, and `MultisManager` pushes the main account's cookies there at launch (`init` → `setCookiesForMain`) and on account switch. Nothing sets the cookies on the request explicitly, though, so it depends on the global storage state at that moment (e.g. `lougout`/`forceCookiesForCompte` wipe it, session-only cookies are not persisted across launches by `HTTPCookieStorage`). **To confirm** on a device (see "Verification" below).
2. **The HTTP status is ignored.** The 403 body (`<title>403 Forbidden</title>`) is handed to the parser, which finds no field and throws `.invalidProfile` → the generic « Profil impossible à lire. ». The user gets no hint that logging in is required, and we can't tell a 403 from a parsing regression in reports.
3. Every presentation of `UserProfileView` (avatar tap, avatar action sheet, profile link in a message, `MessagesView.swift` 3 `.sheet(item: $userProfileDestination…)`) goes through this service.

### Next architecture (`App/SwiftHFR`) is affected too

`App/SwiftHFR/Profile/UserProfileSource.swift` fetches **deliberately without cookies** (`fetcher.profile(memberID:as: .anonymous)`, LOT-116 differences 1–2, #124: the parser was only verified on logged-out pages). With the new server rule this always 403s → `.unreadable`. That design decision has to be revisited (logged-in captures for `R56`, then send the session).

## Verification to run before fixing

- On a device with an account: proxy (Proxyman/Charles) or a temporary log in `fetchProfile` printing `(response as? HTTPURLResponse)?.statusCode` and `HTTPCookieStorage.shared.cookies(for: url)?.map(\.name)`.
  - Cookies `md_user`/`md_passs` present + 403 → the server wants something else (to investigate: Referer, other cookie).
  - Cookies absent → storage state issue → fix 1 below solves it.
- Or by hand: copy one's own `md_user`/`md_passs` from a logged-in browser and `curl -H "Cookie: …" https://forum.hardware.fr/hfr/profil-<id>.htm` → expect 200.

## Proposed fix (4.0.x)

1. **Authenticate the request explicitly** instead of relying on the global storage: inject the main account's cookies (`MultisManager` main compte, the same source `AccountSessionService` uses for replies) via `HTTPCookie.requestHeaderFields(with:)`, with `httpShouldHandleCookies = false` so the global storage is neither read nor modified. Inject a cookie provider into `UserProfileService` so it is testable.
2. **Check the HTTP status**: 401/403 → new `UserProfileLoadingError.loginRequired` (« Connectez-vous pour consulter les profils. »); other non-2xx → `.httpStatus(Int)`; only 2xx goes to the parser.
3. **No account** → don't fire the request; show the "login required" state directly (with a button to the account screen, or « Ouvrir dans Safari »).
4. **Tests** (Swift Testing, `URLProtocol` stub): Cookie header present when an account exists; 403 → `.loginRequired`; 200 → parsed profile; no account → no request.
5. Check the logged-in profile page still parses with `UserProfileHTMLParser` (logged-in HTML may add rows/actions).

Same session semantics for `SwiftHFR` (`.anonymous` → main account session), once logged-in captures exist.

**mac/mac-mbp**: server check, 2026-11-27 (read-only GETs from the Mac, kit account):

| Request | Status |
|---|---|

So HFR still serves profiles to a logged-in session. A 403 while the app is logged in means the request left **without the cookies**, not that the server refuses members. `bb58131d` on `master` (2026-11-26) addresses exactly that: the cookies are set on the request itself instead of relying on `HTTPCookieStorage.shared`. A build made before `bb58131d` will keep showing the 403. Re-check with a build that includes it.

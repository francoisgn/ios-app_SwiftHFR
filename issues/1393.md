### Summary
As a user whose list filter is Favoris, Suivis or Lus, I want a sub-forum to open with the two requests it needs, so that every sub-forum I open does not send a third one that is cancelled at once. Audit #1388, finding B2 (by reading; no app test run in the cloud).

### What happens (read at `dev-swift` `1685bcc`)
1. First load of a `.subforum` source: `subforumTarget` is nil, so the "Tous" page is fetched (`TopicListModel.swift:343-346`). GET 1, needed: only that page names the `subcat` (GAP-023).
2. The load applies; `subforumTarget` is set (`:367`), so `offersFilter` turns true and `wantedFilter` becomes the stored filter. `load` then asks again itself: `if wantedFilter != loadedFilter { await load(page: 1) }` (`:377`). GET 2, needed.
3. The same state change moves the id of `.task(id: model.wantedFilter)` (`TopicListView.swift:129`): SwiftUI starts `onAppear` again, which finds `wantedFilter != loadedFilter` (GET 2 is still in flight) and calls `load(page: 1)` too (`:285-287`). GET 3 supersedes GET 2, which is cancelled (`ContentLoader.swift:26-27`).

Count: 3 requests, 1 cancelled in flight, for every sub-forum opened with a non-« Tous » filter. A cancelled request on the account session is also what #1191 / #1230 had to handle.

### Proposed fix
One owner for "the wanted filter changed": either `load`'s own tail or the view task, not both. For example `onAppear` skips the filter branch while a load for the wanted filter is in flight (remember the filter of the load in flight), or the view task is keyed on something the first load does not change.

### Test
App test with a counting `ForumDataSource`: open a sub-forum with the stored filter `.favorites`, signed in → exactly 2 `topicList` calls, none cancelled.

Refs #1388.

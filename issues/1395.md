# Issue #1395: [SwiftHFR] MPStorage: the MP-list walk repeats (limit reached not remembered, double walk on creation) and a write costs 4 GET + 1 POST

### Summary
As a member with many private messages, I want the MPStorage sync to read each page once and to remember a search that found nothing, so that opening Messages does not walk my whole MP list again and again on the forum's shared flood limit. Audit #1388, findings C1 to C3 (by reading at `dev-swift` `1685bcc`).

### Findings
1. **A walk that hits the 50-page limit is not remembered.** `performDetect` stamps `lastSearch` only on "not found" (`Packages/HFRKit/Sources/HFRClient/MPStorage/MPStorageSync.swift:83-87`); `searchLimitReached` (`MPStorageTransport.swift:123`) leaves through `failing(error, keeping: copy)` with `lastSearch` untouched (`:91-93`). `started` blocks a rerun only inside one `MPStorageSyncModel` (`App/SwiftHFR/MPStorage/MPStorageSyncModel.swift:134-139`), and each root has a new one.
   Scenario: an `unasked` account with more than 50 MP pages opens Messages, Réglages or Bookmarks: **50 sequential GETs + 1 per candidate, at every launch, account switch and window**, never throttled by the 24 h `searchInterval`.
2. **Creation walks the list twice.** `setEnabled` runs a detect walk (`MPStorageSyncModel.swift:168`), then `create` calls `findThread` again (`MPStorageTransport.swift:181`): about 2P + 6 requests for one « Oui » (80 GETs with 40 pages). Legacy: P + POST + 1 (`Classes/MPStorage.m:88-110` @ `87fe0d1c`).
3. **A write is 4 GET + 1 POST.** `performSync` locates and reads (thread page + edit form, `MPStorageSync.swift:99`, `MPStorageTransport.swift:126-128`), `save` loads the same edit form again (`:155`), posts, and reads back (`:171`). Legacy add: 1 GET + 1 POST (`MPStorage.m:230-233`, `:905-913`). `BlocklistSyncModel.run` handles changes one by one (`BlocklistSyncModel.swift:42-46`): three quick blocks = 12 GET + 3 POST. The accepted candidate's first page is also fetched twice (`isAccountThread`, `MPStorageTransport.swift:81-83`, then `read`).

### Proposed fix
1. Stamp `lastSearch` on `searchLimitReached` too.
2. Skip the pre-creation search when a detect ended "not found" seconds ago; keep the post-creation one.
3. Hand the form and page already read to `save` (2 GET + 1 POST), and drain pending blocklist changes into one edit.

### To decide (not coded without the operator)
The unprompted walk for every `unasked` account (ADR 0013 §7, "found → on"): 1 list GET + P walk GETs every 24 h for a member who never used MPStorage (30 pages → 31 requests when opening Messages; page 1 fetched twice). Legacy searches only when `mpstorage_active` is on (`Classes/MPStorage.m:83-90`). Options: a small page bound for the unprompted detect, a longer interval, reuse of the list's own page 1.

### Tests
Engine tests with the scripted MPStorage transport: limit reached → no second walk within `searchInterval`; create after a fresh "not found" → one walk; one edit → 2 GET + 1 POST.

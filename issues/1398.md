# Issue #1398: [SwiftHFR] Network objects: a new probe session (cold connection) per check, poll and gated write; an anonymous transport per `PageFetcher`, never invalidated; AQ feed read again at each root rebuild

### Summary
As a user, I want the app's background requests to reuse the connection the forum session already has, so that a check or a flag write does not pay a new TCP + TLS handshake next to the page I am waiting for. Audit #1388, findings B4, B9, B10. This is the "connection reuse" lead (2) of #1375, with the code evidence; fix it there or here, not twice.

### Findings (read at `dev-swift` `1685bcc`; request counts measured with a scripted transport, handshake cost not measured)
1. **A probe is a new `HFRSession` with 2 new `URLSession`s and an empty connection pool, on every call** (`Packages/HFRKit/Sources/HFRNetwork/Session/HFRSession.swift:85-87`, `:62-68`): `SessionRefreshFlow.refresh` (`:47`), `MPUnreadPoll.unreadCount` (`:58`), `LoginFlow.login` (`:29`, `:46`), `OwnSmileysFlow` (`:32`), `SmileyLookupFlow` (`:44`). Launch with N accounts: N profile checks on N cold connections, next to the first visible load.
2. **Every gated write runs a fresh session check first, with no reuse of a recent verdict** (`TopicFlagFlow.swift:181-202`; also `PollVoteFlow.swift:102`). Measured: add favourite = 1 check GET + 1 write; 3 refreshes in a row = 3 probes. Removing 5 favourites = 10 requests, 5 on new sessions. Legacy: 1 request per write. The check is deliberate (#314, #1200): **only reusing a `valid` verdict for a short window, keyed on the login generation, is proposed, and that is a security trade-off for the operator to accept before any code.**
3. **`PageFetcher.init` builds a fresh `AnonymousTransport()` by default** (`PageFetcher.swift:15`): 2 more `URLSession`s per fetcher (`AnonymousTransport.swift:21`), per environment in `AppEnvironment.swift:48` and per call in `UserProfileSource.swift:34`, `MPCheckForum.swift:37`, `OwnSmileysFlow.swift:35`. `URLSessionTransport.deinit` invalidates only the no-redirect twin (`URLSessionTransport.swift:19-21`): the main session it created is never invalidated (whether that leaks is not verified).
4. **The AQ feed is read 3 s after every root build** (`RootNavigationView.swift:49`, `QualityAlertsModel.swift:123-128`): at launch, and again on each account switch, login, logout and for each window. Legacy reads it once at launch (`MainWindow.swift:1609` @ `87fe0d1c`). The feed does not depend on the account; only the hidden-category rule does.

### Proposed fix
- One long-lived probe transport per account (jar reset per use), or the probe sent on the account's own `URLSession` with an explicit `Cookie` header and cookie handling off.
- One shared `AnonymousTransport`; invalidate a main session the transport created.
- AQ count: once per launch and when the list is shown; a rebuilt root reuses the last feed.
- The verdict reuse of point 2 only on the operator's go.

### Tests
Engine: a counter on probe creation (a `package` seam) → a refresh, a poll and a gated write create no new `URLSession`. App: two root builds → one AQ feed request.

Sessions and auth: merged by the core orchestrator or the maintainer (AGENTS.md §8).

Refs #1388, #1375.

Plan (points 1, 3, 4; point 2, the verdict reuse, stays out until the operator's go):
- Point 1: each account `HFRSession` keeps a small pool of probe connections (`URLSession` + its own jar). A probe stays a fresh `HFRSession` (no `hash_check`, generation 0, jar emptied then seeded with the given cookies), but its `URLSession` is recycled when the probe is released, so a refresh, a poll or a gated write's check stops opening a new connection each time. Isolation kept: two concurrent probes never share a jar; a connection whose last exchange failed or was cancelled is never recycled.
- Point 3: one shared `AnonymousTransport` (default of `PageFetcher` and the other defaults); `URLSessionTransport` invalidates the main session it created itself.
- Point 4: the AQ feed is read once per launch (and when the list is shown); a rebuilt root reuses it.
- Tests: an engine counter of created `URLSession`s → N refreshes of one account create one probe connection; app test: two root builds → one AQ request.
- No change to `AccountsModel` or the refresh flow's decisions (coordination with #1390 on #893).

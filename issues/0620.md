# Issue #620: [SwiftHFR] Ledger: GAP and CHANGELOG entries written by a steward after merge, never by feature PRs

### Summary
As the operator, I want feature PRs never to touch `docs/CHANGELOG-LEGACY.md`, `docs/migration/GAP-LEGACY-VS-SWIFT.md` or their fragment folders. The author writes the entries in the PR body, and a steward writes them into the docs after the merge, in one docs-only batch PR. Then GAP and CHANGELOG can never again cause a conflict, a late push or a rerun of the macOS CI (operator, 2026-11-07).

### Why #614 is not enough
Fragments remove conflicts for **new** rows only when they are in the PR from its first push. Today:
- in-place edits of existing GAP rows still conflict;
- a fragment added late is a push, so the macOS jobs (about 10 min each on the shared queue) run again;
- #590, #604, #605, #607 and #608 each lost a CI run to this on 2026-11-07.

### Design
1. **The author's side.** A PR with doc-ledger entries adds a `### Ledger` section to its body and gets the label `ledger`. The section uses one fenced block per entry, in a fixed, machine-readable format:
   - `changelog`: the row cells, without a number;
   - `gap-new`: section, cells, H.1;
   - `gap-edit`: `GAP-NNN` and the cells to replace.

   The adversarial reviewer reviews this section like the code.
2. **The PR must not touch the ledger files.** The Docs consistency job fails a PR that changes `docs/CHANGELOG-LEGACY.md`, `docs/migration/GAP-LEGACY-VS-SWIFT.md`, `docs/changelog-legacy.d/` or `docs/migration/gap.d/` unless its branch is `docs/ledger-*` (the steward's). The job also checks that the `### Ledger` section of a `ledger` PR parses.
3. **The steward's side.** `tooling/docs/ledger.py`:
   - reads the merged PRs labelled `ledger` (REST: `gh api`), without `ledger: done`;
   - turns each entry into a fragment, or applies the in-place edit;
   - runs `fold.py`;
   - writes the branch `docs/ledger-<date>`.

   The steward opens one docs-only PR. It touches no `App/` or `Packages/` file, so the macOS jobs are skipped. The steward merges it on green CI with the mechanical check of AGENTS.md §8: on its base, `ledger.py` + `fold.py` reproduce it, so no adversarial review is needed. It then swaps the label `ledger` for `ledger: done` on each folded PR.
4. **Who is the steward:** the orchestrator's hygiene routine (`tooling/roadmap/hygiene.py`, daily, dry-run by default), or any orchestrator or sub-orchestrator after a batch of merges.
5. **Docs:** AGENTS.md §8, REVIEW-ROUNDS, CONTRIBUTING (merge criteria and required checks), the `.github/labels.yml` entries `ledger` and `ledger: done`, and the README of `tooling/docs/`.

### Acceptance criteria
- `ledger.py` has tests (stdlib only, `scripts/tests`): parsing each entry kind, refusing malformed blocks, being idempotent, and a dry run.
- A simulated batch of three PR bodies (one new changelog row, one new GAP row, one in-place GAP edit) gives a branch on which `fold.py --check` passes.
- The CI guard fails a PR that touches a ledger file from another branch.

### Transition
The PRs open on 2026-11-07 (#590, #604, #605, #607, #608) are handled by the sub-orchestrator by hand: their ledger rows move to the PR body, and the steward folds them after merge.

# Issue #1190: [SwiftHFR] reader: an edit prefill or a quote in flight does not hold the composer slot, so two composers can be set over one page

- State: closed
- Author: francoisgn · created 2026-11-18T20:09:41Z · updated 2026-11-19T11:27:39Z
- Labels: type: bug, priority: high, difficulty: easy, area: app, origin: audit, m4-review: quality

### Summary
As a member on a slow network, I want a second composer action to be refused while the first is still fetching its form, so that one page never ends with two composers set (LESSONS 11: a guard covers every path that acts).

### Scenario
Tap "+ › Editer" on a slow network, then "Répondre" while "Chargement de l'édition…" shows. The reply composer opens; when the prefill arrives, `editor` is set too. Symmetric: "Citer" in flight, then "Editer".

### Evidence (`7a61018f`)
- `App/SwiftHFR/Reader/Actions/MessageWriteModel.swift:62-68`: `guard progress == nil, editor == nil`, then `try await services.poster.editPrefill(target)`, then `editor = ReplyComposerModel(editing: …)` with no check of the reader after the await.
- `App/SwiftHFR/Reader/Quote/TopicReaderModel+Quote.swift:23-24`: `requestReply` checks `suspendsPageInteractions` only before its own awaits.
- `App/SwiftHFR/Reader/ReaderPageControls.swift:194-197`: the reply button is disabled by `isLoadingQuote || suspendsPageInteractions`, not by `writes.progress`.
- `App/SwiftHFR/Reader/TopicReaderModel+Composer.swift:196`: `suspendsPageInteractions` is true only once a composer is presented.

### Fix
One "busy" notion on the reader, set before the first await of `openEditor`, `requestReply`, `quoteMessage` and `quoteSelection`; re-check after each await and drop the late result with a feedback line.

### Test (fails before the fix)
`MessageWriteModelTests.aReplyOpenedDuringAnEditPrefillKeepsOneComposer`: poster suspended in `editPrefill`, `reader.requestReply()` opens the reply composer, resume the prefill, `writes.editor == nil`.

Confidence: high on the state (two composers set); the visible result (second sheet queued or refused by SwiftUI) was not observed.

Re-verified at `dev-swift` @ `fa96c1c1`: `MessageWriteModel.openEditor` guards only its own `progress`/`editor`, then sets `editor` after `editPrefill` without looking at the reader; `requestReply`/`quoteMessage`/`quoteSelection` check `suspendsPageInteractions` only before their awaits; the reply button ignores an edit in flight. No overlap with the open PRs (#1230 touches `TopicReaderModel.swift`'s fetch only).

Plan:
- One busy notion on the reader: the existing `isLoadingQuote` ("a composer is being prepared"), plus `composerSlotIsFree` = no composer open, none being prepared, no reply handed to the screen.
- "Editer" takes the slot before its await (so the reply button and the quotes are refused meanwhile) and is refused while a quote, a reply or a composer holds it.
- Every path re-checks after its awaits: a composer opened meanwhile (the author menu's MP) drops the late result, with a feedback line.
- Tests first: a reply asked during an edit prefill is refused and one composer opens; "Editer" while a quote is in flight sends nothing; an MP composer opened during the prefill drops the edit with a message.

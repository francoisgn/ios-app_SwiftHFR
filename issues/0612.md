# Issue #612: [SwiftHFR] Stop GAP and CHANGELOG-LEGACY conflicts: one fragment per PR, stable IDs, folded by the steward

### Summary
Every merge into `dev-swift` today put the other open PRs in conflict on `docs/CHANGELOG-LEGACY.md` (sequential row `#`) and `docs/migration/GAP-LEGACY-VS-SWIFT.md` (sequential `GAP-NNN`, the hand-kept H.1 tallies and the Counts table). Each conflict cost a merge commit, a renumbering and sometimes a review round: on 2026-11-07, #577, #578, #581, #583 and #605 were hit. The operator asked for a way to make these two files never trigger a review again.

### Design
1. **Fragments, not edits.** A PR never edits the two shared files. It adds one file per entry:
   - `docs/changelog-legacy.d/<issue>.md`: one line, with the same fields as today's row (section, French summary, lot/PR, legacy proof);
   - `docs/migration/gap.d/GAP-<issue>.md`: one row, with the same columns as today, plus the target section.

   Each PR adds a file with a unique name, so these files cannot conflict.
2. **Stable IDs.**
   - A new GAP row's ID is its **issue number** (`GAP-568`). Existing IDs go up to 229 and today's issues are above 500, so they never collide. Code pointer comments cite the ID from the first commit, and there is never any renumbering.
   - The changelog `#` column becomes the issue/PR number for new entries. Existing rows keep their numbers.
3. **Generated tallies.** The H.1 list, the Counts table and the changelog order are computed by a script, never edited by hand. The Counts table is already out of date by hand (162 vs 164, noted on #572).
4. **Folding.**
   - `tooling/docs/fold.py` moves the fragments into the two files, sorts them, regenerates the tallies and deletes the fragments.
   - It runs in the steward's daily routine (`tooling/roadmap/hygiene.py` or its README routine), as one docs-only PR. The orchestrator can also run it.
   - `--check` mode is called by the existing **Docs consistency** CI job. It checks fragment format, unique IDs, that no fragment ID clashes with a folded row, and that tallies match after folding.
5. **Review rule** (AGENTS.md §8, REVIEW-ROUNDS):
   - a commit that only merges `dev-swift`, or only renames or moves a fragment, keeps the PR's adversarial APPROVE;
   - a fold PR (fragments in, tallies regenerated, no other change) is merged on green CI with no adversarial review, because the script is the reviewer.

### Scope
- `tooling/docs/fold.py` with `--check`, plus tests (`tooling/` test style), run by Docs consistency.
- The two fragment folders, each with a short README stating the format.
- Update AGENTS.md §8 (the "Legacy fixes" bullet and the review rule), `docs/agents/REVIEW-ROUNDS.md`, `docs/lots/TEMPLATE.md` if it mentions GAP numbers, the PR template line, and the header text of both shared files.
- Transition: PRs already open keep their direct edits, and the orchestrator merges them as today. A fragment and a direct row for the same issue are flagged by `--check`.
- No change to existing rows or IDs.

### Acceptance
- Two test branches that each add a fragment merge with no conflict in either order. Show this with `git merge-tree` in the PR.
- `fold.py` folds them deterministically, and `--check` passes.
- Docs consistency fails on a malformed fragment or a duplicate ID.

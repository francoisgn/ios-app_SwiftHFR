# Issue #340: [SwiftHFR] SessionRefreshFlow: never adopt a refresh token across a same-account re-login (LOT-044 follow-up)

### Summary

`SessionRefreshFlow.adoptRefresh` can write the `hash_check` from a refresh made with the old cookies over the token of a same-account re-login that landed while the refresh ran. The next POST then gets HFR's bad-token answer (W17b). The case is rare but cheap to fence. Found by CodeRabbit on #309 (outside-diff finding at b2e83ff, steward analysis on #309); the operator asked for this follow-up on 2026-10-29.

### Where

`Packages/HFRKit/Sources/HFRClient/Session/RefreshUpdate.swift:53-73` (`adoptRefresh`).
- **Cookies are already safe.** Each refreshed cookie is written only if that cookie key still holds the seed's value, and a re-login rewrites `md_passs`/`md_user`.
- **The token is written when `hashCheck == seed.hashCheck`.** Identity is checked by `userKey(now:)`, so a re-login of the **same** account passes the identity check.

The race needs all three of these:
1. a same-account re-login lands while a refresh is in flight;
2. the login's token equals the seeded token (H0);
3. the refresh, made with the old cookies, returns a different token (H1).

The result is re-login cookies paired with token H1. Nothing is sent under another account and no data is lost: the next POST is refused, and the next form load records a fresh token.

### Scope

- Add a login generation to `HFRSession` (HFRNetwork):
  - `public private(set) var loginGeneration: Int`;
  - `public func advanceLoginGeneration()`, called by LOT-043's `adoptLogin` after it installs the cookies and token (`HFRClient/Login/HFRSession+Login.swift`).
- Carry the generation in `RefreshSeed`. `adoptRefresh` returns `.unconfirmed(.sessionChanged)` and writes nothing when the generation moved.
- Coordinate with #308 / PR #315 (`HashCheckSeed`, compare-and-set in `PostingFlow`/`TopicFlagFlow`). If #315 is merged first, consider having `HashCheckSeed` use the same generation, so one fence covers every token write. Otherwise keep the two independent and say so in the LOT-043/044 specs.
- This is a public API addition to HFRNetwork (`HFRSession`), so it needs no ADR. Sessions and tokens are a risky flow: the steward or core merges it, and an outside contributor's PR needs a cross-contributor review (EXTERNAL-AGENTS §7).

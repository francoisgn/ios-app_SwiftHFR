# Issue #1182: [SwiftHFR] app: an unreadable local store has no way out (`discardUnreadableData()` is never called)

- State: closed
- Author: francoisgn · created 2026-11-18T20:09:35Z · updated 2026-11-19T12:03:10Z
- Labels: type: bug, priority: high, difficulty: medium, area: app, origin: audit, m4-review: quality
- Source: https://github.com/ezzz/HFRnow/issues/1182

### Summary
As a member whose local file (pseudo lists, super-favourites, smiley favourites, upload history, reading positions, drafts) became unreadable, I want the app to offer a way to start again from an empty store, so that I am not left with a screen that says "illisible" for ever. Today the engine has the exit, and no screen calls it.

### Scenario
A small-store file is damaged, or was written by a newer build (TestFlight rollback, a backup restored from a newer build). Reads answer empty and **every write throws, at every launch**. The pseudo-list editor shows "illisible" with a "Réessayer" that re-reads the same bytes. The only exit is to reinstall. Separately, an undecodable drafts file is moved to `.corrupt` and nobody is told the drafts were set aside.

### Evidence (`7a61018f`)
- `Packages/HFRKit/Sources/HFRStorage/SmallStores/Core/SmallStoreState.swift:38` `discardUnreadableData()`, documented as "the single way out of a failed load"; same on `PseudoLists/PseudoListStore.swift:140` and `ReadingPositions/ReadingPositionStore.swift:138`.
- `grep -rnE "discardUnreadableData|didRecoverFromCorruptData" App/SwiftHFR` returns nothing.
- The app only displays the failure: `App/SwiftHFR/Navigation/FavoritesOptionsModel.swift:153-159`, `App/SwiftHFR/Settings/PseudoListEditorModel.swift:63-78` (retry = `manager.reload()`).
- `Packages/HFRKit/Sources/HFRStorage/Drafts/DraftStore.swift:69` `didRecoverFromCorruptData()` has no app caller.

### Fix
One shared "données illisibles" recovery (confirmation, then `discardUnreadableData()`, which keeps the `.corrupt` copy), reachable from every screen that shows a load failure; a one-time notice when `didRecoverFromCorruptData()` is true.

### Test (fails before the fix)
`PseudoListEditorModelTests/discardAfterConfirmationMakesTheStoreWritable`: a store over a corrupt file; `retry()` still fails; `discard()` then `add()` succeeds and the `.corrupt` file holds the old bytes. Fails today: the model has no `discard`.

### Definition of done
Every screen that can show a store load failure offers the recovery; the test above and one per store family pass.

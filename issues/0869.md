### Summary

As a reader in any topic list, I want to swipe a row from right to left to add or remove the favourite, and use a second swipe option to add or remove the super favourite, so that I can manage my flags from every list and not only from the flag views. (Operator feedback, 2026-11-13.)

### Observed

The current trailing swipe action "Supprimer" exists only in the views that list flags (Favoris, Suivis, Lus). In "Tous" and in the category topic lists, a row offers no flag action.

### Expected

- **Swipe from right to left, first action:** "Ajouter aux favoris" when the topic is not a favourite, "Retirer des favoris" when it is.
- **Second action:** "Ajouter aux super favoris" or "Retirer des super favoris", by the same rule.
- Available in **every** topic list (categories, Tous, Favoris, Suivis, Lus, search results), with the label following the topic's current state.
- The writes go through the existing flows: the favourite write `TopicFlagFlow` (LOT-051, confirmed-session rule of #314) and the super-favourites store (`SuperFavoritesStore`). No new HFR request without a capture.

Plan (child of cloud/orch, #893):
- Trailing swipe in every topic list (categories, Tous/Favoris/Suivis/Lus filters, Favoris, Drapeaux): a favourite action whose label follows the row's state, and a second action « Ajouter aux / Retirer des super favoris » (`SuperFavoritesStore` through `FavoritesOptionsModel`, now reachable from the forum lists too).
- « Retirer des favoris » on a favourite row (`favoris.gif`, `TopicFlag.yellow`) goes through the existing `TopicFlagFlow.removeFavoriteFromList` (session check first, #314; failure shown, row unchanged, never resent). Blue/red flag rows keep legacy « Supprimer ».
- Same actions as VoiceOver `accessibilityActions` (HIG note above) and in the context menu.
- Model tests for each transition and list kind, plus a counting loopback transport (`hosts: .exactHost`) proving one write per swipe.

**Blocker on « Ajouter aux favoris » (needs an operator decision, not coded):** HFR's only captured add request is the `addflag.php` link carried by each *message* of a logged-in topic page (`HFR-PROTOCOL.md` §6c, `R21`, `P03a`); a list row has no such link (no list capture contains `addflag`), and legacy has no list-level add either (`Favorites.swift:1189-1212`, `MainWindow.swift:752-770` @ 87fe0d1c: trailing swipe = « Supprimer » only). Building the URL from the row (`post`, `numreponse`, `ref`, `subcat`) would be a guessed request. Two ways forward:
- **A (captured requests only):** GET the page of the row's last message (`numreponse=`, R25), read that message's `addflag` link (`MessageActionsParser`), follow it with `TopicFlagFlow.addFavorite`. Side effect to accept: reading the page moves the topic's read flag to that page's last message (`HFR-PROTOCOL.md:580`), i.e. the new favourite sits at the end and the topic reads as read.
- **B:** a Mac capture of an `addflag.php` GET whose URL is built from list data only, to prove HFR accepts it; then a direct GET.

Until one is chosen, the PR ships the rest as `Refs #869` and the add half stays open here.

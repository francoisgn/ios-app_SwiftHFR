# Issue #1193: [SwiftHFR] composer: image chips and the upload history load thumbnails with `AsyncImage`, outside the app's image client and policy

- State: open

- Labels: type: chore, priority: high, difficulty: easy, area: app, status: claimed, origin: audit, m4-review: quality
- Source: https://github.com/ezzz/HFRnow/issues/1193

### Summary
As the maintainer, I want every image the app requests to go through the one cookie-less image client and its policy (scheme and host check, redirect filter, size cap), so that there is one way to load an image. Two views are the only exception.

### Scenario
Opening the image panel, or showing a chip, requests the host-supplied thumbnail URL through `URLSession.shared`: the policy's checks do not apply, and the shared cookie store and cache are used. A stored history entry whose URL is `http://` (`RehostResponse.webURL` accepts `http`, `Packages/HFRKit/Sources/HFRNetwork/ImageHosts/RehostResponse.swift:88-91`) or on another host is fetched as is. No forum cookie is involved.

### Evidence (`7a61018f`)
- `App/SwiftHFR/Composer/ComposerImageChips.swift:64`: `AsyncImage(url: chip.thumbnail)`.
- `App/SwiftHFR/Composer/ImageUpload/ImageUploadView.swift:177`: `AsyncImage(url: image.miniURL ?? image.mediumURL ?? image.fullURL)`.
- These are the only `AsyncImage(` in `App/SwiftHFR`; every other image goes through `ReaderImageFetcher` (`Smileys/SmileyImageLoader.swift:60`, `Profile/UserProfileView.swift`, whose header says "not `AsyncImage`").

### Fix
A small thumbnail view over `ReaderImageFetcher` (third parties allowed, host filter = the configured rehost host), as `SmileyImageLoader.gif()` does for Giphy.

### Test
A convention check that `App/SwiftHFR` holds no `AsyncImage(` and no `URLSession.shared` (fails today); a hosted test that a chip with an off-host thumbnail triggers no request.

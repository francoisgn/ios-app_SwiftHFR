# Issue #512: [SwiftHFR] M4: iPad split view, tapping a topic in Favoris must always show it on the right (bug reported on the current app)

- State: open
- Author: francoisgn · created 2026-11-06T07:51:23Z · updated 2026-11-06T07:51:23Z
- Labels: type: bug, priority: medium, difficulty: medium, area: app, status: ready, host: mac
- Source: https://github.com/ezzz/HFRnow/issues/512

### Summary
As a member reading on an iPad in landscape, I want every topic I tap in the Favoris list to open on the right, so that I never read the wrong topic while the topic I tapped is marked as read without being shown.

A user reported this on the **current app** (legacy, `master`). It is filed in **M4** (validated legacy parity) so that SwiftHFR is checked not to have it, and so that the report and its leads are not lost for the legacy app.

### Report (user, 2026-11-06)
- **Device:** iPad Pro M5, **iOS 26.7**, landscape, split view (list on the left, topic on the right).
- **Symptom:**
  - A topic is already shown on the right.
  - Tapping other topics in **Favoris** on the left does not refresh the right side, which keeps the last topic that worked.
  - **Each tapped topic is still counted as seen/read.**
- **Frequency:** first time; no known reproduction.
- **Video:** https://youtu.be/Iu3Zr8Qon_Q

### Reading of the symptom (hypotheses, to confirm)
- "Counted as read" most likely means the topic page **was fetched with the session**: HFR marks a topic read when its page is served.
- So the selection reached the code that loads the topic, but the **detail column kept showing the old view**. This points to a stale identity or a lost reset of the detail, rather than to the tap itself.
- To tell apart from: the list marking the row read locally on tap. In that case nothing was fetched, and only the local row state changed.

### Legacy leads (for ezzz, `master` @ 21173e7, read-only here)
- `HFRswift/Swift/MainWindow.swift:2018-2037`, `selectTopic(_:for:)`:
  - it sets `favoritesTopicTarget`, regenerates `detailNavigationResetToken` and sets `preferredCompactColumn = .detail`;
  - the detail is identified by `.id(detailNavigationResetToken)` (`:1912`).
- Candidates:
  - a race between the token reset and the per-destination target, for example a `setIPadSidebarDestination` or `iPadForumIdentity` change in the same update, which leaves the detail on an older target;
  - the detail view kept alive by a `NavigationStack` path that does not depend on the token;
  - a regression of the split / Duo work (#372, #450) on iPadOS 26.
- **First thing to capture:** with the video, check whether the topic is fetched on tap (network log or HFR read state) and whether `favoritesTopicTarget` changes while the detail does not.

### SwiftHFR side (what this M4 issue checks)
- In SwiftHFR the detail is a `TopicReaderView` keyed by `.id(topic.id)` on `navigation.selectedTopic` (`App/SwiftHFR/Root/RootTabsView.swift:140-151`; selection from `TopicListView` `List(selection:)`). Each topic gets its own reader model, so the bug should not exist **by design**. It still has to be **shown on a device**.
- **Mac/iPad check** (iPad, iPadOS 27 and, if available, 26.x; landscape split, Favoris tab and sidebar root):
  1. Open topic A, then tap B, C and D in turn. Each shows on the right, and the title and first post match the row.
  2. Tap fast (B then C within half a second). The right side ends on C, and no stale B is shown. A cancelled B load must not mark B read: B's page must never be fetched after C was selected (see `TopicReaderModel` cancellation, LOT-083).
  3. Tap the same topic twice. It reloads or stays, with no blank state.
  4. Repeat after rotating, after a fold or unfold on the Duo, and after switching sidebar destination (Catégories → Favoris).
  5. Do the same from Catégories, Messages and a search result.
- If a step fails, open a bug with the steps, screenshots and the suspected file, without `host: mac`, so a cloud session fixes it.

### Reading of the symptom (hypotheses, to confirm)
- "Counted as read" most likely means the topic page **was fetched with the session**: HFR marks a topic read when its page is served.
- So the selection reached the code that loads the topic, but the **detail column kept showing the old view**. This points to a stale identity or a lost reset of the detail, rather than to the tap itself.
- To tell apart from: the list marking the row read locally on tap. In that case nothing was fetched, and only the local row state changed.

## Analysis (read-only, sub-orch) 2026-11-07

Read at `origin/dev-swift` `4b1e77f`, then cross-checked with PR #575 (head `f23108c`). The video was not watched. Nothing was changed.

### The SwiftHFR iPad path, Favoris

1. **Root.** `RootNavigationView.swift:26-30, 47-49`: a regular-width iPad gets `RootSidebarView`; a compact width (Slide Over or narrow Split View) gets `RootTabsView`. Both read the same `RootModel`, so the same `NavigationModel`s.
2. **Columns.**
   - `RootSidebarView.swift:70-72`: the content column is `TopicsColumn(navigation: model.favorites)`, keyed `.id(source)` (`RootTabsView.swift:128-131`).
   - `:85`: the detail column is `ReaderColumn(navigation: model.favorites)`.
3. **Selection.** `TopicListView.swift:25`: `List(selection: $selection)`, bound to `$navigation.selectedTopic` (`RootTabsView.swift:129`). Each row is `.tag(topic)` (`:118`).
4. **Detail.** `RootTabsView.swift:145-160`: `ReaderColumn.body` reads `navigation.selectedTopic` (observed), calls `navigation.reader(for: topic)`, and wraps the reader in its own `NavigationStack` with `.id("\(topic.id)#\(navigation.readerGeneration)")`.
5. **Model cache.** `NavigationModel.swift:89-102`: `reader(for:)` returns the cached model when `currentReader.id == topic.id`; otherwise it builds a new `TopicReaderModel`. **Building a model fetches nothing.**
6. **The only session fetch of a topic page.** It is `TopicReaderView`'s `.task { await model.onAppear() }` (`TopicReaderView.swift:159-162`), through `TopicPageSource`, whose contract says "never call it for prefetch" (`TopicPageSource.swift:7-9`).
   - When the old view goes away, its `onDisappear` calls `model.cancel()` and `controller.stopLoading()` (`:163-170`).
   - A superseded or cancelled load never delivers (`TopicReaderModel.swift:351-356`, #108).

**Conclusion: no path found where the selection changes, the new topic is fetched (so marked read), and the detail keeps the old reader.**
- The fetch that marks B read is started only by the `.task` of B's own reader view.
- That view only exists as the detail column's content, under an identity built from the same `topic.id` that the model cache uses.
- Legacy's failure shape (a reset token and a per-destination target updated separately, `MainWindow.swift:2018-2037` on `master`) has no counterpart: identity and model derive from one observed value.

### Residual risks found (smaller than the report)

- **R1: fast taps can mark a topic read without showing it** (real, not fixable client-side).
  - Sequence: tap B, then C before B's page arrives.
  - B's view goes away and cancels its task. `URLSessionTransport` uses `session.data(for:)`, so the URL task is cancelled too.
  - If HFR already served B, B is marked read while the detail ends on C.
  - The detail is never wrong, and B is not fetched again after C is selected: step 2 of the check holds. "A cancelled load must not mark B read" cannot be guaranteed for a request already sent. Reword that check to "no request for B **starts** after C is selected".
- **R2: two derivations that must stay in step.** The view identity comes from `topic.id` + `readerGeneration`; the model comes from the cache keyed by `topic.id`. They agree today. A later change to either one could make them diverge without any test catching it (see the test below).
- **R3: a size-class flip mid-load** (rotation in Split View, Stage Manager resize).
  - The root swaps between `RootSidebarView` and `RootTabsView` while both show the same cached model.
  - This is #566's H1b (the old view's `onDisappear` cancels the new view's load). Its symptom is a spinner, not a stale topic.
  - **#575 fixes it:** `viewDidDisappear(viewer:)` cancels only for the view that appeared last.
- **R4: the list reloads under the selection.** Pull to refresh, or `autoRefresh` on reappear (`TopicListModel.swift:189-193`), replaces the rows. The selection is matched **by value**, so the highlight can drop while `selectedTopic` stays. Tapping the same topic again then returns the cached reader (same `id`): no reload, but the right topic. This is not the reported bug. If ever wanted, select by `id`.

### Cross-check with #575

- #575 does not touch the selection path (`NavigationModel` and `ReaderColumn` are unchanged).
- Its retry of an unrequested `.cancelled` is guarded by `!Task.isCancelled`. A superseded B, whose view went away and cancelled the task, is therefore **not** fetched again. This keeps R1 to the one in-flight request.
- One case to include in its Mac check: tap B then C quickly. With `subsystem:SwiftHFR category:reader`, expect:
  - B: `disappear … current=true`, then `load cancelled`;
  - no second `load start` for B's model.

### Proposed test (closes the acceptance criterion; no existing test covers a plain selection change)

Existing tests cover parts:
- `NavigationModelTests.changingTheSourceDropsTheReaderSoTheTopicReopensFresh`, `…aPageAskedForOneTopicIsNotUsedForAnother`, `…openingARowAtAPageBuildsANewReaderThere`;
- `TopicReaderModelTests.aSupersededLoadNeverDelivers` (`:82`) and `…aCancelledLoadNeverDelivers` (`:101`).

None selects A, then B.

1. **Model level** (`App/SwiftHFRTests/NavigationModelTests.swift`), `selectingAnotherTopicBuildsAReaderForThatTopic`:
   - select A; `ra = reader(for: A)`;
   - select B; `rb = reader(for: B)`;
   - expect `rb !== ra`, `rb.requested == ReaderTarget(opening: B)` and `reader(for: B) === rb`;
   - expect `FakeTopicPages.requests` to be empty: building a reader fetches nothing.
2. **Hosted view level** (app-hosted, `UIWindow` + `UIHostingController` as in `AppThemeTests`), `theDetailFollowsTheSelectionAndDropsTheOldLoad`:
   - host `ReaderColumn(navigation:)` over a `FakeTopicPages` whose A load waits on a `ReaderGate`;
   - set `selectedTopic = A` and wait until `requests == [A]`;
   - set `selectedTopic = B`, open the gate, wait until B's model has a page;
   - expect:
     - `requests == [A, B]` (no A after B);
     - A's model page is nil (never delivered);
     - `navigation.reader(for: B)?.page?.topicID == B.topicID`;
     - no third request after a short settle.

   The page fetch only runs from the shown view's `.task`, so "B requested and delivered" proves that B's view replaced A's in the detail.

### Minimal hardening (optional: no bug found, so not a fix)

Remove R2 by taking the identity from the model itself:

```swift
// ReaderColumn
.id(ObjectIdentifier(model))
```

- Keep reading `navigation.readerGeneration` in the body, because `open(_:at:)` on the topic already shown does not change `selectedTopic`.
- The view is then rebuilt exactly when `reader(for:)` returns a new model, and never otherwise.
- Test 2 covers it. Land it after #575, which edits the same reader lifecycle.

**For ezzz (legacy, `master`):** the leads in the issue body stand. The SwiftHFR shape above, with one identity derived from the selection and the fetch started only by the view being shown, is the pattern to compare against.

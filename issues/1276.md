I cannot name a commit from the code. The Mac needs to run **one Instruments capture, or a bisect**; I list both below. I am not writing a test, because I have no path to make fail.

### Why the spinner cannot be stuck by the app's own state
- The spinner is the overlay `ProgressView`, shown only while `value == nil`, `error == nil` and `isLoading` (`TopicListView.swift:298-311`).
- `isLoading` goes back to `false` in only two places: when the current load ends (`ContentLoader.finish`, `ContentLoader.swift:64-84`), or on `cancel()`. A superseded load leaves the flag to the newer load, which ends in turn. Nothing bumps `generation` without one of these.
- On return, `TopicListModel.onAppear` runs `loadIfNeeded`, which does nothing while `isLoading` is true (`TopicListModel.swift:265-268, 275-277`). Since the list did show up, the first load had ended by then.

### What the Favoris load waits on, and the bound of each wait
1. `await isLoggedIn()`. Its answer comes from `ForumListModel.loginStatePage`, or else from `HFRSession.isLoggedIn()`, a call on the session actor (`NavigationModel.swift:84-87`, `AppEnvironment.swift:123-125`). It does no network call and should not hang.
2. `dataSource.favorites(filter:)`, a GET to `forum1f.php` (`ForumDataSource.swift:66`). Its idle limit is `RequestTimeout.standard = 10` s (`HTTPRequest.swift:21`). If no data arrives for 10 s, the load ends in `.timedOut` and the error screen shows.
3. #1230: one retry if that GET comes back `.cancelled` when nobody asked for it (`ContentLoader.swift:37`). That adds at most one more request. A second such cancellation shows `.other`, which is an error screen, not a spinner.

So the longest a spinner can last is roughly 10 s × 2 attempts plus connection setup, followed by rows or an error. **A spinner that lasts that long means the Favoris request itself is waiting on the network at launch.** The iOS transport did not change in the window (`3dfed078` is Linux-only), so what changed is most likely **what else the app sends at the same time**.

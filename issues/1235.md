# Issue #1235: [SwiftHFR] accounts: a session that expires in place is not always reflected in the lists (launch race, no re-check of a valid session)

- Labels: type: bug, priority: low, difficulty: easy, area: app, status: needs-triage, origin: audit, m4-review: quality
- Source: https://github.com/ezzz/HFRnow/issues/1235

### Summary
As a member whose session expired, I want the lists to show me logged out, so that the Favoris/Suivis/Lus filter and a login wall are not presented as if I were signed in. #1231 (#1195) covers a re-login in place and an expiry found by a check; two expiry cases remain, found by its Fable review (rounds 1 and 2).

### Cases
1. **Launch race.** At launch with an expired session, a startup topic list whose load starts before the home page lands takes the session's answer (`NavigationModel.isLoggedIn()` falls back to `HFRSession.isLoggedIn()`, cookie-based, `Packages/HFRKit/Sources/HFRNetwork/Session/HFRSession.swift:159`; `ForumSessionCheck` never clears the session). It loads "signed in". The check's expiry then calls `RootModel.currentSessionChanged(expired: true)`, which returns early because the home page already says logged out (`ForumListModel.sessionDidChange(expired:)`, #1231), so that list keeps the filter offered and shows a login wall as a plain notice until refreshed. Same as `dev-swift` before #1231.
   Fix idea: on that early return, still reload the cached lists whose page `isSignedIn` (lists already logged out cost nothing).
2. **A valid session that expires during a run** is never re-checked: `AccountsModel.recheckUnconfirmedSessions` takes `.restored` and `.checkFailed` only, so nothing bumps `currentSessionChanges`; the lists keep the last home page's "signed in" until a pull on Catégories.
   Fix idea: needs a product decision on what detects it (a list page that answers logged out while the home page said logged in could signal it).

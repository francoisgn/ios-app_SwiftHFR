# Issue #1050: [Legacy 4.0.x + SwiftHFR] Composer: delete an uploaded image from the host (Chevereto v4.5 delete link)

- Labels: type: feature, priority: medium, difficulty: medium, area: app, status: needs-triage, host: mac

### Summary

As a poster, I want to delete from the image host an image I uploaded from the reply composer, so that a picture I posted by mistake (or no longer want online) is really removed, not only hidden from my local history.

_Operator request, 2026-11-17. The image host is `img3.super-h.fr`, a **Chevereto v4.5.x** server._

### Relation to earlier work (not a duplicate)

- FEAT-019 (#163, closed) asked for an "upload history with server-side delete". LOT-103 (#194, closed) shipped the **local part only**: removing an entry clears the history and says the image stays online. The server-side delete was left **out of scope** because it was not evidenced (`docs/features/FEAT-019.md` line 8; `docs/HFR-PROTOCOL.md` §7b **B12**).
- This issue reopens that server-side half, now that we know the host runs Chevereto v4.5.x and can look at its API.

### What we know

**From our capture** (`U01`, #302, PR #394): the upload answer of `POST /api/1/upload` carries `image.delete_hash` and `image.delete_url` = `https://img3.super-h.fr/image/<id_encoded>/delete/<delete_hash>`. Opened once without a browser session, that URL redirected twice and then answered 404 (observed, **not captured**).

**From the Chevereto v4 docs** (read 2026-11-17):
- API V1 has **only the upload endpoint** (`/api/1/upload`, key as `X-API-Key` header or `key` parameter): https://v4-docs.chevereto.com/api/1/file-upload.html, https://v4-docs.chevereto.com/api/1/authorization.html
- API V4 is only the multi-tenant admin API (`/_/api/4/tenants`…), not images: https://v4-docs.chevereto.com/api/4/tenants.html
- **No image-delete API endpoint is documented**, in 4.0 to 4.5. The only delete path is the per-image delete link, introduced in 4.0: "Image uploads include a unique delete link which on access will permanently remove the image" (https://v4-docs.chevereto.com/introduction/changelog/4.0.html).
- The docs say nothing on whether that link needs a browser session, a confirmation page or a CSRF token, nor on guest uploads vs user-key uploads, nor on expiry.

**What the apps store today:** nothing that allows a delete.
- Legacy: `RehostUploadedImage` (`HFRswift/Swift/ReplyService.swift:1852`) keeps the URLs and sizes, **not** `delete_url` / `delete_hash`.
- SwiftHFR: the upload history (LOT-103, synced through iCloud KVS since #966) does not keep them either.
So images uploaded before the fix can never be deleted from the app.

### Open questions

1. **How does `delete_url` behave for a plain HTTP client?** Capture needed (Mac, operator go: it deletes a real image on a third-party host, use a throwaway 16×16 upload as in #302): GET the `delete_url` with no cookie; follow the redirects; does it delete, ask for confirmation (form + token), or require a logged-in session? Then GET the image URL to check it is gone (404).
2. Our uploads use the app's shared key. Are they guest uploads or owned by the key's account? Does that change who can delete?
3. If the link needs a confirmation page, can the app post that form (token in the page), or must it open the link in Safari / `ASWebAuthenticationSession`-like web view for the user to confirm?
4. Should the host's admin (super-h.fr) be asked whether a proper delete endpoint, or a longer-lived guarantee on delete links, is possible?

### Proposal (once question 1 is answered)

- **Store** `delete_url` (or the `delete_hash` + `id_encoded`) with each new upload. It is a **secret**: anyone holding it can delete the image. Keep it out of logs, out of the iCloud KVS sync (or decide explicitly), and anonymize it in every fixture (as `U01` does).
- **Delete action** in the upload history (and right after an upload, e.g. "Supprimer l'image du serveur" in the image's menu), with a confirmation that says the image will disappear from every post that shows it and cannot be undone.
- Then call the delete link (or open it, depending on question 3), check the image URL now answers 404, and only then remove the entry; on failure keep the entry and say so.
- Older entries without a delete link: keep today's "remove from history, the image stays online" wording.
- Scope: legacy (`HFRswift`, composer in `MessagesView` / `AnswerView`) and SwiftHFR (`HFRClient` rehost client + upload history), same behaviour.

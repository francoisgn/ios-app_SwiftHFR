### Summary
« Dark topic » is the community's word for a non-public topic held in a group MP (operator, 2026-11-12): the goal is a group MP that reads **as close as possible to a public topic** (flag, reading position, unread until the last post).

As a member of group MPs ("MP multiple") with MPStorage on, I want SwiftHFR to move and follow the MP flags as legacy does, so that a group MP opened for a few seconds still shows and reopens where I stopped, as a flag does for a public topic.

**Scope (operator, 2026-11-12):** items **1, 2 and 3** of the proposal below are in scope ("Ok 1, 2, 3"): legacy parity with MPStorage on, the app-only reading position for everyone, and the "not fully read" mark. Item 4 (one-to-one MPs): not needed, but if one code path for every MP is simpler than a group-only one, do it for every MP (operator, 2026-11-12); the MPStorage `mpFlags` write stays group-only as legacy unless the spec shows other clients accept one-to-one flags. The operator's missing experience in legacy was most likely MPStorage being off (default). Its on/off switch in Réglages comes with #859 (per-function MPStorage switches).

### Observed (operator, device, 2026-11-12)
- Opening a group MP marks it read on HFR at once, even if I only glanced at it and have not read the last pages. Nothing in the list then tells me where I stopped.
- Wanted: an experience comparable to a public topic's flag. An app-only implementation is fine.

### What HFR offers (documented; nothing guessed)
- MP list: one's own state is only the list icon, `closedbp.gif` "On" (new message) / `closedp.gif` "Off" (HFR-PROTOCOL §6c LOT-023, `R13a`, `R13b`, `R13u1`). HFR sets it to read when the conversation is opened.
- **Mark unread exists**: `GET /user/nonlu.php?…`, linked from every MP page that shows messages; answer `W18` "Le message a été marqué comme non lu avec succès", the list then shows the conversation unread (HFR-PROTOCOL `:252`, `:643`, E6). It is whole-conversation, with no position.
- **No server-side read position for an MP is documented**: flags (`addflag.php`, `P03*`) are captured on public topics only. Whether `addflag` works on an MP is **not captured**: if we want a server flag, that needs a capture first (host: mac capture issue), never a guess.

### What legacy does, and why the operator never saw it
- Legacy keeps a **per-MP read position in MPStorage** (`mpFlags`, HFR-PROTOCOL §3.3; a JSON document in a private MP, shared with other HFR+ clients such as DTCloud):
  - write: after a group MP page loads, the flag moves forward to that page's last message, only if the page is at least the stored one (`OnlineMessagesTableViewController.m:1797-1811`, `MessagesView.swift:3582-3606`, `Common.swift:1567-1580` @ 87fe0d1c);
  - read: the group row shows `⚑ <page> / <max>` and opens at the flag (`MPListView.swift:354-377, 775-786`, `HFRMPViewController.m:228-251`, link `MPStorage.m:539` @ 87fe0d1c).
- All of it runs **only when "Stockage MP" is on** (`mpstorage_active`, default **false**, `AppSettingsView.swift:112-113` @ 87fe0d1c), which is why a member who never switched it on never had this experience.
- SwiftHFR today (LOT-130, #220): reads and shows the flags other clients write (`MessageListModel.flagLabel(for:)`, `MPStorageSyncModel.flag(for:)`), but **never writes them** and never opens at the flag: this was left as a follow-up in `docs/lots/LOT-130-*.md` "Out of scope", with no issue until this one. `MPStorageDocument.upsertMPFlag(_:stamp:)` already exists in the engine.

### Proposal (items 1-3 in scope, operator 2026-11-12; item 4: implementer's call, whichever is simpler)
1. **(a) Parity, MPStorage on**: port the legacy write (flag moves forward to the last message of each group MP page loaded) and the open-at-flag tap. Writes go through LOT-130's edit API (debounced; one forum write per sync, not per page).
2. **(b) App-only reading position, for everyone (MPStorage off too)**: a local per-account store `conversation → last message reached (page, numreponse)`, updated as the reader scrolls (the reader already knows the visible message). The MP list shows `⚑ <page> / <max>` from it, and a tap opens at that message. When MPStorage is on, it is the same position, synced.
3. **(b) "Not fully read" marker**: while the stored position is before the conversation's last post, the row keeps an app-side unread mark (e.g. the unread dot/capsule of topic rows), whatever HFR's own icon says. Calling `nonlu.php` automatically on leaving is possible (W18) but is a forum write on every visit: **not by default**; at most an option, operator's call.
4. Scope: group MPs first (legacy flags them only); one-to-one MPs as an option, operator's call.

### Acceptance criteria
- Open a group MP at page 1 of 12, read to page 3, leave: the list shows `⚑ 3 / 12` and the not-fully-read mark; reopening lands on the last message reached.
- Read to the last post: the mark disappears; a new message from someone else brings it back.
- MPStorage on: the position is written to `mpFlags` as legacy does (forward only), and a flag written by another client is honoured.
- No request leaves the process in tests (scripted transport, as `MPStorageSyncTests`); tests shown to fail without the change.
- Ledger: GAP-119 edit (flags written, open at flag) and a new row for the app-only position if (b) is accepted.
